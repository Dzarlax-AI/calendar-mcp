Calendar Authentik outpost isolation

Status: implemented on 2026-08-25; authenticated-browser acceptance remains pending a user session check.

Problem and evidence

The Calendar Platform UI router uses the shared authentik-auth Traefik middleware. Its forward-auth target is the shared authentik-proxy outpost. An unauthenticated request to calendar.dzarlax.dev/diagnostics was redirected with Readeck scope and callback:

ak_proxy_readeck
https://read.dzarlax.dev/outpost.goauthentik.io/callback

The browser correctly rejects that cross-origin redirect while the SPA is fetching its API, causing the 404/CORS and unavailable-diagnostics symptoms. The existing global Traefik outpost router already owns PathPrefix(/outpost.goauthentik.io/); we will preserve it unless live verification disproves this routing model.

Desired outcome

  • Calendar has its own Authentik Proxy Provider/Application and outpost binding (or a verified multi-application outpost configuration that produces an equivalent Calendar-specific callback).
  • Calendar's protected router uses a dedicated authentik-calendar middleware; Readeck and the shared middleware remain unchanged.
  • An unauthenticated top-level Calendar visit returns through calendar.dzarlax.dev/outpost.goauthentik.io/callback, not read.dzarlax.dev.
  • After login, /diagnostics loads and its quarantine request returns JSON without a cross-origin redirect.

Scope and likely locations

  • Authentik administration: new Calendar application, provider and outpost relationship; capture IDs/settings before changing them.
  • personal_ai_stack/deploy/authentik/docker-compose.yml: add a separately named proxy only if the provider/outpost design requires it.
  • personal_ai_stack/deploy/calendar-mcp/docker-compose.yml: define a Calendar-specific forward-auth middleware and attach it solely to calendar-platform-ui.
  • This plan. No Calendar Go/React change is in scope unless the corrected auth boundary exposes a separate, reproducible client contract issue.

Implementation sequence

  1. Read the current Authentik applications, proxy providers and outposts; record the Readeck binding, existing proxy token owner, and the expected Calendar external host. Do not expose tokens.
  2. Create a Calendar-specific Authentik application and proxy provider with the Calendar external host and authorization policy. Prefer a dedicated outpost/proxy when the current outpost cannot safely serve both applications; otherwise use Authentik's supported multi-application binding only after proving the callback is host-correct.
  3. Add the new Calendar forward-auth middleware to the Calendar deploy configuration. It must target only the Calendar outpost/proxy and retain the identity response headers required by the app. Leave authentik-auth and authentik-readeck untouched.
  4. Deploy the new/updated outpost first and verify its health. Then recreate only the Calendar UI service so Traefik discovers the new labels. Do not restart the shared proxy or Traefik unless the verified design requires it and a fresh approval is obtained.
  5. Validate both top-level browser authentication and API calls. Only then remove no configuration; the old middleware remains as rollback.

Verification and acceptance criteria

  • Unauthenticated GET https://calendar.dzarlax.dev/diagnostics begins a Calendar-specific login flow and has no read.dzarlax.dev callback or Readeck scope.
  • After login, the browser remains on Calendar, /diagnostics renders, and /api/ui/diagnostics/quarantine returns 200 JSON.
  • Calendar health stays healthy; calendar UI and worker logs show no new auth proxy errors.
  • Readeck top-level login and its API path keep working unchanged.

Risks and rollback

  • Incorrect provider/outpost association can lock out Calendar. Roll back the Calendar router label to authentik-auth and recreate only Calendar UI.
  • Changing the existing shared outpost can affect Readeck. We will not mutate it unless the pre-change snapshot shows a supported, low-risk configuration and Readeck is included in verification.
  • Proxy tokens and provider settings are secrets; commands and logs must redact them.
  • A successful internal header-based request is not acceptance evidence; real browser login is required.

Actual implementation and evidence

  • Live inventory showed that the existing embedded outpost already serves several proxy providers. The Calendar application existed but was not linked to any provider.
  • Created Calendar ForwardAuth with https://calendar.dzarlax.dev, the standard five proxy claims, and the existing authorization/invalidation flows. It was attached to the Calendar application and the existing embedded outpost.
  • No Traefik labels, images, environment files, or containers needed changing or restarting. The global outpost callback router correctly serves Calendar by host.
  • External unauthenticated check now redirects Calendar to calendar.dzarlax.dev/outpost.goauthentik.io/callback with ak_proxy, while Readeck still redirects to its own callback with ak_proxy_readeck. Calendar serve/worker stayed healthy and the proxy reported zero errors in the five-minute check.
  • Limitation: a real authenticated browser session remains required to prove the post-login diagnostics screen and API response; this cannot be established from anonymous HTTP headers.
