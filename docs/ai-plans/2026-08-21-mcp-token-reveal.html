MCP token reveal in Settings

Implementation plan · 2026-08-21 · Branch feat/mcp-token-display

Add a deliberate, short-lived way for the authenticated single user to retrieve the primary MCP API key while keeping the legacy migration key hidden.

Summary and decision

Approved design: option A. The Settings page shows the MCP endpoint, a masked token field, Reveal, Copy, and Hide controls. Only API_KEY can be revealed. API_KEY_LEGACY is represented only by a Configured / Not configured status.

This is intentionally a single-user convenience. It does not introduce token creation, rotation, revocation, per-client scopes, or a database schema.

Current behavior

  • The MCP Streamable HTTP endpoint is served at /mcp; the external origin comes from CALENDAR_PUBLIC_URL.
  • API_KEY and optional API_KEY_LEGACY are loaded from the environment and accepted by the MCP authentication middleware.
  • The protected Settings page reports installation readiness and deliberately displays no secrets.
  • Protected UI routes trust the Authentik identity header; state-changing POST requests additionally enforce exact Origin and CSRF validation.
  • There is no UI path to retrieve a configured MCP key, so client setup requires server-side environment access.

Desired behavior

  1. Settings initially renders the MCP endpoint as {CALENDAR_PUBLIC_URL}/mcp, a masked key placeholder, and the legacy-key status. Neither key appears in the initial HTML.
  2. Reveal sends a same-origin authenticated POST containing the existing CSRF token.
  3. The server returns only the primary API_KEY in a non-cacheable JSON response.
  4. The browser inserts the key using textContent, enables Copy and Hide, and starts a 30-second timer.
  5. Hide, timer expiry, and page exit remove the key value from the DOM and reset the controls.
  6. Failures appear inline without putting the key in a URL, redirect, flash message, or log.
Security boundary: any identity accepted by the configured Authentik ForwardAuth boundary can retrieve the primary master key. This is acceptable only while the installation remains single-user. A multi-user deployment must move to per-client, revocable, stored-as-hash tokens.

Assumptions

  • The web UI and MCP endpoint share the same public origin.
  • CALENDAR_PUBLIC_URL has no trailing slash, as required by current configuration validation.
  • Authentik remains the only public ingress to protected UI routes and strips client-supplied identity headers.
  • The primary API key exists in authenticated deployments; the legacy key may be absent.
  • No token value will be added to persistence, analytics, audit records, or application logs.

Implementation steps

  1. Extend the web configuration with MCPAPIKey string and LegacyAPIKeyConfigured bool. Keep the legacy secret outside the web package boundary.
  2. Derive the displayed endpoint from the validated public URL plus /mcp.
  3. Register POST /settings/mcp-key/reveal behind both existing protected and mutating middleware.
  4. Return {"token":"…"} with Cache-Control: no-store, private, Pragma: no-cache, and JSON content type. Return a safe error if the primary key is unavailable.
  5. Render only a masked placeholder in the initial HTML. Render the legacy boolean as Configured / Not configured.
  6. Add dependency-free browser behavior: Fetch with same-origin credentials and CSRF form data; display via textContent; copy with the Clipboard API; clear after 30 seconds, explicit Hide, or pagehide.
  7. Show a short warning that the OS clipboard is not automatically cleared. Do not overwrite the clipboard later because it may contain newer user data.
  8. Update documentation and tests, then run the repository verification suite.

Scope and impact

  • No change to the MCP protocol, provider integrations, sync rules, recurrence behavior, or event data.
  • No change to database schema or migrations.
  • No change to key format or the existing primary-plus-legacy authentication behavior.
  • The new endpoint exposes an existing secret only after explicit user action inside the protected single-user UI.

Automated test plan

  • Settings GET does not contain the primary or legacy key value.
  • Settings displays the correct MCP endpoint and legacy configured state.
  • Reveal without trusted Authentik identity is rejected.
  • Reveal with invalid Origin or CSRF token is rejected.
  • Successful reveal returns the primary key only, never the legacy key.
  • Successful and error reveal responses carry non-cacheable headers and never redirect with secret data.
  • Run node --check internal/web/assets/app.js.
  • Run go test -race -count=1 ./..., go vet ./..., and go build ./cmd/server with build output outside tracked source paths.

Manual QA checklist

  • Open Settings through Authentik and confirm the endpoint and masked state are visible.
  • Inspect page source before Reveal and confirm neither real key is present.
  • Reveal and copy the primary key; verify a client can authenticate to /mcp.
  • Confirm explicit Hide and the 30-second timeout remove the token from the DOM.
  • Reveal again, navigate away/back, and confirm the token is not restored.
  • Confirm the legacy key has status only and is absent from HTML and reveal responses.
  • Confirm an expired or missing Authentik session produces a useful failure state without exposing data.
  • Do not capture the real key in screenshots, recordings, console output, or copied test artifacts.

Risks and mitigations

Rollback plan

Revert the feature commit and redeploy the previous immutable image. No data rollback or environment change is required. Existing API_KEY and API_KEY_LEGACY authentication continues unchanged.

Open questions

None blocking. The next architecture decision is deliberately deferred: if the UI becomes multi-user, replace the master-key reveal with independently revocable per-client tokens.
