Authentik session resilience

Approval required before implementation

Task summary

Make the calendar SPA handle an expired Authentik session predictably instead of turning an API redirect into a cross-origin/CORS error and the generic message “The request could not be completed.”

Observed evidence: production access logs show a refresh POST for Google returning 202 while the Apple refresh POST receives 302 from the Authentik ForwardAuth layer. The calendar data and quarantine state remain intact.

Current behavior and architecture

  • Traefik applies authentik-auth to the calendar UI host; an unauthenticated request is redirected to auth.dzarlax.dev.
  • The SPA calls same-origin /api/ui/* using fetch with credentials and expects JSON.
  • frontend/src/lib/api.ts parses non-2xx JSON errors but does not identify an Authentik redirect or an opaque cross-origin redirect.
  • CalendarPage.tsx refreshes several calendars concurrently with Promise.all, so one redirected request obscures the outcome of the other calendars.
  • Backend calendar refresh itself is eligible and queueable for the affected Apple and Google calendars; this plan does not alter event quarantine, provider tokens, or cached events.

Desired behavior

  • When Authentik redirects an API request, the client detects session loss and navigates the top-level page to /app (which safely starts Authentik login), rather than surfacing a CORS-shaped generic error.
  • Concurrent calendar refreshes report per-calendar outcomes. A successful Google queue is not presented as a total failure because Apple re-authentication is needed.
  • After re-authentication, the calendar reloads and the user can retry repair without losing cached events.
  • Normal API errors (provider, permission, conflict, validation) keep their existing safe messages and do not trigger a login redirect.

Execution waves

  1. Contract freeze — Terra: confirm the browser-visible distinction between ordinary API errors and Authentik redirect/session loss; no credentials or redirect payloads may be logged.
  2. Parallel implementation — Luna/Luna/Terra: implement the two frontend lanes and the optional backend observability lane with disjoint file ownership.
  3. Integration — root coordinator: inspect the actual diff, combine the user-facing messages, and run all checks. Allow at most two focused correction turns per lane before reassessing with Terra.
  4. Production gate: no commit, push, deploy, Traefik change, or Authentik policy change is included until separately authorized after local evidence.

Implementation steps

  1. Add a narrow API response classification for opaque/cross-origin redirects and an explicit session-expired error path. Preserve same-origin JSON error parsing and avoid retrying mutation requests automatically.
  2. Change refresh aggregation from fail-fast Promise.all to an outcome-preserving approach. Display “signed in again” for session loss and identify calendars that were queued versus not queued.
  3. Add tests for JSON API errors, redirect/session-loss classification, mixed refresh success/failure, and the no-automatic-mutation-retry invariant.
  4. If backend changes are warranted, add safe structured logging or a JSON response only at the application boundary; do not bypass ForwardAuth or expose provider tokens, calendar paths, or user credentials.
  5. Run local browser smoke checks at mobile and desktop widths with an expired-session simulation, then update this plan with actual changes and limitations.

Test and QA plan

  • npm test (or the repository’s configured frontend test command) — all existing tests pass plus new API/session and refresh aggregation cases.
  • npm run build — production frontend build succeeds.
  • go test -race -count=1 ./..., go vet ./..., git diff --check — backend and repository checks pass.
  • Browser QA: authenticated bootstrap/events; expired Authentik session during refresh; one calendar returning 202 while another redirects; cached events remain visible; top-level re-authentication returns to the calendar.
  • Production verification, only after explicit deploy approval: inspect Traefik status codes, application health, and one real refresh path without changing credentials or deleting cached data.

Risks and edge cases

  • A redirect may happen after some concurrent refreshes have already been accepted; the UI must not blindly retry those mutations.
  • Top-level navigation can discard unsaved event-form state; session-loss messaging must make that tradeoff explicit.
  • Changing Traefik or Authentik behavior could affect every protected service; this plan defaults to a client-side fix and treats infrastructure changes as out of scope.
  • Browser extensions, service workers, and mobile WebViews may expose redirects differently; tests must include the supported browser path.

Rollback plan

Revert the client/API changes as one release unit. Do not delete quarantine rows, cached events, sync state, OAuth tokens, or Docker volumes. If a production deploy is made later, redeploy the previously verified immutable image digest.

Open questions

  • Should session expiry always navigate to /app, or should the UI first show a confirmation when an edit form is dirty?
  • Do we want a backend JSON 401 contract through a separate API route, or is client-side redirect classification sufficient for this single-user deployment?
  • Should refresh results show calendar names, provider names, or both on mobile?
