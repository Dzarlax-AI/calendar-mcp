Unified sync activity

Approval required before implementation

Task summary

Replace the separate “Sync Rules” and “Runs” navigation items with one sync-management entry and one combined screen. The screen keeps rule controls and shows recent run history directly below them.

Current behavior

  • frontend/src/app/App.tsx exposes distinct /rules and /runs routes and navigation entries.
  • ControlPlanePage renders Rules and Runs as separate sections, both sourced from the already-loaded bootstrap payload.
  • The Calendar sidebar’s Manage menu repeats those two links.

Desired behavior

  • One navigation item, labelled Sync activity, opens /rules.
  • /rules shows rule creation/control first, then a clearly separated “Recent activity” list of runs.
  • Existing /runs deep links redirect to /rules; no run data or existing rule actions disappear.
  • Manage menu and app navigation show only the consolidated entry.

Impact and boundary

No backend/API, migration, provider, auth, or permission changes. This is a frontend route and information-architecture change over existing bootstrap data. The existing /rules/new creation path remains unchanged.

Likely files and steps

  1. frontend/src/app/App.tsx: collapse navigation, render the combined rules section at /rules, and redirect /runs compatibly.
  2. frontend/src/features/control-plane/ControlPlanePage.tsx: compose the existing Rules and Runs panels into the rules screen, with concise section hierarchy and empty states.
  3. frontend/src/features/calendar/CalendarPage.tsx: replace the two Manage links with the one consolidated link.
  4. Update route/menu tests and the focused browser check. No visual baseline refresh unless the approved UI change intentionally changes a captured surface.

QA

  • npm --prefix frontend run typecheck
  • npm --prefix frontend test
  • Focused Playwright: open Calendar → Manage → Sync activity; verify rules and recent runs are on one screen; open /runs and verify redirect.
  • Manual: create a rule from the unified screen, return/cancel correctly, and confirm Settings/Connections remain reachable.

Risks and edge cases

  • Run history can be empty while rules exist; retain its explicit empty state rather than hiding the section.
  • External bookmarks may use /runs; redirect rather than remove the route.
  • The combined page can become visually dense with many rules/runs; keep panels independently scannable and defer filtering/pagination to a separate request.

Model allocation and integration

  • GPT-5.6-Sol — lead/integration: owns the route contract (/rules, compatibility redirect from /runs), composes the unified screen, resolves cross-file conflicts, and runs the final typecheck/build.
  • GPT-5.6-Terra — UI review lane: independently reviews the existing Rules/Runs panel hierarchy and the combined empty/long-list states; returns bounded UX/test recommendations, without modifying routes or API behavior.
  • GPT-5.6-Luna — navigation/test lane: updates or proposes the focused browser checks for the Calendar Manage menu, unified route, and legacy redirect; verifies menu labels do not duplicate.

Sol integrates only the reviewed, scoped outputs. All lanes use the existing synthetic frontend data; no model receives credentials, production data, or deployment access.

Rollback

One frontend revert restores the two navigation entries and the old /runs screen. No backend data or provider state is changed.

Open question

The default label is “Sync activity” to cover both configuration and history. If you prefer “Sync” or “Rules & runs”, change only the label before approval.

Approval gate

Implementation must not start until this plan is explicitly approved. Approval covers only the frontend navigation/combined screen and tests; it does not authorize backend, API, provider, auth, or deployment changes.
