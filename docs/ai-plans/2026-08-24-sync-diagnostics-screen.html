Sync diagnostics screen

Approval required before implementation

Task summary

Add a protected, read-only-first diagnostics area for calendar sync degradation. It should let the operator identify failed calendars, inspect quarantine metadata and bounded raw provider payloads, then optionally request a bounded repair retry without exposing diagnostics to ordinary users or ordinary calendar APIs.

Current behavior

  • The React UI is under frontend/src/ and receives calendar/source status through GET /api/ui/bootstrap.
  • Raw artifacts are encrypted in calendar_sync_raw_artifacts; storage already exposes GetRawEventSyncArtifact.
  • POST /api/ui/sync-artifact exists, accepts identifiers in the JSON body, and is fail-closed against RawArtifactOperators plus UI CSRF/auth middleware. There is no diagnostics screen or quarantine-list endpoint.
  • The trusted identity comes from Authentik's X-authentik-username; direct access around the reverse proxy must remain impossible.

Desired behavior

  • Add an authenticated /diagnostics route visible only to the configured diagnostics operator (prefer an explicit username allowlist first; group-based access is a later option).
  • Show summary counts and a table grouped by calendar: display name, provider, status, active quarantine count, last successful sync, last error, and next repair.
  • Show object details on demand: opaque object ID, ETag, error class, capture time, provider status/content type, truncation flag, and a redacted/escaped raw payload viewer.
  • Keep raw payload retrieval on a dedicated no-store API. Do not put calendar/object identifiers in URLs, ordinary bootstrap JSON, logs, or client analytics.
  • For the first version, make repair an explicit, bounded action that requeues or schedules one object and reports confirmed/failed outcomes. Do not add bulk delete or automatic mutation controls.

Security, data, and UX impact

Trust boundary: Authentik/Traefik must strip any client-supplied identity header and set the authenticated value. The application must remain unreachable directly from the public network.
  • Raw artifacts may contain private event data; access is operator-only, responses are no-store, and payloads remain encrypted at rest.
  • Identifiers stay in POST bodies or server-rendered state, not query strings or links.
  • Mobile layout should prioritize calendar health and a short “why degraded” summary; raw payload is a collapsible secondary view.
  • Repair is not a blind retry: the UI must display the exact target and confirmed enqueue/repair result.

Test and manual QA plan

  • go test ./internal/web ./internal/storage ./internal/runtime ./internal/eventsync
  • npm --prefix frontend run typecheck and npm --prefix frontend test
  • go vet ./... and git diff --check
  • Unauthenticated request redirects through Authentik; non-allowlisted authenticated user receives no data.
  • Allowlisted user sees degraded calendars, opens one object, views escaped payload metadata, and sees truncation/expiry states correctly.
  • Mobile and desktop smoke checks; verify refresh does not expose identifiers in the address bar or browser history.
  • After deployment: verify container health, sanitized logs, authenticated diagnostics route, and unchanged calendar/MCP paths.

Risks and rollback

  • Overexposure: a broad allowlist or bypassed proxy could reveal private events. Mitigation: explicit identity, fail-closed tests, ForwardAuth-only route.
  • Payload rendering: provider content must be treated as untrusted text. Mitigation: escaped preformatted output and strict response limits.
  • Repair amplification: repeated manual retries could worsen provider throttling. Mitigation: idempotent one-object repair scheduling.
  • Rollback: remove the diagnostics navigation/route and API handlers, keep existing encrypted artifacts and quarantine rows, and redeploy the previous immutable image. No destructive data migration is required for the first version.
