1. Current Architecture and Verified Starting Point

  • calendar-mcp currently provides Google Calendar, Microsoft Graph, and Apple CalDAV adapters, MCP on port 8080, and an internal REST API on port 8081.
  • GitHub PR #2, “Add unified calendar event lifecycle,” is merged. After a read-only fetch, origin/main points to merge commit 285c038; the local working tree is four commits behind and must not be fast-forwarded until execution begins.
  • The merged V2 implementation already contains typed events, recurrence identity, mutation scopes, notification safety, Google recurrence writes, and Microsoft expanded recurrence reads. This work will be reused rather than recreated.
  • calendar-sync is a separate Go service with no third-party dependencies or tests. It polls the Calendar MCP REST API every ten minutes, synchronizes M365 to Google, persists JSON mappings, omits attendees, and currently reads only the next 14 days.
  • The current sync treats expanded occurrences as independent events. Its data model has no series master, exception, cancellation, lookback, or lookahead fields.
  • Book is a separate deployed product and consumes Calendar MCP through the internal REST API. Its API compatibility must be preserved.
  • Production deployment definitions live in personal_ai_stack/deploy/calendar-mcp/ and personal_ai_stack/deploy/calendar-sync/. The shared PostgreSQL 17 instance uses per-service users and schemas.

2. Desired Architecture and Boundaries

One artifact

  • One repository and Go module.
  • One multicall binary: calendar.
  • One immutable OCI image and digest.
  • No runtime CDN assets.

Two production processes

  • calendar serve: MCP, REST, UI, OAuth, migrations.
  • calendar worker: jobs, sync execution, reconciliation.
  • Shared PostgreSQL or SQLite storage.
  • Independent health, logs, restart, and network policies.

The UI and MCP use the same backend domain model and connection records but retain different ingress and authorization boundaries. Book remains outside this repository and image.

3. Assumptions Confirmed by Plan Approval

  • Each installation is single-user but may connect multiple Google, Microsoft, and Apple accounts. Every connection has its own encrypted credentials, discovered calendars, verification state, and reconnect/delete lifecycle.
  • The writable sync matrix includes Google, Microsoft, and Apple as both source and target: all nine provider pairings, including same-provider rules across different calendars and accounts.
  • Every rule remains one-way. A true bidirectional rule with conflict resolution is outside this execution; users compose independent one-way rules only where cycle validation allows it.
  • Standalone portable events are supported across the full matrix. Recurrence is synchronized only when the target can represent it without semantic loss; dry run blocks an unsupported rule or event with a structured explanation instead of flattening or approximating it.
  • Rule validation rejects direct and transitive calendar cycles. Mirror events carry private origin metadata and are never allowed to feed back into their originating rule.
  • The production UI hostname is calendar.${DOMAIN}. MCP remains at mcp.${DOMAIN}/calendar; REST remains internal.
  • Authentik ForwardAuth protects every UI route except provider callbacks. Callback routes remain protected by expiring, single-use state and PKCE.
  • PostgreSQL uses the existing convention: database aistack, schema calendar, role calendar_user, and a service-specific password supplied outside source control.
  • SQLite is supported through DATABASE_URL=sqlite:///data/calendar.db, WAL mode, foreign keys, busy timeout, and exactly one worker.
  • Rule defaults are: interval 10 minutes, lookback 0 days, lookahead 14 days, attendees excluded, notifications disabled, and initial state paused.
  • Accepted depth bounds are lookback 0–365 days and lookahead 1–365 days. Values outside these bounds are rejected by the domain layer and HTTP handlers.
  • The existing API key remains valid for MCP and internal REST. UI access does not reuse the API key.
  • The old calendar-sync repository remains intact as a rollback and history reference until a separately approved archival step.

Credential envelope

CALENDAR_ENCRYPTION_KEY is base64-decoded to exactly 32 bytes. Credentials use AES-256-GCM with a random nonce and a versioned envelope. Associated data binds ciphertext to the connection ID and provider. A missing or invalid key fails closed; secrets and raw provider payloads never enter logs or run history.

HTTP surfaces

  • MCP listener: existing /mcp behavior and API-key authentication.
  • REST listener: existing /api/calendars, /api/events, and V2 routes preserved for Book and internal consumers.
  • UI listener: /, /connections, /rules, /runs, /settings, and HTMX fragments.
  • OAuth: /oauth/google/start, /oauth/google/callback, /oauth/microsoft/start, and /oauth/microsoft/callback.
  • Mutating UI handlers require same-origin requests, Authentik ingress, and CSRF tokens. OAuth callbacks atomically consume state.

Sync depth semantics

Every run computes [now - lookback_days, now + lookahead_days] in UTC for provider queries while preserving event timezones in the portable model. Increasing depth adds newly visible events. Decreasing depth does not delete mappings merely because events fall outside the window; deletion requires a provider tombstone, explicit cancellation, or reconciliation evidence.

8. Risks and Edge Cases

  • Recurrence expressiveness mismatch: Google and Apple accept broader iCalendar recurrence constructs than Microsoft Graph. Unsupported conversions must remain visible dry-run blockers, not approximations.
  • Exceptions around DST: mappings require original occurrence time plus series identity; UTC event time alone is insufficient.
  • Ambiguous remote writes: provider timeout may occur after success. Private target metadata and lookup must precede retry.
  • Notification side effects: attendees stay excluded and notification policy stays none. The worker must reject any path that cannot suppress scheduling side effects.
  • Depth shrinkage: absence from the active window is never deletion evidence.
  • SQLite concurrency: only one worker is supported; WAL and busy timeout reduce contention but do not make multi-worker claiming supported.
  • Credential loss: loss of the encryption key requires reconnecting providers. Backup documentation must cover the key separately from the database.
  • Schema rollout: serve migrates before worker starts. A worker with mismatched schema must stay unready rather than partially run.
  • Local branch drift: local main is behind merged origin/main; implementation must branch from fetched origin/main, not the stale local commit.
  • User-owned changes: the dirty calendar-sync README and untracked local tooling files must not be included in implementation diffs.
  • Third-party assets: HTMX and CSS must be served from the image. Runtime CDN use is prohibited.

13. PR #3 Review Remediation Plan

Added 2026-08-20 after automated review. PR #3 remains ready for review as requested. This section is a new approval gate for the broad local remediation pass; commit, push, remote replies, and thread resolution remain separately authorized actions.

13.1 Confirmed merge blockers

  • PostgreSQL rule exclusion: two workers can claim different pending jobs for one rule before either transaction observes the other's uncommitted running state.
  • Lease ownership: long jobs have no heartbeat, stale recovery can reissue live work, and an old worker can finish a newer attempt.
  • Remote-create recovery: Google has provider-side markers, while Microsoft and Apple remain vulnerable when remote create succeeds but the local mapping write does not.
  • Control-plane boundary: local and PostgreSQL examples can publish an unauthenticated UI; ForwardAuth headers are safe only behind a proxy that strips client-supplied identity headers.
  • OAuth redirect validation: empty return paths should normalize to /connections, and network-path/backslash variants must be rejected.
  • Dependency security: upgrade indirect google.golang.org/grpc from 1.79.3 to at least 1.82.1 for GO-2026-6061.
  • Provider correctness: fix Apple recurrence overlap/time parsing/EXDATE timezone behavior, Microsoft combined-view pagination/instance normalization/recurrence payloads, Google marker pagination, and the event hash fields.

13.2 Implementation decisions

  1. Add database-level partial uniqueness for one running job per rule and one mapped target event per rule. Serialize PostgreSQL claim selection by rule and treat uniqueness conflicts as contention, not job failure.
  2. Carry worker ID plus attempt through lease renewal and completion. Heartbeat active jobs, cancel execution when ownership is lost, use a fresh clock value for every claim, and condition FinishRun on the exact live owner/attempt.
  3. Add Microsoft extended-property and Apple iCalendar-property sync markers with exact lookup before create. Keep Google lookup, but follow pagination and reject duplicate markers.
