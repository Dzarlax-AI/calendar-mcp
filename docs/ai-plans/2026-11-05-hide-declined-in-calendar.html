Скрытие отклонённых событий в календаре

Редакция 2 · Реализовано локально · 5 ноября 2026

Цель и результат

Добавить в веб-календарь переключатель «Hide declined events». При включении скрывать только события с достоверно известным ответом пользователя declined. События с неизвестным ответом и всеми прочими ответами остаются видимыми. Переключение сразу обновляет все виды календаря, включая мобильный месяц и список. Пользователь уточнил: настройка хранится на сервере и общая для сервиса, включая все браузеры; по умолчанию выключена, чтобы сохранить действующее поведение.

Текущая реализация и границы достоверности

Ответ /api/ui/events не содержит статус участия, а список участников намеренно исключён из UI JSON. В native cached-events уже есть проверенный контракт: статус выводится только для подтверждённого основного Google-календаря, если ровно один участник помечен self и ответ принадлежит допустимому набору. Общие календари, неподтверждённые основные календари, Apple/Microsoft и неоднозначные или отсутствующие ответы остаются неизвестными. Статус событий и ответ участия — разные поля.

Дополнить браузерную выдачу событий необязательным полем self_response_status по тем же консервативным правилам, без передачи списка участников и идентификаторов. Применить одинаковые проверки к кешированной и прямой выдаче, если для прямой выдачи можно однозначно установить подтверждённый календарь; иначе не отдавать статус. Изменение не влияет на MCP, native API, мост, данные у провайдеров и права.

Изменения и порядок

  1. На чистой базе выделить общую проверку статуса участия из native в безопасную общую функцию и применять её в UI при наличии достоверной привязки календаря. Проверить нормализацию canonical ID и обработку отсутствия записи.
  2. Добавить необязательное поле в клиентскую модель и обработку JSON. Вычислять отфильтрованный список без дополнительного запроса и не менять кеш запроса.
  3. Добавить доступный переключатель в раздел Settings сервиса, доступный на широком и узком экране; сохранять выбор в настройках сервиса через защищённый CSRF и проверкой origin API, с индикацией сохранения и ошибок. Значение загружается из сервера и общее для браузеров.
  4. Проверить все представления, перечитать фактический diff и записать результаты в этот план.

Проверки

  • Синтетические Go-тесты: primary Google с одним self/declined; accepted, tentative и неизвестный ответ; несколько self; общий/неподтверждённый календарь; отсутствие участников в UI-ответе; одинаковое поведение прямого и кешированного чтения.
  • Frontend: normalisation поля, переключение и сохранение на сервере, повторное открытие в другом браузере, ошибка записи, declined/unknown/accepted; календарная сетка, список и мобильный месяц; отсутствие скрытого события во всех режимах.
  • Запланированы go test для затронутых пакетов, npm run typecheck, frontend-тесты и синтетическая визуальная проверка широкого и узкого интерфейса. Реальные события и уведомления не изменяются.

Риски и восстановление

Нельзя определять отказ по чужому ответу или по первому self в неоднозначном событии: в таких случаях поле отсутствует и событие остаётся видимым. Дополнительная проверка идентичности календаря не должна раскрывать участников. При недоступности данных статуса фильтр не скрывает события. Добавляется миграция схемы SQLite/PostgreSQL с настройкой по умолчанию false; для отката приложения необходимо учитывать проверку версии схемы и совместимость с миграцией. Откат только клиентского отображения не изменяет календарные данные.
