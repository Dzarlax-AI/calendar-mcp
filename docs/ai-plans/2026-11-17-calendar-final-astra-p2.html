Границы и исходное состояние

Рабочая ветка codex/google-orphan-occurrence, HEAD 24c8e16. Контроль собирается из текущего рабочего дерева, которое включает незакоммиченные оптимизации SQLite и проверку отзыва доступа. При исполнении сохраняем этот снимок и отдельный diff каждой фазы.

  • Буфер на вызов сохраняет 8 МиБ сырых payload и 8 192 строки. SQLite освобождает соединение до декодирования помещающейся выборки. При переполнении сохраняется потоковое чтение.

  • UI и /api/native/v1/cached-events сохраняют текущий серверный контракт частичной выдачи. В этой ревизии меняется потребление unavailable в браузере. Live-маршрут CalendarApp /api/native/v1/events остаётся отдельным контрактом.

1. Передать в верификацию ревизию конкретного reconnect

Apple и Microsoft сейчас сохраняют новую ревизию через BeginAuthorization, а веб-обработчик затем запускает верификацию по ID подключения. Если между этими шагами успеет второй reconnect, первая попытка считывает его ревизию, и её сбой может закрыть более новую попытку.

Передать снимок, возвращённый BeginAuthorization, через результат reconnect в веб-обработчик. Конструктор провайдера, публикация discovery и закрытие при ошибке работают с этой же ревизией. Путь первого подключения сохраняет отдельный вход по ID. Повторная загрузка текущего снимка для старой попытки исключается. Переход pending, очистка проекции и сброс lease остаются атомарными.

Приёмка. Для Apple и Microsoft управляемый тест блокирует первую попытку между сохранением и входом в верификацию. Более новая попытка публикует свою проекцию, а завершение, отмена или ошибка первой оставляют её в силе. Проверить обе последовательности завершения. Штатное обновление OAuth сохраняет ревизию. Кешированный ответ во время reconnect исключает старые события и сохраняет соседний источник.

2. Применить отзыв к открытым формам браузерного UI

Сетка уже использует новый список событий. Открытая карточка, форма редактирования, выбор области серии и подтверждение удаления хранят собственные копии. Адаптер ответа сейчас преобразует unavailable в failed.

Сохранить unavailable в типе, адаптере и представлении статусов. По свежему успешному ответу закрыть карточку и формы только для указанного в статусе источника. Убрать связанный запрос на изменение серии из локального состояния формы. Следующий пользовательский клик из такой формы не отправляет мутацию. Обработчики завершения ранее отправленной операции учитывают отзыв при обновлении уже закрытой формы. Использовать текущие данные запроса и состояние формы.

Приёмка. Компонентный тест обновляет ответ при открытых карточке, редакторе, выборе области серии и диалоге удаления. Событие и управляемые формы исчезают для отозванного календаря. Другой открытый календарь сохраняется. Смена временного диапазона, placeholder, временное failed и pending сохраняют обычное поведение. Проверить опоздавший успешный ответ мутации и отсутствие повторной отправки. Серверные проверки SQLite/PostgreSQL и кешированный native остаются частью регрессии.

3. Согласовать построение маршрута Microsoft с верификатором

Верификация принимает действующий access token без refresh token. Затем Factory.Build использует конструктор, который подставляет пустой токен, если сохранённый состоит только из access token. Подключение выглядит готовым, хотя чтение не работает.

Использовать существующий строгий конструктор снимка Microsoft на путях верификации, построения рабочего маршрута и его обновления. Действующий access token без refresh token пригоден до истечения срока. Для истёкших credentials без способа обновления сохранить штатный отказ авторизации. Обычный OAuth refresh сохраняет CAS и текущую ревизию. Legacy-конструктор с файловым хранилищем сохраняет свой контракт.

Приёмка. На синтетическом токене проверить весь переход verify → Build → live/worker. Первый Graph-запрос отправляется с верной привязкой без лишнего refresh. Отдельно проверить истёкший токен, обычную ротацию, повреждённый снимок и сохранение соседних маршрутов. Отправленный вызов не повторяется автоматически.

4. Закрыть два сбоя Google bootstrap

Короткий ID проверяется по текущей готовности аккаунтов

После bootstrap второго аккаунта google:<calendar> может разрешиться по устаревшему содержимому реестра. Для platform mode перед выбором аккаунта выполнить один пакетный поиск владельцев короткого ID в БД. Для единственного найденного аккаунта использовать существующий точечный путь регистрации или обновления. При неоднозначности действуют существующие ошибка и требование канонического ID. Проверка выполняется до чтения или мутации у провайдера. Пустой верифицированный аккаунт не считается владельцем произвольного короткого ID.

Приёмка. В двух Store второй аккаунт проходит bootstrap между вызовами. Первый короткий запрос после этого получает неоднозначность даже без предварительного list_calendars. Канонические запросы, однозначный короткий ID и файловый legacy-режим проходят прежними путями. Проверить коллизии, пустой аккаунт, незавершённую верификацию и замену маршрутов. Поиск выполняет ноль вызовов Google.

Непригодная запись не блокирует очередь

Worker выбирает первый старый аккаунт, а проверка размера и типа credentials срабатывает позже и откатывает транзакцию. При выборе возвращать ID и результат существующего предиката размера и типа. Для непригодной записи атомарно зафиксировать одноразовый закрытый результат с безопасной диагностикой и очисткой старой проекции. Условие обновления повторно проверяет готовность к bootstrap и непригодность. Выбор и диагностика передают только метаданные. Последующие циклы обрабатывают следующие аккаунты.

Приёмка. Синтетический миграционный набор содержит первый аккаунт с превышением лимита или неверным типом и второй с пригодной записью. Первый завершается закрытым состоянием, второй обрабатывается следующим циклом. Повторный цикл не пытается заново читать непригодную запись. Параллельный явный reconnect побеждает устаревшую попытку. Лимит одного аккаунта на цикл и текущая смена ревизий сохраняются.

5. Восстановить диапазон для целочисленных дат SQLite

В полном кешированном чтении bound для end_at сейчас передаётся как текстовая дата. SQLite сравнивает её с целочисленным timestamp по правилам типов и исключает timed-строку. Драйвер допускает unix, unix_milli, unix_micro и unix_nano через существующий DSN.

Получить единицу измерения из DSN при открытии Store. При настроенном числовом формате сравнивать INTEGER-скаляры с целочисленными границами в той же единице. Для полуоткрытого пересечения по сохранённой точности верхняя граница округляется вверх до тика, нижняя вниз. Проверить отрицательные timestamp и переполнение. В том же запросе сохранить отдельную индексную ветвь для прежних текстовых строк. Без числовой настройки сохранить нынешнюю форму текстового запроса. Сортировка ключей, дочитывание payload по rowid, получение SQL-ID источника, фильтр мастеров и границы буфера сохраняются.

Приёмка. Прогнать fixture, открытый с реальными DSN-опциями драйвера для всех четырёх единиц, с включённым и выключенным _inttotime. Проверить точное касание границы при сохранённой точности, доли секунды, календарный день, offset из старой записи, смешанные TEXT и INTEGER-строки в одной БД и одинаковые ответы UI/native. Измерить план на длинной истории. Стандартный путь и числовая ветвь должны сохранять индексную верхнюю границу и единый SQL-вызов за диапазоном.

Единица уже записанных INTEGER определяется текущим DSN. База с несколькими историческими единицами в INTEGER неразличима по одному значению. Поддержка смены единицы с преобразованием старых данных потребует отдельного решения. Форматы payload и PostgreSQL остаются прежними.

Исполнение, откат и согласование

Исполнение начинается после согласования ревизии 1. Координатор фиксирует контроль, принимает reconnect и UI, затем последовательно принимает Microsoft, Google и SQLite. Для реализации подходят ограниченные задания Terra high. Reconnect владеет connections, веб-обработчиками и границей снимка. UI владеет frontend/src. Microsoft и Google получают providers/factory.go последовательно. Последняя фаза владеет SQL диапазона и параметрами Store. Каждый этап возвращает diff, результаты целевых тестов и ограничения. Astra 6.2 проверяет итоговый diff и адресует гонки, совместимость и границы производительности.

При локальном откате снять точный diff неуспешного этапа поверх сохранённого рабочего снимка, сохранив независимые изменения. Состояние авторизации и данные синтетических проверок изолированы. Действующее ограничение схемы 008 сохраняется для будущего деплоя.

Согласование охватывает локальную реализацию пяти этапов и приёмку. Коммит, push, PR, деплой и операции с реальными аккаунтами отдельно согласуются. Результаты выполнения приведены ниже.

Итоги реализации и приёмки

  • Apple и Microsoft передают в верификацию снимок конкретного reconnect. Запоздавшее завершение, отмена и ошибка первой попытки сохраняют актуальную ревизию и проекцию второй.
  • Браузер закрывает карточку, редактор, выбор области серии и подтверждение удаления для отозванного источника. Старые и опоздавшие ответы диапазонов не возвращают его события. Мутация сверяет ревизию перед отправкой и после завершения. В Chromium проверено сохранение карточки соседнего календаря.
  • Microsoft использует строгий конструктор снимка при верификации, построении и обновлении маршрута. Тест прошёл от верификации до чтения Graph и delta-запроса worker с действующим access token. Повреждённая запись изолирована от остальных маршрутов.
  • Короткий Google ID разрешается по одному запросу метаданных и по ревизии найденного владельца. Неоднозначный результат и изменение ревизии прекращают разрешение. Непригодная запись bootstrap закрывается один раз с очисткой проекции. Следующий цикл выбирает следующий аккаунт.
  • Полный SQLite-диапазон с числовым DSN читает целочисленные, старые текстовые и all-day записи одним запросом. Проверены четыре единицы с обоими значениями _inttotime, отрицательные даты, касание границ, временная зона старых записей и индексы. Даты и границы вне диапазона выбранной единицы возвращают ошибку. Единицу существующих числовых записей задаёт DSN.

Буфер на вызов — 8 МиБ и 8 192 строки. Пул SQLite — одно соединение. Схема и количество кешей сохранены.
