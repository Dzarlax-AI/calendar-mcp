P1 · Уведомить UI/native об отзыве до начала чтения

Начальный снимок Store включает только подключённые читаемые источники. Финальная сверка выставляет unavailable лишь для источников, которые исчезли из этого снимка. Источник, отозванный раньше, выпадает из обоих результатов. HTTP-обработчик подставляет pending, и браузер сохраняет открытую форму. Native также подставляет pending, если источник прошёл предварительный отбор и стал недоступен до захвата снимка.

Пакетное чтение Store возвращает один статус для каждого уникального запрошенного ID. Окончание проверки после декодирования определяет результат по уже существующим двум снимкам. При изменении или исчезновении полномочий удаляем события по SQL-ID только затронутого источника. При ошибке финального чтения исключаем выдачу всего ответа.

Состояние источникаКешированный ответ
Доступ подтверждён в обоих снимкахСобытия и статус синхронизации этого источника.
Доступ подтверждён, состояние синхронизации ещё отсутствуетpending, stale=true, complete=false.
Источник недоступен при захвате либо полномочия расходятся при сверкеunavailable, stale=true, complete=false. В ответе остаются данные остальных источников.

UI использует результат Store напрямую и закрывает карточку, редактор, выбор области серии и подтверждение удаления для unavailable. Для cached native известный явно запрошенный календарь, сохранившийся в каталоге после отзыва, участвует в сборке частичного ответа со статусом unavailable. Для него наружу выходят только запрошенный ID и статус. Неизвестный или уже удалённый до предварительного отбора ID сохраняет текущий 403. Если известный ID исчез в ходе чтения, действует статус Store. При запросе без явных ID список по-прежнему формируется из доступных календарей. Эндпоинт native live и проверка токена сохраняют текущий контракт.

Приёмка. На изолированных фикстурах проверить два источника и отзыв до захвата, в ходе чтения и после декодирования. UI и cached native возвращают unavailable для затронутого источника и прежние данные соседнего. Доступный незагруженный источник получает pending. Отдельно проверить mixed-запрос cached native с известным недоступным ID, неизвестный ID, отмену и ошибку финальной сверки. Chromium использует безопасные тестовые ответы API для проверки всех четырёх форм, сохранения соседней формы и отсутствия новых мутаций.

P2 · Четыре исправления после приёмки P1

1. Сохранить сведения об отзыве при переходе между страницами

Перенести существующие признаки отзыва и порядок запросов из CalendarPage в состояние авторизованного приложения, живущее вместе с QueryClient. Использовать общий источник для отображения и для проверки отложенной мутации перед отправкой и завершением. Сбрасывать эти сведения при смене сессии вместе с данными запросов. Дополнительное хранилище событий не требуется.

Приёмка. В рамках одной сессии свежий unavailable блокирует прежние ответы других диапазонов и после возврата на страницу. Задержанный ответ и отложенная мутация со старой ревизией игнорируются. Новый подтверждённый ready разрешает свежие данные этого источника. Соседние источники, placeholder и временные статусы сохраняют обычное поведение.

2. Передать точный снимок Google reconnect до верификации

Применить к Google тот же принцип, который используется для Apple и Microsoft. После сохранения credentials callback передаёт снимок своей попытки прямо в VerifyGoogleSnapshot. Создание первой авторизации выполняется отдельно. Публикация discovery и закрытие при сбое сохраняют привязку к переданному снимку. Сохраняется требование собственного refresh token при Google reconnect.

Приёмка. Синтетические тесты на границе callback и сервиса подтверждают ровно одну смену ревизии на reconnect. Оба порядка завершения, отмена и ошибка прошлой попытки сохраняют более новую опубликованную проекцию и соседний источник. Проверить обычный OAuth refresh и существующий отказ при отсутствии refresh token.

3. Сохранить однозначные короткие Google ID на обновлённой базе

При EVENT_READ_MODEL_ENABLED=false один запрос метаданных учитывает также подключённую запись со схемы до 008, у которой ревизия ещё пуста. Для неё требуется точный сохранённый ID доступного календаря или сохранённая отметка primary. Объединить таких кандидатов с верифицированными владельцами и принять только одного владельца. Различать отсутствие владельца и допустимый пустой legacy-снимок, сверять выбранный аккаунт и привязку маршрута при refresh. Изменение привязки завершает запрос до обращения к провайдеру.

Приёмка. Фикстура, обновлённая с версии 007, при выключенной модели чтения сохраняет однозначный короткий ID в live/compat. Короткий ID с двумя владельцами, неизвестный ID и пустое discovery закрыты. Проверить коллизию legacy с верифицированным аккаунтом и смену ревизии в ходе разрешения. Для включённой модели сохраняется требование верифицированного владельца. Сохранённые данные legacy разрешают только live-маршрут. Проверки cached MCP по ревизии, receipt и окну остаются обязательными.

4. Провести числовой SQLite DSN через штатные точки входа

Повторное ревью подтвердило ошибку Scan на created_at и discovered_at для всех четырёх единиц при _inttotime=false. Использовать уже существующий принцип декодирования временных метаданных по единице DSN. Сначала охватить чтение подключений и календарей, затем пройти по прямым зависимостям bootstrap UI и worker. В bootstrap входят правила и история запусков, а worker читает времена состояния и lease. Расширять адаптацию по фактическим сбоям этих штатных путей.

В числовой ветви сохранять точность знаковых значений и исключить эвристику драйвера при ранних миллисекундах. Для старых текстовых данных сохранять локальную зону из DSN и явные смещения. Проверка смешанной базы охватывает TEXT и INTEGER одной выбранной единицы. Схема, устройство индексов и обычный текстовый путь сохраняются.

Приёмка. Фикстура создаётся с числовым DSN с самого начала. Проверить unix, unix_milli, unix_micro, unix_nano с обоими значениями _inttotime. На ней проходят Factory.Build, /api/ui/bootstrap с сохранёнными правилами и запусками, полный диапазон UI, /api/native/v1/cached-events и один штатный цикл чтения worker с тестовым провайдером. В выдаче UI/native совпадают события, пересечения и статусы. EXPLAIN QUERY PLAN подтверждает ограниченные индексные ветви на длинной истории.

Порядок исполнения, риски и откат

Координатор фиксирует исходное состояние и принимает фазы последовательно. Предлагаемый исполнитель — Terra high для P1 и состояния браузера, затем Terra high для каждого ограниченного блока Go. Изменения состояния браузера начинаются после стабилизации контракта P1. Блок Google reconnect закрывается до правок маршрутизации. SQLite выполняется последним, поскольку переиспользует сканирование статусов, которое затрагивает P1. Astra 6.2 проверяет совокупный diff и результаты приёмки.

Для каждой фазы исполнитель получает этот план, актуальный снимок и перечисленные файлы. Возвращает фактический diff, результаты проверок и выявленные ограничения. Узкие вызовы общего кода можно скорректировать в фазе, которой они принадлежат. Координатор проверяет пересечения и запускает итоговую приёмку на собранном дереве.

  • Гарантия сервера опирается на финальный снимок БД конкретного запроса. Состояние браузера учитывает полученные от сервера статусы. Требование видеть смену полномочий целиком между двумя успешными ответами без промежуточного unavailable потребует отдельного решения о контракте.
  • Изменение cached native касается статуса известного запрошенного ID. Проверки токена, неизвестных ID и отсутствия лишних метаданных входят в P1. Числовая ветвь SQLite интерпретирует INTEGER по единице текущего DSN. Смена единицы для существующих INTEGER потребует отдельного преобразования данных.
  • Для локального отката снять патч нужной фазы относительно зафиксированного снимка. Сначала снять зависящие изменения, в частности браузерное состояние перед откатом контракта P1. Сохранить исходные локальные правки. При повторной приёмке использовать новые копии синтетических фикстур.

Баннер синхронизации, создание события и cached native

Баннер ограничен текущим выбором и учитывает те же отзывы, что и сетка. Проверка при нажатии отсекает устаревшие действия восстановления. Форма создания сохраняет черновик при отзыве выбранного календаря и требует явного выбора другой цели. Отложенное создание проверяет ревизию перед отправкой и при завершении.

Cached native определяет основной календарь Google по последней пакетной проверке прав. Признак берётся из того же снимка, что ревизия и разрешение источника. Тест меняет признак между чтением каталога и чтением событий и проверяет, что событие остаётся в выдаче без self_response_status.

Повторное ревью Astra 6.2 подтвердило исправления, включая смену выбора во время загрузки и содержание баннера. Прошли 837 проверок Go с -race, 168 проверок PostgreSQL в отдельном прогоне, 71 тест Vitest, TypeScript и восемь сценариев Chromium. Native проверялся на уровне серверного API.

Медианы парных изменений составили −1,0%, 0,0% и +0,3%. У тяжёлого UI разброс пар составил от −15,3% до +34,4%. Состав и порядок выдачи совпали. Размер пула и буфера сохранён, новых кешей нет.
