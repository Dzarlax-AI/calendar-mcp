Calendar Event Read Model

Replace repeated provider reads on every calendar navigation with a durable Postgres projection maintained by incremental background synchronization.

Task summary

The providers remain authoritative. The UI reads locally and shows source freshness; writes still go to the provider first and then update/reconcile the projection.

Current architecture

  • Every /api/ui/events request fans out to selected providers and drains their pagination.
  • React Query retains range results in memory for 15 seconds, but the backend has no event cache.
  • Calendar metadata is stored in Postgres; events are not. Apple Family Sharing may require hundreds of GETs through the existing fallback.
  • An existing worker processes rule jobs, but production compose keeps it behind the optional worker profile.

Recommended decisions

Postgres, not RedisDurable events, cursors, leases, source freshness, and replay safety live together.
UI-only cutover firstMCP and REST continue direct reads until the browser path is proven.
Polling before webhooksIncremental polling is the correctness mechanism; webhooks later reduce latency.

Default window: 365 days back / 730 days forward. Freshness: 60 seconds for Google/Microsoft and 5 minutes for Apple. All values are configurable.

Data and migration impact

  • Schema version 2 adds cached_events, calendar_sync_state, and calendar_sync_objects.
  • Event payloads remain normalized EventV2 JSON with indexed timed/all-day range columns.
  • Opaque provider cursors never enter logs or frontend responses.
  • Full sync uses generations: old rows are swept only after the replacement sync finishes successfully.
  • The migration is additive. Rollback disables reads/worker and leaves tables intact; no destructive downgrade.

Test and QA plan

  • Red/green unit tests for migrations, range queries, cursors, pagination, deletions, lease recovery, and provider reset semantics.
  • Provider httptest suites for Google 410, Graph delta links, and Apple sync-token/cursorless replacement fallback.
  • Frontend tests, typecheck, and production build.
  • Full go test -race -count=1 ./..., go vet ./..., and server build.
  • Production dark launch: initial sync counts and recurrence samples compared with direct provider reads before cutover.
  • Acceptance: warm UI p95 below 300 ms and zero provider list calls during ordinary navigation.

Risks and edge cases

  • Recurring masters, exceptions, moved instances, cancellations, and all-day boundaries must preserve provider IDs and time zones.
  • A crash during pagination must replay safely without advancing the cursor or sweeping good rows.
  • Apple Family collections may never support reliable REPORT responses; the safe cursorless replacement fallback remains a first-class strategy.
  • Starting the existing worker can also execute enabled rule jobs. Production preflight must confirm rules are paused or intended.
  • Provider writes can succeed while the local projection update fails. Return the confirmed provider result and reconcile; never retry the mutation blindly.

Rollback

  1. Set EVENT_READ_MODEL_ENABLED=false and restart only calendar-serve.
  2. Stop calendar-worker if provider load is abnormal.
  3. Keep additive schema and cached rows for diagnosis; do not drop tables.
  4. Redeploy the prior immutable image only with explicit approval.

Open questions

No blocking questions. The proposed retention and intervals are defaults and remain configurable. Webhooks, MCP/REST cutover, Redis, offline browser storage, and full-text search are explicitly outside this implementation.
