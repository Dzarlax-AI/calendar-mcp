Все чтения Calendar MCP через Gateway из локальной базы

Один PR в calendar-mcp и одно переключение для клиентов. Запрос на чтение получает данные и состояние покрытия из базы. Обнаружение календарей, синхронизация событий и проверка прав выполняются сервером в фоне.

Цель, исходное состояние и граница PR

Один PR в calendar-mcp и одно переключение для клиентов. Все шесть календарных чтений через Gateway используют только опубликованные локальные данные. Чтение при промахе кэша, просроченных правах, ошибке БД или неполном покрытии отвечает сразу и явно. Оно не вызывает API провайдера, не обновляет токен, не запускает discovery, не добавляет джобу и не ждёт worker.

База плана — origin/main 391c647d, схема 29. Основной современный /mcp уже выдаёт кэшированные страницы get_events. Пять остальных чтений используют Registry или Application. Нативный API уже получает список из calendars. Рабочий get_events после обновления Apple подтвердил 7/7. В повторном медленном list_calendars запрос к Calendar MCP занял 6,09 с из 6,63 с.

Read-only сверка рабочего реестра Gateway 18 ноября, ревизия 245, обнаружила одну включённую Calendar-идентичность calendar с путём /mcp. Шесть чтений отмечены read, шесть записей — write. Для календарного сервера включён batch, политика classified. Снимок охватывает записи с календарным идентификатором или известным календарным адресом. Перед включением проверить полный реестр и обнаруживаемые маршруты, включая произвольные псевдонимы, доступные ключам. Зафиксировать эффективные схемы, ограничения размера, правила ACL и batch по каждому инструменту. Маршрут с иной схемой нельзя просто перенаправить. Если такой маршрут обнаружится, он блокирует активацию до совместимого решения или отдельно согласованного снятия публикации.

Сохраняются существующие имена, входные схемы, канонические ID и ACL. Все проверки Gateway продолжают применяться к текущим запросам. Прямые /mcp/modern, /mcp/compat, REST, нативный API, UI и правила копирования сохраняют свои действующие интерфейсы. Записи выполняются у провайдера. Менять исходный код Gateway в этом PR не требуется при подтверждении текущего контракта маршрута.

Отсутствующая граница берётся из целевого окна кэша, описание инструмента отражает фактическую область. Порядок детерминирован, покрытие выдаётся в прежнем формате страниц. Это изменение по отношению к провайдерскому поиску, входит в согласование редакции.

Полный проход и курсоры. Курсор включает инструмент, нормализованные параметры, проверенную серверную учётную запись, состав выборки, версии прав и версии опубликованных данных каждого источника. Версия меняется при изменении результата чтения, покрытия или видимости. Пустой sync и продление тех же прав версиям не мешают. Каждая страница читает данные и версии в одном снимке и перепроверяет полномочия и версии перед выдачей. При изменении состава, прав или опубликованных данных старый курсор получает cursor_unavailable с указанием начать с первой страницы. Не возвращать complete=true для обхода, в котором перемещение события через границу сортировки могло привести к пропуску или дублю.

Идентичность. Calendar MCP видит проверенный upstream-ключ, общий для пользователей Gateway, и не получает проверенный ID конечного пользователя. Персональную привязку к конкретному пользователю за общим ключом этот контракт не обещает. Каждое продолжение проходит существующую проверку ACL Gateway. В MCP привязка идёт к upstream-ключу, конфигурации и разрешённой области. Клиентские заголовки с якобы личностью игнорируются. Различные клиентские ключи Gateway и запрещённые инструменты проверяются в синтетике без расширения ACL.

Доказательства прав и фоновое обновление

Календарь в списке доказывает обнаружение, а доступ к событиям и приватным полям подтверждается отдельно. Для каждого источника сохранять срок полномочий, класс видимости и квитанцию, связанную с ревизией подключения и поколением прав. Для строк событий хранить происхождение и класс доступа, под которым они получены. При понижении прав или переподключении старая богатая проекция перестаёт быть доступной в той же транзакции. Открывать поля заново только после публикации данных под новым доказательством.

Перед поиском, индексированием доступного текста, подсчётом, выбором страницы и выдачей отфильтровать невидимые строки и поля. Защищённые значения не влияют на факт совпадения, порядок и числа. Источники с истёкшим правом не раскрывают идентификаторы или состояние. Проверка прав на календарь не продлевает возраст доказанности приватности конкретного события. Для полей, видимость которых может меняться, стартовый максимум — 15 минут от последней завершённой синхронизации, покрывающей событие под текущим правом, либо локального подтверждённого изменения. После превышения границы применяется безопасная редукция полей или состояние недоступности. Возможность обещать полноту при такой редукции зависит от запроса, например поиск по закрытому полю не считается полным.

Выделить отдельный ограниченный цикл фоновой проверки в worker. Стартовая цель — каждые 5 минут на подключение и базовый срок доказательства 15 минут. Собственный ограниченный набор исполнителей, аренда по подключению, таймауты, распределение попыток во времени и ограниченный backoff сохраняют обработку здоровых аккаунтов при недоступном провайдере и непрерывной очереди правил. Новая проверка сохраняет право только после полного успешного прохода. Частичный ответ не продлевает доказательство и не удаляет пропущенные источники. Подтверждённый отказ применяется сразу. Для обычного продления существующей роли нужен отдельный путь публикации под текущей ревизией. Процедура переавторизации с очисткой кэша применяется только при изменении основания доступа. Действующие интервалы получения событий сохраняются, а 5/15 и возраст видимости измеряются отдельно.

Уточнение согласования 18 ноября. Проверка, начатая до истечения доказательства, может сохранить доступ на срок до 60 секунд после его истечения и только пока действует её аренда. Возврат ошибки, достоверный отказ или истечение аренды заканчивает отсрочку. Проверка, начатая после истечения доказательства, отсрочки не даёт. Абсолютная граница в 15 минут для видимости полей события сохраняется.

Проекция событий и чтение после записи

Мастера, экземпляры и удаление. Переиспользовать calendars, cached_events и calendar_sync_state и добавить недостающие подтверждённые данные в одной добавочной миграции SQLite и PostgreSQL. Точный состав определить матрицей полей по провайдерам. Google сейчас синхронизирует развёрнутые события, Apple при синхронизации не запрашивает show_deleted, а Graph сводит перенос за пределы окна и удаление к одному сигналу исключения из проекции. Фоновый сборщик отдельно материализует мастера, исключения и исходные идентификаторы экземпляров. Хранит происхождение и тип перехода. Подтверждённую отмену или удаление отличать от переноса из окна, обрезки истории, исчезновения из неполного ответа и потери прав. Последние состояния не выдавать как отмену. Tombstone хранит только разрешённые данные, необходимые для ID, времени или фильтров, до выхода из соответствующего окна хранения. Частные артефакты синхронизации остаются вне MCP.

Публиковать согласованный снимок нужного диапазона, версии доступа и содержимого. Замена диапазона учитывает мастеров, исключения и удаления до объявления полноты. Перенос через край окна, возврат в окно и смену серии тестировать в обоих направлениях. В пределах активного окна нужны доказанные рабочие результаты всех шести инструментов для поддерживаемых провайдеров. Постоянная выдача partial или cache_miss вместо деталей и повторений блокирует активацию. Реальные ограничения за пределами окна и у неполученных полей описываются явно.

Подтверждённый результат записи. Сейчас MCP регистрируется с appService, в котором нет активной проекции для MCP-записей. Текущая защита при завершении операции сбрасывает поколение и переводит календарь в pending. Подключить согласованный слой проекции для MCP и переиспользовать существующее устойчивое резервирование операции, защиту копирования и блокировки. До отправки сохранить operation_id, область возможного изменения и последовательность записи. Если сохранить отметку невозможно, запрос завершается до провайдера. Связывать операцию с календарём и событием или серией, а при перемещении — с обоими календарями. При неизвестном ID создаваемого события защищать затронутую область календаря.

После однозначного ответа провайдера одной транзакцией сохранить подтверждённый результат, закрыть только отметку этой операции, отсечь уже начатую синхронизацию предыдущего поколения и изменить нужные опубликованные версии. Сохранить защиту для правил копирования и не выдавать непроверенный диапазон как полный. Подтверждённую точечную запись можно читать сразу из локального результата под действующим правом. Если охват серии или переноса пока неполон, показать ожидание для непроверенной части. Поздний sync, запоздалый ответ записи и результат предыдущего подключения не могут восстановить старое значение. Порядок блокировок и транзакционную границу согласовать со слоями write_dispatch и event_authority.

Потерянное подтверждение и перезапуск. Сохранять известный результат провайдера и состояние сверки независимо от готовности проекции. Для операции с неизвестным исходом worker использует устойчивый идентификатор операции и подтверждаемые механизмы каждого провайдера. Срок сверки составляет пять минут от фиксации отправки. Если подтверждение не получено, worker атомарно фиксирует неизвестный исход, освобождает резерв и сбрасывает поколение синхронизации затронутых календарей. До нового снимка чтение событий недоступно. После публикации чтение отражает новый снимок при действующих правах. Штатный путь не повторяет запись или уведомление при неоднозначном исходе. Доказанный отказ снимает отметку без изменения события. Если провайдер подтвердил запись, а локальная проекция ещё не готова, вернуть предупреждение в существующих OperationResult.warnings или в проверенном MCP _meta для create_event и import_event с прежним телом EventV2. Подтверждение доставки предупреждения через существующий Gateway входит в синтетику. При неподтверждённом исходе сохраняется прежняя ошибка без рекомендации повтора.

Порядок работ в одном PR

  1. Зафиксировать доказательства и совместимость. Координатор составляет матрицу полей, разрешений, идентичности, удалений и покрытия для шести чтений по Google, Apple и Microsoft. Сверяет публичные схемы, текущие aliases, ACL, batch-классификацию и поддержку _meta в Gateway. Сначала проверяются Family Sharing, приватность, явные отмены и восстановление неподтверждённого создания. Существенное изменение внешнего контракта сверх редакции 2 вернуть на согласование.
  2. Хранилище и фоновые процессы. Один исполнитель владеет схемой, общей проверкой прав и версиями публикации в internal/storage/. Другой после заморозки интерфейсов берёт internal/{connections,providers,eventsync,runtime}/ для независимого фонового расписания, сбора доказательств и материализации повторений. Старые записи прогреваются под новой проверкой прав. Они не получают полномочия по умолчанию.
  3. Локальные чтения. Исполнитель берёт отдельный новый файл запросов в internal/storage/ и internal/{cachedpages,mcpserver}/, общий слой прав меняет владелец предыдущего шага. Собрать единый строгий каталог для всех шести имён. Подключить версии содержимого к пагинации и проверить вывод Gateway. Сохранить существующие границы размера и дать явный результат при превышении.
  4. Записи, восстановление, интеграция. Владелец internal/application/read_model.go, MCP-привязки и существующей защиты отправки согласует транзакции со владельцем хранения. Встроить подтверждённый результат, ожидание, обработку перезапуска и предупреждения. Координатор принимает объединённый diff и тесты. Для существенных переходов прав и записи требуется отдельное ревью diff при наличии разрешения на делегирование.

Фактический статус локальной реализации

Ветка codex/gateway-cache-only-reads создана от подтверждённого на GitHub origin/main 391c647d в отдельном checkout. Оба исходных HTML сохранены. Основной checkout не использовался для правок.

Локальный режим подготовки GATEWAY_CACHED_READS_PREPARE по умолчанию отключён. Все шесть локальных читателей подключены к /mcp одним флагом GATEWAY_CACHED_READS_ONLY, выключенным по умолчанию. Прямые MCP-каталоги сохраняют исходные схемы и обработчики. Фоновый worker использует состояние обычной синхронизации и сохраняет дополнительную атомарную проекцию событий с мастерами, экземплярами и явными отменами из доступных V2-представлений. Проверки и критерии активации

  • Ноль provider I/O. Синтетический Gateway вызывает шесть инструментов при доступном, медленном и недоступном провайдере. Для каждого проверяются горячий и холодный кэш, ошибка БД, истёкшие права, пустой и неполный результат. Счётчики конструктора провайдера, OAuth, discovery, HTTP и добавления фоновой работы должны показать ноль на пути чтения.
  • Права и публикация. Три провайдера, downgrade с ранее прогретыми приватными строками, отзыв, отключение, переподключение, частичная проверка, истечение прав и отдельное истечение видимости при живом discovery и остановленном event sync. Поиск по скрытому тексту, количество, статус и пагинация не выдают закрытые данные. Поддержать 5/15 в сценарии с заблокированным провайдером, непрерывной очередью правил и здоровым подключением. Перезапуск и конкурирующие workers не публикуют просроченные результаты.
  • Контракты и страницы. Снимки шести схем, публичные поля, стабильное чтение, отрицательные случаи, точность Apple и DST, реальные мастера, исключения и отмены в синтетике каждого провайдера. Перенос через границу страницы при неизменных правах делает курсор недействительным. Проверить также неизменный цикл sync, смену состава, истечение, обновление прав и ACL разных Gateway-ключей. Размер и планы запросов проверить на обоих диалектах.
  • Чтение после записи. После создания, изменения, удаления и переноса проверить подтверждённое состояние или явное ожидание. Проверить запоздалый sync, разные порядки ответов, crash до отправки и после ответа, потерянное подтверждение при неизвестном ID и ошибку публикации кэша. Для каждого случая общая проекция и правила копирования остаются согласованными, повторного вызова записи и уведомления нет. Использовать только синтетических провайдеров с отключёнными уведомлениями.
  • Совместимость и производительность. Проверить SQLite и PostgreSQL после миграции с версии 29, go test -race -count=1 ./..., go vet ./..., релевантные -tags=integration и сборку. Расширить существующую фикстуру scripts/verify_calendar_coverage_gateway.{go,py} либо добавить отдельный синтетический сценарий. Снять планы запросов поиска и экземпляров. Сравнить одиночные вызовы и полный дневной обход через тот же Gateway с одинаковыми аргументами. Главные критерии — отсутствие обращений из чтения и корректный ответ при задержке провайдера.

Результаты локальной приёмки зафиксированы в фактическом статусе. Одно переключение и восстановление

Сначала подготовить совместимую схему и прогреть проекции закрытым режимом подготовки. Клиенты продолжают пользоваться прежним маршрутом. Использовать отдельное имя режима для подготовки и один переключатель для строгого каталога. Одна активация переводит все шесть чтений существующего маршрута calendar на локальное хранилище. Обязательные условия — рабочие снимки по всем шести инструментам, свежие права, подтверждённое отсутствие живых календарных чтений в опубликованных маршрутах и сохранение эффективных ACL. При некорректной обязательной конфигурации строгий каталог не стартует.

Перед миграцией остановить старых писателей, проверить процедуру на копии предыдущей версии и сохранить согласованную резервную копию. После перехода проблемы хранилища и фоновой актуальности приводят к объяснимому отказу или неполному ответу в разрешённой области. При восстановлении использовать исправление вперёд либо совместимую версию со строгим чтением. Подмена на образ, который не понимает новую схему, возврат к живым чтениям или восстановление базы требуют отдельного решения. Наблюдать возраст прав, очередь и результат синхронизации, причины неполноты и тайминги без вывода идентификаторов и содержимого.
