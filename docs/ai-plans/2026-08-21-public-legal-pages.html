Public homepage, Privacy Policy, and Terms of Service

Implementation plan · 2026-08-21 · calendar-mcp

Task summary

Add repository-maintained Markdown documents for the product homepage, Privacy Policy, and Terms of Service, then expose the same content on the verified application domain for Google OAuth verification.

Proposed production URLs: https://calendar.dzarlax.dev/ for the public product landing page, plus /privacy and /terms. The authenticated control plane moves to /app. GitHub renders the policy source documents for repository visitors, but Google OAuth configuration will use the owned-domain URLs.

Current behavior

  • The Calendar Platform dashboard and all UI pages are protected by application authentication and production Authentik ForwardAuth.
  • Only Google and Microsoft OAuth callback paths bypass ForwardAuth.
  • The repository does not currently contain public product, privacy, or terms documents.
  • The production proxy has no anonymous router for legal or product-information pages.

Desired behavior

  • Anyone can open the public landing page, Privacy Policy, and Terms without signing in.
  • The public homepage identifies Calendar Platform, explains its calendar connection and synchronization purpose, and links prominently to Privacy and Terms.
  • The homepage includes a clear sign-in/open-control-plane action that leads to the Authentik-protected /app route.
  • The Privacy Policy explains the calendar data and OAuth credentials accessed, how they are used and stored, when event data is sent to a user-selected target provider, retention/deletion controls, revocation, security measures, and contact options.
  • The Terms explain service scope, account authorization, calendar mutation risks, user responsibilities, open-source/self-hosted use, availability, warranty limitations, and termination.
  • The authenticated application remains protected; no operational state, connection metadata, secrets, or actions become public.

Assumptions and decisions

  • English is the publication language for OAuth review and repository-facing documentation.
  • The Privacy and Terms Markdown files are the canonical policy text and are embedded into the Go binary at build time. The small product landing page is a normal local HTML template. No runtime GitHub request or CDN is introduced.
  • A bundled Go Markdown renderer may be added; generated HTML is rendered inside a local template with unsafe raw HTML disabled.
  • The hosted instance remains a single-user service, while the wording also distinguishes independent self-hosted installations.
  • The policy describes the broad Google Calendar access actually requested today. Scope minimization is a separate security change and will not be implied as already complete.
  • The effective date will be the publication date.
  • Google Search Console/domain ownership verification and Google Console field entry remain operator actions after deployment.

Implementation steps

  1. Bring the local branch to the current origin/main without overwriting existing untracked planning artifacts.
  2. Draft factual Privacy and Terms Markdown based on implemented provider, storage, sync, and deletion behavior; avoid promises not enforced by code.
  3. Add a concise public landing page describing Google, Microsoft, and Apple calendar connections, one-way synchronization, MCP access, and the single-user/self-hosted model.
  4. Embed the Markdown and render it through the public template. Disable embedded/raw HTML and keep all assets local.
  5. Register exact public routes for GET /, GET /privacy, and GET /terms. Move the protected dashboard to GET /app and update internal dashboard links and post-action return locations.
  6. Add visible cross-links between all public pages and legal links in the authenticated UI.
  7. Add a narrowly matched anonymous Traefik router at higher priority than the Authentik-protected host router. Static bundled assets may be public, but no API, OAuth-start, connection, rule, run, or settings route may match it.
  8. Run automated and manual verification, inspect the cumulative diff, commit in English, and push directly to main without a PR as requested.
  9. Deploy only after separate deployment authorization, then verify the anonymous URLs and protected dashboard from outside the trusted network.

API, data, security, and compatibility impact

  • No MCP, REST, provider, database-schema, or sync-rule contract changes.
  • No calendar access is performed while rendering public pages.
  • The new landing and policy routes are deliberately anonymous and read-only; /app and all existing stateful UI routes stay behind both proxy and application authorization.
  • Existing self-hosted installations continue to work without a proxy change. Their local legal pages will describe the software; each independent public operator remains responsible for supplying accurate operator/contact details.

Automated test plan

  • The root landing page and policy pages return 200 without ForwardAuth headers and use text/html; charset=utf-8.
  • /app and the other authenticated application pages still return 401 without trusted authentication.
  • Unknown paths do not accidentally render the dashboard or a public document.
  • Privacy and Terms links resolve, and the homepage contains a clear product description.
  • Rendered Markdown does not permit raw HTML/script injection.
  • Run go test -race -count=1 ./... and go vet ./....
  • Render/validate the private Compose configuration and confirm the anonymous router matches only the exact root, policy pages, and static asset paths.

Manual QA checklist

  • Open the root landing page and both policy URLs in a private browser session; each must load without an Authentik redirect.
  • Open https://calendar.dzarlax.dev/app in the same session; it must require Authentik.
  • Check mobile and desktop readability, navigation, policy effective date, and contact link.
  • Verify the homepage states the product purpose and links directly to Privacy and Terms.
  • Confirm no connection names, calendar data, credentials, environment values, or internal errors appear in page source.
  • After domain verification, enter the owned-domain URLs in Google OAuth branding and compare the consent-screen identity with the homepage.

Risks and mitigations

  • Proxy bypass expands too far: use an exact root matcher plus explicit policy and asset paths; never make PathPrefix("/") anonymous.
  • Policy overpromises: derive every data-handling statement from current code and call out hosted versus self-hosted responsibility.
  • Markdown injection: disable raw HTML and keep templates/assets embedded in the reviewed binary.
  • Text drifts from behavior: keep one canonical Markdown source and require policy review when OAuth scopes, retention, sync payloads, or hosting change.
  • Google still rejects verification: confirm domain ownership, homepage visibility, branding consistency, and exact scopes separately from document publication.

Rollback plan

Revert the application commit and immutable image, then remove the anonymous landing/policy router. The protected catch-all router and OAuth callbacks remain unchanged throughout. Repository Markdown can remain published even if the application routes are rolled back.
