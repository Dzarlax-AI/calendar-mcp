Per-object quarantine и repair для календарей

Approval required before implementation

1. Краткое резюме

Один повреждённый Google event или Apple .ics-resource не должен переводить весь календарь в generic failed. Мы сохраняем валидные события, помещаем конкретный объект в quarantine, продвигаем безопасный cursor, оставляем последнюю cached projection видимой и даём bounded repair.

Текущий baseline: commit b3e2307 в ветке fix/calendar-sync-protocol-isolation; production уже исправил OAuth client mismatch, но object-level protocol failures остаются.

2. Доказанное текущее поведение

  • Google adapter добавляет warning с ObjectID, но warning не сохраняется отдельно; coordinator блокирует terminal cursor для всей попытки.
  • Apple fallback изолирует malformed resources, но resource path и причина также выбрасываются после page processing.
  • Storage сохраняет valid cached events, но переводит весь calendar source в degraded/protocol.
  • API/UI не поддерживают degraded: неизвестный status нормализуется как failed, поэтому пользователь видит «calendar failed».
  • В production cached events остаются видимыми; OAuth ошибок после parity fix не наблюдается.

3. Целевое поведение

  • Valid siblings синхронизируются, а terminal cursor продвигается.
  • Для известного объекта создаётся quarantine row с provider-local ID, ETag, safe error code, timestamps и bounded retry.
  • Full replacement sweep не удаляет cache membership активного quarantined object.
  • Один due repair запускается под тем же calendar lease; repair не меняет основной cursor.
  • Успешный upsert или подтверждённое удаление очищает active quarantine атомарно; активная нерешённая запись не истекает по TTL.
  • UI показывает amber «Events pending repair» и aggregate count; provider IDs, ETags, URLs, cursors, raw payload и credentials наружу не выходят.

4. Контракт и инварианты

type EventSyncObjectRepairProvider interface {
  RepairEventSyncObject(context.Context, EventSyncObjectRepairRequest) (
    EventSyncObjectRepairResult, error)
}

type EventSyncObjectRepairResult struct {
  Object  SyncObject
  Outcome EventSyncObjectRepairOutcome
  Upserts []EventV2
  Warning *EventSyncWarning
}

type EventSyncObjectRepairOutcome string

const (
  ReplaceMembership    EventSyncObjectRepairOutcome = "replace_membership"
  AbsentFromProjection EventSyncObjectRepairOutcome = "absent_from_projection"
  ProviderDeleted      EventSyncObjectRepairOutcome = "provider_deleted"
  StillQuarantined     EventSyncObjectRepairOutcome = "still_quarantined"
)
  1. Warning без stable ObjectID остаётся hard protocol error.
  2. На каждой page valid mutations и quarantine upserts атомарны; на terminal page в ту же транзакцию входят quarantine-aware sweep, aggregate status и cursor advance.
  3. Changed ETag сбрасывает repair backoff; unchanged ETag сохраняет backoff.
  4. Hard repair failure не блокирует основной feed.
  5. At most one due repair per claimed calendar run.

6. Execution waves

  1. Contract freeze: Terra finalizes types, migration and invariants.
  2. Provider lanes: Terra implements Google and Apple repair against the frozen contract.
  3. Coordinator/storage: Terra integrates atomic quarantine and cursor behavior.
  4. API/UI: Luna consumes the stable aggregate contract.
  5. Integration: root inspects diffs and runs full checks.
  6. Root integration: inspect the cumulative diff, reconcile the model outputs and run the release checks.

7. Tests and QA

  • Focused: go test ./internal/{google,apple,eventsync,storage,web} -count=1.
  • Full: GOCACHE=/private/tmp/calendar-mcp-go-build go test -race -count=1 ./..., go vet ./..., frontend typecheck/Vitest, git diff --check.
  • SQLite and Postgres tests must prove atomic sweep exclusion, cursor advance, repair success/delete, backoff and lease loss; Postgres verification is a production rollout blocker, not optional evidence.
  • Manual QA: malformed Google object, malformed Apple resource, cached events visible, repair accepted, source returns ready, no raw diagnostics in browser response.
  • Deployment QA: same immutable image for serve/worker, migration compatibility, internal health, external UI, one real Google repair and one Apple repair.

8. Риски и rollback

  • Advancing cursor before a repair path is durable could permanently miss a malformed event; quarantine transaction must commit first.
  • Replacement sweep could delete poisoned cache membership; active quarantine exclusion is mandatory.
  • Schema migration is not rolling-safe with older binaries; use an expand-only migration, drain old serve/worker processes, wait for leases, migrate once, then start the same immutable digest. Name a compatible rollback digest before rollout.
  • Diagnostic metadata can leak calendar content; public API exposes aggregate fields only.

До migration activation rollback — previous immutable digest. После schema activation rollback only via the pre-declared compatibility build; do not manually delete cursors, cached rows or quarantine rows. A production rollout is blocked if Postgres migration and replay checks are unavailable.

9. Открытые решения

  • Публичный status: рекомендовано добавить degraded вместо маскировки под failed.
  • Repair: Phase 1 — automatic bounded repair; Phase 2 — calendar-scoped manual scheduling. HTTP action performs no provider I/O, atomically wakes at most one due quarantine/next sync, and returns explicit 202/409/422 outcomes.
  • Quarantine retention: active unresolved rows have no TTL; resolved/history retention is Phase 2. Provider object IDs, ETags and diagnostic tokens do not cross the public API.
  • Provider semantics: Google 404 is confirmed deletion; Apple repair must capture the response ETag (never reuse the caller ETag) and distinguish changed, unchanged and missing resources.
  • Hard auth/permission/schema/protocol failures remain quarantined or failed according to source semantics; transient/rate-limit repair failures reschedule without blocking the normal feed.
  • Microsoft не включать в этот scope: для него пока нет доказанной object-level repair semantics.

10. Фактический результат реализации

  • Backend contract/storage/coordinator и Google/Apple object repair реализованы; schema version поднята до 3 с SQLite/Postgres quarantine migration.
  • API/UI сохраняют degraded, не раскрывают provider payloads и оставляют cached events видимыми; manual retry использует существующий provider-free refresh endpoint.
  • Проверки: полный Go test и vet пройдены, frontend Vitest (21 тест) и production build пройдены, git diff --check чистый.
  • Sol code review PR нашёл и заблокировал три проблемы; они исправлены в последующем commit: active quarantine влияет на terminal status, Apple malformed repair сохраняет response ETag, still-quarantined repair получает bounded retry.
  • Ограничение: production Postgres integration требует отдельного окружения с TEST_POSTGRES_URL; deploy до этой проверки не разрешён.
