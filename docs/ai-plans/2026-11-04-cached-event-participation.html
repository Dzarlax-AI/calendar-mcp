Ответ пользователя в кэше событий

Редакция 3 · Реализовано локально · Согласовано пользователем 2026-11-04

Цель и границы

Добавить в ответ только GET /api/native/v1/cached-events необязательное поле self_response_status, чтобы мост мог скрывать отклонённые пользователем события. Сервер не фильтрует события. При отсутствии поля мост сохраняет событие видимым. Это ответ подключённого пользователя, а не общий статус события и не утверждение о владельце общего календаря.

В рамках этой редакции поддерживается только достоверный Google self. Microsoft и Apple проверены по текущему коду и остаются неизвестными; их поддержка потребует отдельного подтверждения семантики владельца и изменения плана. Мост, настройки дисплея, авторизация, provider writes, MCP и другие API не меняются.

Текущее состояние и контракт

На проверенной рабочей версии internal/google/mapping_v2.go переносит self и responseStatus участников в EventV2; internal/google/event_sync.go использует этот mapping, а internal/storage/event_cache.go сохраняет полный EventV2 как JSON. Поэтому существующие кэшированные записи могут уже содержать нужный признак; для записей без него результат неизвестен. Маршрут internal/nativeapi/server.go читает только локальный кэш и выдаёт узкую проекцию без участников. Свежесть определяется существующими sources и complete.

Предлагаемый контракт: поле присутствует только для Google-календаря с сохранённым provider ID primary, когда найден ровно один участник с self=true и его ответ входит в допустимый набор: accepted, declined, tentative, needsAction. Значения передаются в написании Google. Нет self, несколько self, пустой или неизвестный ответ, другие провайдеры — поле отсутствует. Никаких догадок по email, организатору, статусу события или отсутствию приглашённых. Мост скрывает только точное значение declined; остальные и неизвестные остаются видимыми. Например: {"status":"confirmed","self_response_status":"declined"} — отклонено участником; {"status":"confirmed"} — ответ неизвестен.

Ответ относится к аутентифицированной учётной записи, указанной Google как self. На общих календарях это не обязательно владелец календаря; не выдавать его за ответ другого человека. Доступность self и самих отклонённых событий зависит от данных Google и прав доступа. При устаревшем кэше ответ также может быть устаревшим; существующие индикаторы свежести не изменяются.

Реализация и совместимость

  1. Добавить поле с omitempty в узкую структуру native cached-events и отдельное преобразование Google self, не расширяя EventV2, БД или другие проекции. Использовать текущие данные EventV2 после чтения; никакого provider I/O из обработчика.
  2. Проверить передачу self в синтетическом пути Google sync → кэш → native endpoint, а также корректность write-through и старого JSON без поля. Старый кэш с сохранёнными attendees работает сразу; данные, которые отсутствовали при записи, появятся только при последующем обновлении соответствующей записи или полном обновлении проекции. Не сбрасывать курсоры и не инициировать массовый backfill.
  3. Документировать поле, набор значений, неизвестность, ограничение учётной записи и свежести в README. Сохранить контракт без идентификаторов и списка участников, email и других персональных данных.

Ожидаемые файлы: internal/nativeapi/server.go, его тесты, возможно синтетические тесты Google sync/storage и README.md. Схемная миграция не нужна: существующий JSON содержит участников; никаких новых данных участников не добавляется в кэш. Существующие изменения пользователя в этих файлах необходимо сохранить и проверить перед правкой.

Проверка и приёмка

Проверки выполнены на изолированных фикстурах без реальных календарей и уведомлений; фактические результаты указаны ниже.

  • Тесты значений Google: все четыре ответа; отсутствующий self; несколько self, в том числе с противоречивыми статусами; неизвестный или пустой ответ; событие без attendees; несовпадение provider/ID; Microsoft и Apple с похожими данными — поле отсутствует.
  • Интеграционный синтетический тест sync → сохранение/чтение → HTTP: поле попадает в ответ; старый payload без self остаётся видимым для моста; при изменении ответа последующая запись заменяет прежнюю. Проверить повторяющиеся экземпляры с собственными ответами без наследования догадками.
  • Проверить JSON на отсутствие attendee, email и прочих данных участников; подтвердить существующую авторизацию, completeness и отсутствие фильтрации/сетевого обращения к провайдеру.
  • Выполнить целевые Go-тесты затронутых пакетов, затем go test -race -count=1 ./... и go vet ./..., если среда позволяет. Зафиксировать фактические результаты и ограничения в этом документе.

Риски и восстановление

Отсутствие поля безопасно для видимости, но не означает согласие или отсутствие приглашения. Устаревший ответ может временно скрыть событие после изменения ответа; мост должен учитывать существующие признаки свежести. Провайдер может не отдавать отклонённое событие совсем, и это изменение не восстанавливает его. При откате удалить только добавленные проекцию, тесты и документацию, сохранив посторонние изменения; ни миграция, ни необратимый backfill не планируются.
