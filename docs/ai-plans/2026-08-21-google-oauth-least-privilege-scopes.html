Google OAuth Least-Privilege Scopes

Approval required before implementation

Prepared 2026-08-21 for calendar-mcp.

Task Summary

Replace the broad Google Calendar OAuth permission with the narrow permissions required to discover calendars and synchronize their events. Keep the hosted web UI, MCP operations, and Google-to/from-any-provider synchronization functional while making the runtime request match the scopes declared in Google Cloud.

Current Behavior

  • Both the legacy environment-driven Google provider and the web connection flow request https://www.googleapis.com/auth/calendar.
  • That scope grants broader calendar administration rights than the product uses, including calendar sharing and calendar deletion.
  • The same literal is duplicated in internal/google/auth.go and internal/runtime/serve.go, allowing the two connection paths to drift.
  • The operator has reported that the Google Cloud consent configuration and production OAuth client credentials are now configured for the narrower scope set.

Desired Behavior and Scope Decision

ScopeProduct use
https://www.googleapis.com/auth/calendar.calendarlist.readonlyList the calendars visible to the connected account and expose them for selection in the UI, MCP, and sync rules.
https://www.googleapis.com/auth/calendar.eventsRead and mutate events on calendars where the connected account already has the corresponding access.

Do not request full calendar, ACL, settings, calendar-property mutation, or calendar subscription mutation scopes. Do not use calendar.events.owned, because that would prevent supported synchronization involving shared calendars not owned by the connected account.

Assumptions and Unknowns

  • Google Cloud contains exactly the two desired scopes above; this must be checked manually because repository code cannot inspect the console configuration.
  • The redirect URI remains https://calendar.dzarlax.dev/oauth/google/callback.
  • No active production Google connection needs to be preserved. If one exists, it will not be silently deleted or mutated; the operator must explicitly revoke and reconnect it to obtain a genuinely narrowed grant.
  • Narrowing scopes improves least privilege but does not guarantee that Google will waive scope justification or demo-video review.

Files Likely to Change

  • internal/google/auth.go — define one canonical OAuth scope function and use it in the legacy provider path.
  • internal/google/auth_test.go — assert the exact two scopes and explicitly reject the broad scope.
  • internal/runtime/serve.go — consume the canonical Google scope function in the web OAuth path instead of maintaining a duplicate literal.
  • README.md — document the least-privilege Google scope contract and reconnection requirement.
  • This plan — record actual implementation, verification, deployment, limitations, and follow-ups after approval.

No database schema or migration is planned.

Implementation Steps

  1. Add a canonical google.OAuthScopes() helper that returns a fresh slice containing only calendar.calendarlist.readonly and calendar.events.
  2. Use that helper in both the legacy token flow and the hosted web OAuth provider configuration.
  3. Add regression tests for exact membership, absence of full calendar, and defensive slice copying.
  4. Update operator documentation without including client credentials or tokens.
  5. Run local verification, commit in English, and publish through CI only after a separate implementation approval.
  6. Deploy the CI-built immutable image by recreating only calendar-serve; do not touch legacy calendar-mcp, worker, PostgreSQL, Traefik, or Authentik.

Test and Manual QA Plan

  • go test -race -count=1 ./...
  • go vet ./...
  • go build ./cmd/calendar ./cmd/server
  • Inspect the generated Google authorization redirect and confirm it contains the two approved scopes and not the broad auth/calendar scope.
  • Connect a dedicated test Google account from the web UI.
  • Verify calendar listing, event read, create, update, delete, and a dry-run synchronization using a dedicated test calendar with notifications and invitations disabled.
  • Confirm persisted connection metadata records the two scopes and that service health/logs remain clean.
  • Only after these checks, record the Google verification video using the deployed flow.

Risks and Edge Cases

  • Existing refresh tokens can retain the previously granted broad permission. Changing requested scopes does not revoke old grants.
  • Removing calendar.calendarlist.readonly would break calendar discovery; replacing calendar.events with calendar.events.owned would break shared-calendar destinations and sources.
  • Google Console and runtime scope mismatch can cause verification rejection or consent behavior that differs from the submitted video.
  • A real-calendar test could send invitations or modify production data. QA must use an empty/dedicated calendar and explicitly disabled notifications.
  • Google may still require a justification and unlisted YouTube demo because event access remains sensitive.

Rollback Plan

Roll production back to the previously recorded immutable image digest and restore the prior server .env backup if deployment configuration changes unexpectedly. Code rollback restores the previous full scope, but doing so would also require restoring the Google Cloud scope declaration and obtaining a new user grant; existing tokens must never be assumed to change scope automatically.

Open Questions

  • Confirm in Google Cloud that the configured scope list is exactly calendar.calendarlist.readonly plus calendar.events.
  • Confirm whether any Google account is already connected in production. If yes, revoke the old Google grant before reconnecting for the demo.

Approval Gate

Production code, OAuth grants, and deployment must not be changed until the user explicitly approves this plan. Approval authorizes implementation and verification, but recording or publishing the YouTube video remains a separate user action.
