React Calendar Client

Make a unified, interactive calendar the primary Calendar Platform screen, migrate the small authenticated control plane to React, and support safe event viewing, creation, editing, rescheduling, and deletion across connected Google, Microsoft, and Apple calendars.

1. Current Architecture

  • calendar serve composes one provider registry and application service for MCP, optional internal REST, OAuth, and the web control plane.
  • The authenticated UI is a small Go-template application in internal/web/ with same-origin CSS and a small vanilla JavaScript file. It does not load HTMX; a test explicitly prevents HTMX runtime/boosted navigation because Authentik redirects must remain top-level navigation.
  • Public landing, privacy, terms, and OAuth callback routes are intentionally outside ForwardAuth. Authenticated application routes require the trusted X-authentik-username header, unless the explicit local bypass is enabled.
  • Mutating UI forms already require exact origin plus a double-submit CSRF token. Internal REST uses an API key on a separate listener and must not be exposed to the browser.
  • The typed V2 application layer already supports expanded event reads, get/create/update/delete, recurrence scopes, ETags, provider capability checks, and notification_policy=none. Its external REST exposure is controlled by ENABLE_V2.
  • The current dashboard is operational status, not a calendar. Existing Connections, Sync Rules, Runs, and Settings flows must remain available during the migration.

2. Decisions and Desired Behavior

  • Frontend: React + TypeScript + Vite. React owns all authenticated screens so the project does not retain two competing authenticated UI stacks.
  • Calendar engine: FullCalendar React with the Standard day-grid, time-grid, list, and interaction packages. FullCalendar owns date layout, selection, drag, and resize; Calendar Platform owns the toolbar, sidebar, event rendering, drawers, dialogs, colors, and responsive styling.
  • Data fetching: TanStack Query for server state and mutation invalidation. React Router handles authenticated routes. No Next.js, Redux, runtime CDN, or server-side JavaScript service.
  • Primary route: /app opens the calendar. Week is the initial desktop view; day is the initial narrow-screen view. Month and list remain available.
  • Unified view: read events from all selected connected calendars for the visible range; show calendar/provider identity, all-day events, and partial-source failures without hiding successful sources.
  • MVP mutations: create, open/view, edit title/time/all-day/description/location, drag or resize to reschedule, and delete. Calendar reassignment, attendees, RSVP, reminders, conferencing, attachments, natural-language input, and tasks are deferred.
  • Recurring events: display expanded occurrences. Before edit/reschedule/delete, ask for only the scopes supported by that calendar: this event, this and following, or entire series. Never guess a recurrence scope.
  • Control-plane parity: Connections, Sync Rules, Runs, and Settings move into the React shell with the same capabilities. Google/Microsoft connect and reconnect continue through ordinary top-level links, not fetch.
  • Preferences: selected calendars, current view, sidebar state, and display density may use local storage; provider data and secrets may not.

3. Calendar Write Safety

  • Every create/update/delete request generated by the web UI sets notification_policy to none. The UI does not expose a notification override in this MVP.
  • Create and update payloads omit attendees, conference data, reminders, attachments, and guest permissions. Existing values not edited by the form must not be cleared accidentally.
  • Use ETags for edits, drag/resize, and delete when supplied by the provider. A conflict rolls the optimistic UI back, refetches the event, and asks the user to retry.
  • Drag/resize is optimistic only visually. Any failure restores the original event position and reports the provider-safe error.
  • Delete requires explicit confirmation and has no automatic retry after an ambiguous provider response.
  • Before the first live provider mutation, confirm notification/invitation suppression and use a dedicated empty test calendar with synthetic events. Production/user calendars are outside this plan's automatic verification authority.

4. Browser API, Auth, and Data Contract

Add a same-origin browser API under /api/ui/. It calls the existing storage, connection, and application services directly; it does not proxy the API-key REST listener and never sends the MCP/API key to normal calendar requests.

GET    /api/ui/events?start=&end=&calendar_id=...
GET    /api/ui/event?calendar_id=&event_id=
POST   /api/ui/events
PATCH  /api/ui/event?calendar_id=&event_id=
DELETE /api/ui/event?calendar_id=&event_id=

GET    /api/ui/control-plane

DELETE /api/ui/connections/{id}
POST   /api/ui/rules
POST   /api/ui/rules/{id}/enable
POST   /api/ui/rules/{id}/run
POST   /api/ui/settings/mcp-key/reveal
  • bootstrap returns authenticated UI metadata, browser-safe calendar records, capabilities needed for controls, and a CSRF token. It must not contain provider credentials or the MCP key.
  • Event list accepts repeated calendar IDs, drains bounded provider pagination server-side, sorts results, and returns per-source completion/error metadata. A provider failure can produce a partial successful response.
  • Timed events use RFC3339 instants plus explicit IANA timezone. All-day events use date values and an exclusive end date. Display defaults to the browser timezone without rewriting stored event semantics.
  • JSON mutations require ForwardAuth/local bypass, exact public origin, the CSRF cookie, and matching X-CSRF-Token. Keep form-token compatibility only while old handlers exist. The CSRF cookie must be secure for an HTTPS CALENDAR_PUBLIC_URL, including behind TLS termination.
  • Return structured error codes and safe messages from calendar.APIError; do not leak provider payloads, tokens, or raw credentials.
  • The browser API uses the typed application service regardless of whether external V2 MCP/REST catalog exposure is enabled. ENABLE_V2 remains an external compatibility switch.

9. Risks, Edge Cases, and Deferred Scope

  • Build coupling: Go embedding needs a deterministic frontend-before-Go production build. Make, Docker, and CI must share the same order, while source-only Go tests remain possible with an explicit placeholder/failure mode.
  • Provider differences: capabilities and recurrence scopes differ. Controls must be capability-driven, not provider-name guesses.
  • Fan-out cost: large ranges or many calendars can trigger many paginated provider calls. Fetch only the visible range, cancel stale requests, cap pagination, and surface partial completion.
  • Timezone/DST: browser display timezone and event timezone can differ; never derive provider payloads from formatted labels.
  • Recurring drag semantics: a moved occurrence may need scope=single plus original start identity. Require a scope decision before committing the drag.
  • Read-only/special events: birthdays, working location, provider-locked events, or calendars without write capability must render without edit/delete controls.
  • Cross-calendar move: deliberately deferred. The existing same-provider move API does not define safe cross-provider move semantics; copy-then-delete would be a separate consequential workflow.
  • Deferred product scope: attendees/RSVP, notification controls, Meet/Teams, reminders, attachments, tasks, search, natural-language creation, offline/PWA, and cross-calendar moves.

10. Rollback

Keep the existing Go-template authenticated UI until React route and functional parity tests pass. During development, switching the route registration back to the template handlers restores the old UI without database migration or provider reauthorization. The browser API is additive and can be removed independently. No schema migration is planned for this MVP.

A production rollback, if later authorized, would deploy the previous immutable image; connected accounts and sync data remain compatible because this plan does not change their storage schema.

11. Assumptions and Open Questions

  • Assumed: the visual spike is a direction check, not a pixel-perfect specification. Implementation will reuse its information architecture while refining density, typography, spacing, compact events, and narrow-screen behavior.
  • Assumed: the first release migrates the whole small authenticated control plane to avoid a long-lived mixed frontend; public/legal rendering stays in Go.
  • Assumed: week/day/month/list plus calendar filtering are enough for initial viewing; global event search is deferred.
  • Assumed: no schema change is required; connected calendar metadata and the provider registry remain the source of truth.
  • Implementation-time check: confirm current compatible package versions and licenses before locking dependencies.
  • Post-MVP choice: whether cross-calendar move should mean provider-native move, copy-delete with confirmation, or remain unsupported.
