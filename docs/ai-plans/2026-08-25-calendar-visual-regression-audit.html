Calendar Visual Regression Audit

Implemented locally — awaiting PR review

Task summary

Add a deterministic, screenshot-backed visual QA suite for Calendar so responsive failures are caught before merge. This follows the separate responsive fix in PR #21; it does not change production Calendar behavior.

Current behavior and evidence

  • frontend has Vite, Vitest, and jsdom unit tests only; there is no browser or screenshot test harness.
  • Production and local Vite both require /api/ui/bootstrap; an unauthenticated local browser shows the Calendar unavailable gate, so it cannot exercise a real Calendar surface.
  • The Calendar has responsive boundaries at 560, 820, 1080, and 1439/1440px, plus a canvas-width container query. The reported 1280px defect crossed the prior drawer breakpoint without a rendered regression test.
  • Current CI runs frontend typecheck, Vitest, build, Docker build, Go tests, and vet, but no Chromium job or visual artifact upload.

Desired outcome

Every Calendar UI PR runs deterministic browser checks using synthetic data, captures approved screenshots at representative viewport sizes, and fails with inspectable artifacts when layout changes unexpectedly. No test contacts production, Authentik, providers, calendars, or sends notifications.

Proposed implementation

  1. Add @playwright/test, a test:e2e script, and frontend/playwright.config.ts. Run against built local Vite preview at /spa/app, with fixed timezone, locale, reduced motion, and deterministic fonts.
  2. Add source-owned synthetic fixtures under frontend/e2e/fixtures/: seven capability-varied calendars; long, read-only, all-day, overlapping, and Meet events; sanitized HTML; source states; and mutation outcomes. Fixtures contain no personal calendar data.
  3. In Playwright, intercept only /api/ui/* requests per test. Fulfil bootstrap, events, and relevant mutation/refresh requests locally; reset localStorage before each test.
  4. Add calendar.visual.spec.ts with screenshots and functional assertions: no document horizontal overflow, visible key controls, event drawer close via Escape/scrim, modal focus/action visibility, and responsive mode at the exact boundaries.
  5. Commit reviewed Linux Chromium screenshot baselines. Add CI Chromium installation, npm --prefix frontend run test:e2e, and failure-only uploads for Playwright report, traces, and screenshot diffs.
  6. Keep Vitest for domain/unit checks. Add a small live production smoke checklist after deployment, performed in an authenticated user session, but do not automate it against real calendar data.

Likely files

  • frontend/package.json and frontend/package-lock.json — Playwright dependency and scripts.
  • frontend/playwright.config.ts — browser, server, screenshot, timezone, and retries policy.
  • frontend/e2e/calendar.visual.spec.ts and frontend/e2e/fixtures/calendar.ts — deterministic routes, interactions, assertions, and fixtures.
  • frontend/e2e/...-snapshots/ — reviewed Chromium baselines.
  • .github/workflows/ci.yml — install Chromium, run visual suite, upload failure artifacts.
  • Only if tests expose a real defect: the narrowest affected Calendar component or stylesheet. No production API, storage, provider, auth, or migration changes are planned.

Validation and manual QA

  • npm --prefix frontend test, npm --prefix frontend run typecheck, npm --prefix frontend run build, and npm --prefix frontend run test:e2e.
  • CI passes from a clean Ubuntu Chromium environment and produces inspectable artifacts on an intentional failing snapshot rehearsal.
  • Review screenshots at the five primary widths and boundary probes. Confirm no crop, horizontal page scroll, multi-line primary action, inaccessible close control, or hidden destructive action.
  • After a future deployment, manually open the real Calendar, a rich-description event, and Create event in an authenticated session. Treat this as a smoke check, not fixture evidence.

Risks, trade-offs, and safeguards

  • Visual baselines are browser/OS-sensitive. Generate and compare them only in Ubuntu Chromium CI, not by mixing local macOS goldens.
  • Browser installation and screenshots increase CI time and artifact storage. Measure the first run; upload reports only on failure and keep the matrix targeted.
  • Fixture drift can hide real UX gaps. Keep fixtures representative and add a state whenever production reveals a new class of issue.
  • No automatic browser test will prove production authentication or provider sync. Those remain bounded manual smoke checks.

Rollback

Remove the new CI visual-test step and Playwright files in one reverting commit. Production behavior and data are unaffected because the suite runs only against intercepted local responses.
