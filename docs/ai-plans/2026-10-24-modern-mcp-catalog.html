1. Цель и границы

Пользователь и ассистент видят один современный набор инструментов с именами без _v2. Старые клиенты сохраняют свои имена, схемы и поведение в отдельном режиме совместимости. Выбор контракта происходит при настройке подключения, а не при каждом вызове.

В объёме: регистрация MCP-каталогов, HTTP-маршруты, явный выбор режима основного адреса, конфигурация, тесты и инструкции миграции клиентов. Вне объёма: изменение провайдеров и бизнес-логики, REST/native API, синхронизация, схема БД, OAuth, отзыв ключей, изменение разрешений Gateway и производственных подключений.

Приёмка: современный каталог содержит ровно 12 инструментов без суффикса; каталог совместимости сохраняет текущие 5 либо 16 инструментов в зависимости от ENABLE_V2; без новых настроек прежние клиенты продолжают работать на прежнем адресе. Ни одна операция не выбирает контракт по содержимому аргументов и не переключается на другой контракт при ошибке.

2. Исходное состояние до реализации

  • internal/mcpserver/server.go: buildServer всегда вызывает registerTools; при включённом флаге добавляет registerToolsV2. Register обслуживает /mcp и /mcp/.
  • tools.go: пять исходных инструментов. tools_v2.go: ещё одиннадцать, включая get_calendar_capabilities; чтение и запись проходят через application.Service. list_calendars общий для обоих будущих каталогов.
  • Исходный get_events возвращает список событий через jsonResult. V2 возвращает структурированный результат страницы, сведения об источниках и полноте. Схемы создания/изменения также различаются. Замена обработчика под старым именем на том же подключении нарушит контракт.
  • internal/runtime/serve.go подключает MCP и отдельно использует EnableV2 для REST. Оба CLI используют этот runtime. Тестовая утилита scripts/measure_calendar_listing.go вызывает существующий Register.
  • internal/config/config.go и .env.example: ENABLE_V2=false по умолчанию. Middleware применяет API key, дополнительный legacy key и существующий явный режим без аутентификации. Web UI показывает адрес с /mcp.
  • Есть тесты регистрации и внутрипроцессный MCP-тест Apple search. CI содержит go test -race -count=1 ./..., CGO_ENABLED=0 go build ./..., CGO_ENABLED=0 go vet ./....

База: ветка codex/google-orphan-occurrence, HEAD 24c8e163b7e301040922f29b5f39ace150e3083d. Рабочее дерево уже изменено: среди прочего README.md, AGENTS.md, internal/mcpserver/tools_v2.go, Apple/application/registry и новые тесты/скрипты. Исполнитель должен учитывать фактическое дерево, а не только HEAD, и сохранить эти изменения.

На этапе планирования были изучены исходники и конфигурация; Go-тесты и сборка тогда ещё не выполнялись. Production и конфигурации реальных клиентов не проверялись. В доступном чату каталоге присутствуют обе версии чтения. Полный перечень потребителей неизвестен.

Явные адреса и безопасный default

Новая настройка MCP_CATALOG_MODE=compat|modern, default compat. Она выбирает только контракт /mcp. Это позволяет обновить бинарник без автоматического изменения контракта существующих клиентов.

Адрес сервисаПоведение
/mcp, /mcp/Каталог, выбранный MCP_CATALOG_MODE. При отсутствии новой настройки — прежний каталог.
/mcp/modern, /mcp/modern/Только современный каталог, доступен при ENABLE_V2=true.
/mcp/compat, /mcp/compat/Зафиксированное прежнее поведение: исходные пять инструментов, плюс существующие одиннадцать при ENABLE_V2=true. Суффиксы сохраняются для уже использующих их клиентов.

Неизвестный непустой режим — ошибка старта. modern вместе с ENABLE_V2=false — ошибка старта до открытия listener. При выключенном V2 modern-путь возвращает 404 после существующих auth/body-limit проверок, не попадает в compat-обработчик через /mcp/ и не перенаправляет клиента. REST-флаг сохраняет прежнее значение и смысл.

Все адреса используют одну действующую политику API key и ограничения тела запроса. Режим не выбирается по ключу, заголовку или параметрам инструмента; прав на запись он не расширяет. Выделить точные маршруты и изолированные MCP server/transport instances для двух каталогов; основной адрес использует транспорт выбранного каталога. Проверить, что сессия другого каталога не позволяет вызвать инструмент с чужим контрактом. Не использовать HTTP redirect для MCP POST.

Совместимость означает сохранение всего прежнего каталога, включая старые V2-имена. Поэтому дубли временно остаются только в compat-подключении. Одновременное подключение modern и compat к одному ассистенту снова создаст неоднозначность; клиенту выбирают один каталог.

4. Переход клиентов и открытые вопросы

  1. Реализовать и проверить оба каталога локально. Обновление с default compat не меняет текущий /mcp. Здесь планируется только код и документация, без выкладки.
  2. Перед реальной миграцией составить таблицу потребителей: клиент/подключение, прямой адрес или Gateway, вызываемые имена, ожидаемая схема, разрешённые операции. Проверять актуальную конфигурацию и безопасные метаданные, не сохранять ключи и частные события.
  3. После отдельного разрешения перевести один выбранный клиент на явный modern-путь. На Gateway использовать отдельную идентичность modern-сервера, чтобы одинаковое имя get_events не унаследовало legacy schema/cache/ACL. Существующую compat-регистрацию и разрешения не переиспользовать молча.
  4. Проверить initialize, tools/list, схемы, безопасное чтение, обработку частичных результатов и следующей страницы. Обновить кеши/подключение штатным способом, проверить отсутствие второго calendar-подключения. Перенос разрешений — явное сопоставление, без автоматического расширения.
  5. Остальных клиентов переводить по одному. После подтверждённой инвентаризации оставшиеся старые клиенты закрепить на /mcp/compat. Только затем отдельным разрешённым изменением выбрать MCP_CATALOG_MODE=modern для /mcp. Срок удаления compat не задаётся этим планом.

Основной согласованный пакет регистрации и тестов подходит агенту gpt-6-luna с усилием high: контракт и границы определены, бизнес-логика сохраняется. Brief исполнителя: база — указанные HEAD плюс текущее грязное дерево, которое перед запуском повторно перечитывается; разрешены только файлы этапов 1–3; запрещены provider/application изменения, реальные календари, Git/external actions. Сначала согласовать с ведущим снимок контрактов, затем общий пакет кода и проверки. Отчёт: файлы, фактический diff, команды и результаты, ограничения. Документацию и общий diff завершает ведущий после приёмки кода. Review получает этот план, реальный diff и результаты тестов; материал не отправляется внешним сервисам.

6. Проверки и критерии приёмки

Ниже сохранены согласованные критерии проверки. Результаты выполнения приведены в разделе 8. Используются синтетические календари, локальный httptest и fake-провайдеры; реальные события не создаются и уведомления не отправляются.

  1. Каталоги: compat + V2 off = прежние пять; compat + V2 on = прежние шестнадцать; modern = ровно двенадцать. Нет повторяющихся имён. В modern нет ни одного _v2; вызов get_events_v2 возвращает unknown tool. В compat get_events сохраняет старый результат, get_events_v2 — прежний современный контракт.
  2. Эквивалентность: схемы каждого modern-инструмента равны схемам соответствующего текущего V2-инструмента, кроме имени. Проверить также raw schema update_event. Сравнить structured/text outputs и ошибки. Список событий: неполный источник, page token и продолжение не теряются; все инструменты вызывают тот же обработчик.
  3. Запись: fake-провайдер видит те же scope/ETag/operation ID/presence-aware patch и notification policy. Проверить пропущенное значение, явный none, preview и отказ неподдерживаемой операции; не менять действующие defaults и защиту от уведомлений.
  4. Маршруты: HTTP initialize → tools/list → tools/call на обоих явных адресах и основном адресе в обоих режимах. Проверить trailing slash, неизвестный подпуть, V2 off, отсутствие redirect/fallback, параллельные независимые клиенты и чужие session IDs. Уже открытая compat-сессия не превращается в modern при выборе другим клиентом другого пути.
  5. Защита: valid primary/legacy API key, invalid/missing key, явно разрешённый unauthenticated-режим, прежний body limit на всех путях. Native/read-only tokens не приобретают доступ к MCP. Для неизвестных путей результат не должен раскрывать другой каталог.
  6. Конфигурация: переменная отсутствует или пуста → compat; compat/modern принимаются; опечатка отклоняется; modern + V2 off отклоняется до listener. Старый вызов Register и локальный listing fixture продолжают собираться.

Ошибки текущей базы отделить от регрессий изменений и записать, а не объявлять baseline зелёным.

Ручная локальная QA: новый клиент, подключённый только к modern, видит один get_events и одну операцию каждого вида; описание объясняет страницы/полноту. Старый клиент с прежней схемой успешно читает fixture на неизменённом адресе. Реальная QA после отдельного разрешения выкладки: health и полный безопасный путь чтения через фактический proxy/Gateway. До любой проверки записи на реальных данных отдельно подтвердить изолированный календарь и отключение приглашений/уведомлений.

7. Риски и откат

  • Одинаковое имя — другой контракт: запрещено незаметно менять основной адрес, пока потребители не проверены. Снимки схем и ответы защищают compat; отдельные идентичности Gateway защищают кеши и разрешения.
  • Частичный результат принимается за пустой: modern сохраняет sources/complete и page metadata; примеры клиента обязаны их учитывать.
  • Пересечение маршрутов и сессий: явные пути, без редиректов и выбора режима по входным аргументам; проверить SDK HTTP-поведением, а не только списком Go-инструментов.
  • Устаревшие списки инструментов у клиента: переподключение и штатное обновление discovery/cache входят в миграцию; на этапе кода реальные настройки не трогаются.
  • Существующие незакоммиченные изменения: до реализации повторить status/diff; учитывать пересечения в tools_v2.go, README и AGENTS. Не выполнять reset/checkout поверх пользовательской работы.

Локальный откат: отменить только изменения этой реализации по её проверенному diff, сохранив исходную грязную базу. После отдельно разрешённой выкладки откат клиента — вернуть его прежнее compat-подключение и схемы/разрешения; не удалять modern-регистрацию вместе с чужими настройками. После будущего переключения default возврат MCP_CATALOG_MODE=compat тоже требует разрешённого production-изменения и проверки клиентов, уже использующих основной адрес как modern. Клиентов на явных путях смена default не затрагивает.

Откат бинарника требует сначала вернуть modern-клиентов на совместимый контракт: предыдущий бинарник не знает новых путей. Не удалять данные, токены, подключения или sync mappings ради отката.
