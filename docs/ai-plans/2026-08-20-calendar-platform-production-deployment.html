Calendar Platform Production Deployment

Parallel shadow rollout with an unchanged MCP URL, Authentik-protected UI, isolated PostgreSQL schema, temporary dual API keys, and immediate router rollback.

1. Task summary and inspected current state

Current production

One legacy calendar-mcp container serves https://mcp.dzarlax.dev/calendar. No platform worker is running.

New public origin

https://calendar.dzarlax.dev is reserved for UI and OAuth. The user created DNS, but propagation was not visible at the latest check.

Shared infrastructure

Reuse Traefik, Authentik, infra-postgres-1, and existing Docker networks. The live calendar role/schema still need explicit provisioning.

Credential state

Legacy credentials remain temporarily compatible. New API/provider credentials are required before legacy retirement.

2. Desired topology

calendar-mcp

Legacy image and credentials. Low-priority MCP router. Kept running for compatibility and rollback.

calendar-serve

New immutable image. UI, OAuth, MCP, schema migration. Authentik on UI only.

calendar-worker

Same immutable image. Infra network only. Starts after connection QA; rules begin paused.

MCP stays at: https://mcp.dzarlax.dev/calendar. A priority-300 Traefik overlay moves traffic to calendar-serve without removing the legacy router.

4. Implementation sequence

  1. Create an isolated branch/worktree from current origin/main; preserve the dirty root checkout.
  2. Implement dual-key support test-first; run race tests, vet, build, and docs checks.
  3. Prepare base Compose, cutover overlay, and PostgreSQL provisioning SQL; validate against disposable PostgreSQL 17.
  4. Review cumulative diffs. Commit/push/PR only after a separate authorization.
  5. After merge, resolve the CI-built GHCR digest. Never deploy latest or build on the VPS.
  6. Perform read-only production preflight, backup PostgreSQL, provision the schema, configure Authentik, and create parallel provider credentials under a separate production approval.
  7. Start only calendar-serve; verify TLS, Authentik, callbacks, migrations, health, logs, and unchanged legacy MCP.
  8. Connect providers, then start worker and test only paused rules on empty dedicated calendars.
  9. After explicit cutover approval, add the priority-300 router and verify MCP with primary and legacy keys plus a real Personal Assistant read path.
  10. Keep legacy service, router, key, and credentials until the user separately authorizes retirement.

5. Test and manual QA plan

  • Dual-key tests: primary accepted, non-empty legacy accepted, invalid rejected, and an absent credential rejected when the optional legacy key is unset.
  • go test -race -count=1 ./..., go vet ./..., go build ./..., formatting, and git diff --check.
  • Base and cutover Compose both render; worker has no Traefik exposure; all deployed images are digest-pinned.
  • Provisioning SQL succeeds twice on disposable PostgreSQL 17 and proves schema ownership/search path/public denial.
  • DNS/TLS, Authentik redirect, authenticated UI, callback invalid-state behavior, spoofed-header resistance, health/restarts/logs.
  • Provider connection and calendar discovery with newly authorized credentials.
  • Dry run followed by one approved real sync on empty test calendars: normal, all-day, and recurring moved exception.
  • No copied attendees, invitations, or notifications.
  • Unchanged MCP URL works with both keys; invalid key fails; Personal Assistant read path succeeds.

6. Risks and edge cases

  • Legacy key exposure: compatibility is intentional but temporary. It is removed only on the user's command.
  • OAuth cutover: standalone token files are not imported. Provider accounts must be reauthorized through the UI.
  • Shared database: the live role/schema are absent despite the first-start init source. Provision explicitly and verify permissions.
  • Router collision: use unique new router/middleware/service names and explicit priority; never overwrite the legacy labels.
  • Sync safety: no production-calendar rule may be enabled during initial deployment. Test calendars and disabled notifications/invites are mandatory.
  • Secret handling: do not copy `.env`, print values, place credentials in commands/artifacts, or pass an Authentik token until a safe method is agreed.

7. Rollback

  • Before cutover: stop only new serve/worker; legacy MCP remains untouched.
  • After cutover: recreate only calendar-serve from base Compose without the overlay. The lower-priority legacy router resumes.
  • Pause the exact test rule and stop worker if sync validation fails.
  • Preserve schema, volumes, token files, mappings, old keys, and old provider credentials. No automatic destructive rollback.
  • Do not restart shared Traefik, Authentik, or PostgreSQL without separate approval and evidence that it is necessary.

8. Assumptions, unknowns, and exclusions

  • DNS propagation and a valid certificate must be observed before OAuth configuration.
  • The exact Authentik identity/policy and the final GHCR digest are discovered at execution time; neither is invented in the plan.
  • Initial deployment excludes old-key removal, credential revocation, legacy-container deletion, legacy-router deletion, and production-calendar sync enablement.
  • The user manages Cloudflare DNS. The assistant configures Authentik after production approval; a key is requested only if supported authenticated UI/API access cannot be used safely.
