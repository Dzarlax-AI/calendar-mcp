Результат и границы

После разблокировки Apple-аккаунта синхронизация восстанавливается автоматически или одной кнопкой «Возобновить синхронизацию» (Resume sync в текущем английском интерфейсе), используя сохранённые зашифрованные реквизиты. Не требовать пароль для каждого из трёх календарей. Не запускать форму Reconnect при обычной попытке восстановления.

В scope: восстановление проекции событий, отображение ошибки и времени следующей попытки, ручная кнопка. Вне scope: включение приостановленных правил копирования событий, восстановление отключённого Microsoft-аккаунта в legacy-сервисе, смена ключей/паролей, изменение gateway/auth, production-операции.

Проверенные исходные факты

  • Рабочий репозиторий calendar-mcp, ветка codex/google-orphan-occurrence, HEAD 24c8e16. Много существующих незакоммиченных изменений; сохранять их.
  • Прод: три Apple-календаря parked/auth после ошибки около 02:27 по Белграду; позднее живое чтение всех трёх прошло HTTP 200. Google синхронизируется. Историческая первопричина отказа не установлена; пользователь сообщил о блокировке и последующей разблокировке аккаунта.
  • eventsync.fail переводит auth в parked; ClaimDueCalendarSync исключает parked. Редкой перепроверки нет.
  • POST /api/ui/calendars/{id}/refresh уже ставит parked в pending, сохраняя cursor и защищая активную lease. Ответ 202 означает постановку в очередь, а не завершение синхронизации.
  • CalendarPage показывает отдельную кнопку только для degraded. Общий refresh существует. Apple Reconnect в ControlPlanePage открывает форму username/app_password.
  • Пользователь наблюдает три запроса пароля. Точный маршрут и причина трёх запросов пока не воспроизведены; по исходникам refresh пароли не передаёт. Истёкшая сессия приложения отдельно обрабатывается как session_expired.

Согласуемое поведение

  • Для Apple parked/auth автоматически выполнять ограниченную по существующим лимитам попытку чтения каждые 15 минут. Повторное auth сохраняет ошибку и назначает следующую попытку; успешная синхронизация возвращает обычную периодичность. Фиксированный интервал выбран для небольшого изменения без счётчика попыток и миграции.
  • Существующие Apple parked/auth подхватываются новой политикой без ручного SQL. Дедлайн хранится в существующем next_sync_at и переживает рестарт. Другие parked-классы permission/protocol/unsupported не получают автоматических повторов.
  • В строке ошибки календаря показать Resume sync для затронутых доступных для чтения parked-источников. Повторно использовать refresh API; отправлять запросы только для этих календарей. Общее нажатие запускает восстановление всех затронутых выбранных источников без отдельных форм пароля.
  • При нажатии показать «поставлено в очередь», блокировать повторное нажатие на время запроса; показать результат синхронизации после ответа worker. Частичный успех, 409 и неизвестный исход не выдавать за восстановление.
  • Ошибка auth остаётся видимой во время ожидания; показывать следующую попытку и последние успешные данные. Не маскировать устаревшие данные зелёным connected. Обновление статуса страницы ограничено по частоте; без постоянного быстрого polling.
  • Никакого обхода входа в приложение. Истечение сессии требует обычного входа один раз; ошибка провайдера не должна переводить на страницу входа приложения или повторять авторизацию для каждого календаря. Запрос нового app-specific password остаётся отдельным явным действием Reconnect при необходимости.

Риски и восстановление

Пятнадцатиминутные попытки используют сохранённые реквизиты и могут повторять отказ действительно заблокированного аккаунта; периодичность ограничена. Успех ListCalendars сам по себе не подтверждает успешную фоновую синхронизацию. Разные production-версии serve/worker требуют совместного рассмотрения перед будущим deploy. Данные и credential storage не меняются; авторизация исправления отдельных объектов у провайдера этим действием не выдаётся.

Локальный откат — удалить только собственные изменения по сохранённому patch, без reset/checkout поверх чужих правок. Старый worker снова исключит parked. Откат состояния production и любые изменения БД не входят в согласование.

Фактические результаты реализации

  • Политика Apple auth реализована в internal/storage/event_cache.go: ParkCalendarSync сохраняет next_sync_at = now + 15 минут; ClaimDueCalendarSync выбирает только подходящие Apple parked/auth. Использован реальный provider из connection, а не префикс ID. Изменения интерфейса service/storage и миграция не понадобились.
  • EnsureCalendarSyncStates сохраняет parked, причину и deadline при суточном сдвиге окна. Lease/CAS, cursor, credential storage и настройки правил копирования сохраняются.
  • CalendarPage получил Resume sync у ошибки, использующий прежний refresh API; сведения о восстановлении и медленный polling статуса добавлены в lib/calendar.ts. Pending/syncing больше не маскируются собственным stale-флагом, но отдельный устаревший источник сохраняет предупреждение.
