Responsive calendar views

Port the accepted HTML direction into the existing React/FullCalendar client, with mobile Week and Month treated as first-class calendar surfaces rather than squeezed desktop controls.

Current architecture

frontend/src/features/calendar/CalendarPage.tsx owns visible date, selected sources, queries, event mutation, filters, drawers, and the FullCalendar ref. It currently persists one of timeGridDay, timeGridWeek, dayGridMonth, or listWeek in calendar:view. On phones, FullCalendar remains the single canvas; Week gets an 820 px minimum width and horizontal scrolling below 760 px.

frontend/src/styles/app.css provides the responsive toolbar, FullCalendar event styling, sidebar-sheet behavior, and the 1440 px persistent-sidebar threshold. Existing unit coverage asserts the sidebar threshold and event-density helper in CalendarPage.test.tsx.

Desired behavior and accepted direction

  • Desktop (≥1440 px): retain the persistent source sidebar and existing calendar behavior.
  • Laptop/tablet: retain an overlay calendar filter, not a compressed permanent sidebar.
  • Phone Schedule: keep a readable selected-day agenda as the default view.
  • Phone Week: show a genuine, readable three-day time grid around the selected day; changing date keeps the same calendar context.
  • Phone Month: use a full-height month surface inspired by the supplied reference: large month title, weekday row, six rows of days, compact event pills, explicit +N more, and bottom controls. No empty area under a tiny grid.
  • Filters remain an accessible sheet; event click, create, edit, delete, refresh, and provider permissions keep their existing behavior.

Implementation boundary

This is a frontend-only responsive presentation change. It will reuse the existing event query, calendar selection, mutation APIs, event capability checks, and mock data. No backend endpoint, database migration, OAuth scope, provider behavior, real-calendar write semantics, or deployment configuration will change.

Mobile Month will be a small React presentation component fed by the already-normalized EventRecord collection and visible date. It will send date/event actions back through the existing calendarRef and surface state instead of creating a parallel source of truth.

Steps

  1. Extract view/date helpers with explicit timezone-safe day boundaries from the existing event model; write focused tests before using them in Month.
  2. Introduce phone-only rendering selection. Keep FullCalendar as the shared date/navigation authority and preserve the persisted view preference.
  3. Implement the three-day Week grid using FullCalendar configuration/styles where possible; it must show time, readable event names, current/selected day, and event click/create selection.
  4. Implement the dense Month component from normalized events: group by local day, cap visible pills per cell, expose an interactive +N more, navigate or open details on day/event action, and retain source colors.
  5. Implement the phone header/bottom controls and filter sheet affordances without duplicating calendar/provider state.
  6. Apply the smaller audit polish shared by all widths: robust current-day hierarchy, readable event truncation, and clear interactive more-links.
  7. Run typecheck/tests/build and verify local synthetic-data paths in the browser at phone, laptop, and wide-desktop breakpoints.

Implementation result — 2026-08-26

  • CalendarPage.tsx now has timezone-aware day-key helpers and a phone-only Month surface. It groups timed and multi-day all-day normalized events into a Monday-first, six-week grid; keeps two compact, source-coloured event pills per day; exposes keyboard-reachable +N; and routes day, event, filter, create, Today, and next-month actions to the existing calendar and surface state.
  • Phone Week is now a FullCalendar custom mobileThreeDay time-grid view, while the persisted preference remains the standard Week value. The earlier 820 px horizontal canvas applies only to the 561–760 px layout, not phones.
  • app.css adds scoped ≤560 px styles for a full-height Month grid, current-date emphasis, compact event affordances, a sticky bottom control row, and more legible phone Week slots. Desktop and tablet layout rules remain unchanged.
  • CalendarPage.test.tsx adds coverage for timezone-aware timed events, all-day dates, Monday-first six-week Month construction, and event grouping.

Risks and edge cases

  • All-day, multi-day, recurring, timezone-boundary, and overlapping events must not be silently dropped by the mobile Month grouping.
  • Month overflow must be keyboard reachable and must not rely on color alone to identify an event.
  • A custom phone surface can drift from FullCalendar navigation if it owns its own date. The implementation must route every date change through the existing calendar API.
  • FullCalendar custom-view capabilities may not express the intended three-day Week cleanly. If inspection shows that limitation, use a small derived phone grid while keeping date/event authority in the existing page; do not weaken event mutation constraints.

Rollback

Revert the frontend files in this change set. No server-side state is created, so rollback restores the present FullCalendar-only responsive layout immediately.

Open questions resolved for this scope

  • The supplied Month reference is the mobile visual target; it is an inspiration, not a pixel-for-pixel clone.
  • The implementation keeps a full Month mode because it was explicitly requested, despite the phone default being Schedule.
  • “Week” means the validated three-day readable time grid, not a seven-column horizontal-scroll heatmap.

Approval gate

Do not modify production React/CSS files until this plan is explicitly approved. Approval authorizes only the frontend scope above; it does not authorize commit, push, deployment, or changes to real calendar data.
