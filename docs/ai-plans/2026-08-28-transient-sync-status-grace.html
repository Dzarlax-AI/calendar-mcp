Transient calendar sync status grace

Implemented locally; not committed or deployed

Task summary

Do not alarm the user for a short, retryable calendar-sync failure when cached events are available and the worker has already scheduled another attempt. Preserve immediate, actionable warnings for states that do not self-heal.

Inspected current behavior

  • The worker stores status, a safe last_error_code, and next_sync_at in calendar_sync_state.
  • ListCachedEvents reads next_sync_at, but the public event-source response does not expose it.
  • The React summary treats every failed or parked source as an immediate red “N calendar(s) failed” alert. Its polling stops unless a source is pending or syncing.
  • A successful next sync clears the stored error. The production read-only check on 2026-08-28 found all six sources ready and no active quarantined objects.

The grace is bounded by the worker-provided next-attempt time, not a guessed five-minute client timer. No provider payloads, calendar IDs, or unsafe provider reasons will be added to the browser response.

Likely files

  • internal/storage/event_cache.go — retain next_sync_at on the cached source-status value already read from storage.
  • internal/web/api.go — serialize that timestamp in the cached event-source status only.
  • frontend/src/lib/types.ts — model optional next_sync_at.
  • frontend/src/lib/calendar.ts — classify only active scheduled transient/rate-limit retries as syncing; make polling follow that classification.
  • frontend/src/lib/calendar.test.ts and focused API/storage tests — lock down the contract and edge cases.

Implementation steps

  1. Add an optional next-sync timestamp to the storage-to-UI source model and expose it from the cached-events endpoint.
  2. Add one pure frontend predicate for an active retryable source: status === failed, a safe retryable code, and a parseable future retry timestamp.
  3. Use that predicate before the failed aggregate, returning the existing syncing summary for active retries; retain failed precedence for parked/auth/permission/unsupported and expired or unknown retries.
  4. Let eventStatusPollInterval continue polling for active retries, subject to its existing 30-attempt cap. Do not change data fetching, mutations, refresh semantics, provider behavior, or worker retry policy.
  5. Add regression tests for: transient and rate-limited future retry; timestamp passed; malformed/missing timestamp; parked; degraded; and serialized API timestamp.

Impact and limits

This is an additive API/UI contract change with no migration, credentials, authorization, provider mutation, or deployment action. It uses the server's scheduled retry as the source of truth. The UI will still surface a genuine sustained outage; it merely removes the noisy intermediate alert.

Risks, rollback, and open questions

  • A clock-skewed or malformed timestamp must never hide an error; it falls back to the existing failed alert.
  • A burst longer than the client polling cap becomes the existing stale/refetch state rather than spinning forever.
  • Rollback is a normal redeploy of the prior UI/service image; no data migration or cleanup is required.
  • No open product choice remains: the planned distinction follows the agreed “do not show short-term errors” intent while keeping actionable failures visible.

Actual implementation and verification

  • Added next_sync_at from calendar_sync_state to the cached source-status model and serialized it only in the browser event-source response.
  • The UI now identifies an active retry only when the source is failed, its safe code is transient or rate_limited, and next_sync_at is valid and in the future. It presents that state as Syncing and continues bounded polling.
  • Expired, missing, malformed, parked, auth, permission, unsupported, and degraded states retain their previous alert/repair behavior.
  • Regression tests cover future transient/rate-limit retries, expired and malformed timestamps, parked auth, bounded polling, storage propagation, and UI serialization.
