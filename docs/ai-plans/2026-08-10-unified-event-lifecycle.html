Unified Calendar Event Lifecycle

Goal: build a safe, predictable event-management MCP for Google Calendar, Microsoft 365, and Apple CalDAV, with Google as the first complete reference implementation and full recurring-event lifecycle support.

Architecture: introduce a typed V2 domain and application layer between MCP/REST transports and provider adapters. Keep legacy tools as compatibility wrappers, validate per-calendar capabilities before writes, and return structured partial failures instead of silent omissions.

Tech stack: Go 1.25, mcp-go, Google Calendar API v3, Microsoft Graph REST, CalDAV/iCalendar, net/http, table-driven tests, httptest provider fakes.

1. Scope and Planning Decision

The approved design is intentionally broader than one safe implementation batch. This master plan decomposes it into release phases that each leave the service buildable, testable, and rollback-ready. Implementation should pause for a cumulative diff review after every phase.

Included: all review fixes; V2 event types and patches; capabilities; Google list/get/search/create/update/delete/import/move/instances/response behavior; series/single/following recurrence; reminders, colors, visibility, transparency, attachments, Meet, guest controls, extended properties, and Google special event types; Microsoft and Apple alignment where natively supported.

Excluded: ACL, Calendar settings, free/busy, event watch/webhooks, and general calendar-management APIs. These require separate designs.

2. Current Behavior

  • A single calendar.Provider interface exposes five basic operations.
  • MCP and REST duplicate parsing and patch-building logic.
  • Google lists only one page, expands recurring events unconditionally, and sends updates to all attendees for create/update.
  • Microsoft formats local wall time while labeling it UTC and does not follow Graph pagination.
  • Apple returns iCalendar UID but reconstructs mutation hrefs from that UID; fallback failures can appear as empty success.
  • Update DTOs cannot distinguish omitted fields from explicit clearing; Apple ignores attendee updates.
  • An empty API key disables authentication without an explicit unsafe-mode switch.
  • Tests cover date parsing and a small set of provider conversions, but not transports, registry semantics, pagination, recurrence, or error mapping.

3. Desired Behavior and Invariants

  • No notification or invitation is sent unless the caller explicitly requests a supported notification policy.
  • No provider field or operation is silently ignored.
  • No paginated or failed provider response is presented as a complete successful result.
  • Timed recurrence preserves IANA time zone and wall-clock time across DST.
  • All-day end dates remain exclusive; timed and all-day representations cannot be mixed.
  • Apple mutations use the actual CalDAV resource href, not an inferred filename.
  • Mutations support optimistic concurrency through ETag/version where the provider supports it.
  • Legacy MCP inputs remain accepted. Advanced typed behavior lives in V2.
  • following is reported as a composite, recoverable operation, never as a falsely atomic write.

Phase 5 — Recoverable this-and-following

Outcome: clients can preview and execute a split-series mutation with idempotency and explicit recovery.

  • Implement preview that resolves the target occurrence, validates ETag, computes old/new recurrence rules, and reports exceptions after the split that Google will reset.
  • Create the replacement future series with notifications disabled and a private operation marker.
  • Trim the old series with ETag protection using UNTIL or recomputed COUNT.
  • If trim fails, delete the replacement with notifications disabled; if compensation fails, return partial_failure with both IDs.
  • On retry, search for the operation marker before creating another series.
type FollowingRequest struct {

8. Risks and Edge Cases

  • This-and-following is not atomic. Preview, idempotency marker, ETag, compensation, and recovery output reduce but cannot eliminate partial-failure risk.
  • Following resets later exceptions in Google. Preview must enumerate and warn about affected exceptions before mutation.
  • Microsoft notification suppression may be impossible for attendee writes. Safety wins: reject rather than send unexpectedly.
  • Provider recurrence models differ. Strict capabilities prevent lossy best-effort translation.
  • Time-zone names differ between Graph and IANA. Only explicit tested mappings are accepted.
  • Apple Family Sharing remains higher latency. Concurrency is bounded and failures become visible.
  • Google conference creation is asynchronous. A pending conference is a valid result, not a failed Meet creation.
  • Special Google event types have account/calendar restrictions. Capabilities and preflight validation are necessary, but provider permission errors remain possible.
  • Legacy notification behavior changes from “all” to “none”. This is an intentional safety correction and must be documented prominently.

9. Rollback Plan

  1. Keep V2 registration behind a configuration switch until manual QA is complete.
  2. Do not remove legacy tools or routes during this project.
  3. Treat each phase as a deployable rollback boundary; retain the previous image tag, not only latest.
  4. If V2 fails in production, disable V2 routing and redeploy the previous artifact while retaining safe auth/notification fixes.
  5. For a partial following mutation, use returned old/new series IDs and recovery action to remove overlap or complete the trim.
  6. No database migration exists; rollback does not require data transformation.

10. Assumptions and Resolved Questions

  • The product goal is a convenient multi-provider MCP, not a literal wrapper around every Google Calendar resource.
  • Google is the first complete event reference provider; Microsoft and Apple expose truthful portable subsets.
  • V2 tools are preferred over breaking existing MCP schemas.
  • Notification policy defaults to none.
  • Recurrence supports series, single, and recoverable following.
  • Provider writes during QA require a separate explicit confirmation and dedicated calendars.
  • Commits, pushes, PRs, and deployment require separate explicit permission. Phase checkpoints only prepare and show diffs.

Open questions: none blocking implementation. Provider behavior that cannot be determined from local fakes must remain disabled until verified on dedicated test calendars.
