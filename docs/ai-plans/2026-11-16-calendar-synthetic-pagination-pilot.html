Редакция 6. Перенос пагинации в runtime и проверка прав

R0–R4 одобрены пользователем 2026-11-17 и локально реализованы; ограниченное ревью фактического patch/evidence — ACCEPTED. Разрешены указанные runtime-изменения и isolated integration с fake providers, synthetic credentials и одноразовыми SQLite/PostgreSQL. Это отдельное одобрение редакции 6; результаты E0–E3 остаются историческим supporting evidence. Реальные providers/credentials/application DB, commit/push/PR/merge, Gateway, клиенты и rollout требуют своих разрешений. Скрытых provider reads в cached tool не будет.

1. Объём и желаемое поведение

Первый runtime-перенос — Google, summary, cached_weak. Новый additive get_cached_events только в существующем modern catalog. Старые live get_events/get_event, compat, REST/native API сохраняют свои контракты; общий cache/fencing затрагивается только там, где это требуется для недопущения старых прав и поздних записей. Microsoft/Apple detail support нового инструмента не заявляется и не включается; их существующие возможности, discovery и Apple recovery сохраняются. Это осознанное ограничение первой версии на основе E2/E3, а не тихое исключение источников.

Нет нового endpoint/catalog, event corpus, replay/page store, cache subsystem, пула или индекса. SQL-проекция и SQLite eligibility берутся из E3; эксперименты не импортируются runtime-модулем, compile overlays и SyntheticEvidenceForBenchmark не переносятся. Используются настоящие Store methods и обычные migrations. Разделы 1–7 сохраняют согласованный контракт; фактическая реализация, проверки и ограничения зафиксированы ниже в результатах R0–R4.

Регистрация: ENABLE_V2=true + EVENT_READ_MODEL_ENABLED=true + platform Store/cipher + настроенный primary API_KEY + подключённый narrow cached reader. При отсутствии dependency инструмент не регистрируется: modern остаётся с12 tools, с dependency —13. Не ломать старую обёртку Register. /mcp получает инструмент только если его текущий catalog mode — modern; /mcp/compat не получает. В режиме unauthenticated cached tool отсутствует, прочие прежние маршруты не меняются. Env/file-token провайдеры без platform Store не приобретают новые гарантии.

2. Контракт нового инструмента

  • Request: обязательные calendar_ids (1–16 unique canonical platform IDs, каждый ≤1024 UTF-8 bytes), обязательные RFC3339 start/end, end>start, годы1–9999; page_size default25,1–50; optional page_token ≤4 KiB. Unknown fields/duplicates/невалидные IDs — bounded invalid_argument. Даты нормализуются UTC, IDs сортируются до binding. Для v1 нет implicit fan-out: это явное упрощение относительно optional IDs в редакции5. Существующие registry aggregate/imported/exclusion semantics не переопределяются.
  • Scope: любой explicit missing/неподтверждённый/denied/source без sync-state или unsupported provider закрывает весь запрос bounded unavailable/permission error. Не сокращать scope молча и не возвращать title из допустимого поднабора. Кеш недоступен — отказ; не вызывать provider, не начинать sync и не перескакивать в live tool. Пустой результат допустим только для проверенного scope, а не как маскировка неизвестного календаря.
  • Result: items: event/calendar ID, title, start/end с all-day/timezone, status; sources: компактные безопасные freshness/status, observation time, target sync window. Описания/attendees/attachments/raw поля не извлекаются в Go и не передаются модели. consistency=cached_weak, next_page_token, partial, complete. Complete означает конец cached SQL-выборки, не полноту данных провайдера. last_success_at может относиться к degraded sync и не является доказательством полного покрытия. Не выдавать target window за подтверждённое coverage; за пределами настроенного cache window — bounded unavailable, без fallback.
  • Budget:16 KiB фактического SDK CallToolResult вместе с text+structured/escaping/cursor/sources; JSON-RPC envelope/HTTP bytes измеряются отдельно. Page_size — верхняя граница, не обещание числа событий. Остаток обычной summary целиком переносится на следующую страницу. Oversized marker допустим только если summary не вмещается в пустую страницу с обязательным continuation либо SQL summary >32 KiB; marker явный partial с reference/time/reason. Metadata overflow — явный отказ. Повторить реальный mandatory-cursor boundary E2.
  • SQL: максимум page_size+1 eligible rows; master исключается до LIMIT. Timed/all-day strict overlap, NULL, mixed eligibility UNION без дублей; обе сортировки согласованы с cursor: дата участвует только для all-day, затем event_id/calendar_id. Stored scalar byte/type guards — до передачи драйвером. PostgreSQL repeatable-read read-only page tx; SQLite тот же snapshot.32 KiB ограничивает одну передаваемую summary, не всю память SQL executor. Новых index/backfill не планируется.
  • Cursor: stateless AEAD через существующий Cipher с отдельным domain AAD; фиксированы tool/catalog/schema, normalized args, verified caller key/config fingerprints, source receipts/auth revisions, position и абсолютный expiry300s. Один process boot nonce инвалидирует старые cursors после restart без хранилища страниц. API key/config/cipher rotation, изменение scope/прав или tamper — cursor_unavailable; не повторять root query автоматически. cached_weak допускает изменение данных между страницами и не обещает snapshot/replay всего обхода.

4. Минимальная модель прав и OAuth

Два новых bounded metadata поля, без новых таблиц. Выполнена migration 008_cached_detail_authority.sql для обоих dialects поверх исходной007: connections.authorization_revision TEXT NOT NULL DEFAULT '' и calendars.detail_receipt TEXT NOT NULL DEFAULT ''. Revision — server-generated неповторяемый UUID/epoch, а не timestamp или счётчик, который может повториться после delete/recreate ID. Новые connection/Begin/reconnect/revoke получают новый epoch. Legacy empty допускает только старые live пути; новый cached reader требует nonempty epoch и receipt. Receipt ≤1024 bytes, ciphertext transfer для snapshot ≤16 KiB до копирования/декодирования; не хранить ciphertext в cursor или Permit. credential_version остаётся версией формата шифрования, не подменяется revision.

Begin→provider→Complete: под connection lock выпустить новый epoch, pending, закрыть grants/receipts, детерминированно fence все sync generations/leases до удаления старых cache projections/object inventory/repair authorizations; commit до provider construction. Построить verifier из этого snapshot и snapshot-bound token store, не из новой текущей записи после I/O. Собрать полный bounded discovery (до256 календарей/64 страниц, repeated token/duplicate IDs/error/overflow — closed). Complete в одной транзакции проверяет исходный epoch/pending, публикует membership/read-write-recurrence/primary только из общего staged результата. Исчезнувшие/freeBusy/deleted закрыты; empty/all-denied listing корректно завершает verification без открытого grant и без выбора обязательного readable календаря. Не переносить ограничение bootstrap collector E2, оставлявшее такие случаи pending.

Роли и свежий payload: использовать реальный Google accessRole, не ReadOnly/scopes_json. freeBusyReader/none/unknown не разрешают summary details. Owner/writer/reader и документированный writerWithoutPrivateAccess допускаются только с проверенными fake fixtures свежего provider-filtered payload: reader и writerWithoutPrivateAccess не открывают private details. Старый owner title нельзя дополнять в redacted response. Mapping поддерживает произвольное количество календарей в пределах discovery budget, а не только16 query IDs. Primary/capabilities публикуются из одного полного snapshot. Источники: Google CalendarList accessRole и Events list/continuation.

Refresh: initial no-change Save идемпотентен; штатный access/refresh-token update того же authorization context не меняет epoch/receipt и не инвалидирует действующий cursor. Save CAS проверяет captured epoch + expected stored ciphertext, после успеха обновляет собственный expected ciphertext. DB Save получает свежий bounded timeout на саму транзакцию, не бессрочный Background и не уже завершённый context первого Factory.Build. При конфликте не overwrite и не переименовывать старый provider response новой ревизией; вернуть bounded stale-credentials, новый provider строится для следующего вызова без автоматического повторения mutation. Успешный CAS сохраняет новый refresh token; lossless concurrent provider rotation не обещается. Независимые TokenSource API/worker могут выполнить внешние refresh параллельно до DB CAS. Если выигравший токен уже недействителен, не обходить CAS и не переписывать чужую новую ревизию: текущее подключение закрывается и восстанавливается reconnect. Новая межпроцессная refresh-lock система не добавляется. Обнаруженное изменение scopes/identity или auth denial закрывает epoch/receipt и требует новой verification; scopes_json, который сейчас может быть пуст, не считается доказательством права. Допущение «обычный refresh сохраняет authorization context» явно тестируется, а не выводится из совпавшего access token.

Google reconnect без смешивания аккаунтов: replacement обязан содержать собственный refresh token; при отсутствии — bounded re-consent-required до изменения существующего connection/epoch/receipt/cache. Не наследовать previous.RefreshToken из runtime ReconnectOAuth для Google без независимого доказательства того же principal/client/grant; в v1 такого наследования нет. Working account A остаётся рабочим при отклонённом candidate access token B без refresh token. Новый AT/RT комплект из одного OAuth exchange затем проходит snapshot verification и обычный revoke/purge старого контекста; displayName, first calendar и scopes_json не являются доказательством principal. Проверить A/B + missing refresh и нормальный same-account re-consent. Для Microsoft текущее reconnect-поведение не менять без отдельного требования.

Успешный HTTP200 тоже может сообщить смену доступа: Google generated Events.AccessRole сейчас не используется в google/event_sync.go. В новых actual adapter/coordinator paths связать role observation с source, исходными epoch/receipt до применения items. Несовместимая role/видимость (включая owner→reader или writerWithoutPrivateAccess) закрывает прежний receipt/generation до публикации даже пустой incremental page; затем full discovery + свежий refetch, без дополнения старым private title. Missing/unknown AccessRole в Google sync/evidence path — закрыть proof для нового reader и не применять эту страницу как подтверждённый grant; не выводить роль из пустого поля. Тот же observation primitive применить к другим настоящим Google Events.List paths, где role стала известной. Изменение remote ACL до наблюдения по-прежнему не обещается обнаруженным.

Поздние errors и обновление registry: auth/permission invalidation compare-and-set по исходному source/epoch/receipt; старый provider error не закрывает новое авторизованное подключение. Для401/invalid_grant superseded токена в том же epoch дополнительно сверить token/cipher snapshot: ошибку старой версии не считать доказательством отказа текущему token. Возвращается bounded stale-credentials для этого вызова, без replay mutation. Для API registry, уже работающего во время отдельного worker Begin/reconnect/refresh, перед следующим platform-Google provider I/O сверять epoch/token binding с актуальным Store snapshot. При изменении — построить только нужный provider из нового snapshot и compare-and-replace по route под существующим Registry mutex, сохраняя порядок/другие providers. Нужны узкие context-aware resolve/Providers helpers и injected factory callback в existing Registry; это обновление существующего registry, не второй provider cache, watcher или очередь. Проверка охватывает single calls и list/fan-out paths; pending/error source сразу unavailable. Уже начатую mutation не переигрывать; запрос следующего пользователя разрешает новый snapshot, а не новый Permit задним числом для старого response. Legacy env providers остаются на прежнем пути.

Legacy bootstrap: не очищать массово last_verified_at и не считать legacy CanRead доказательством. В existing worker при включённом read model выбрать не более одного connected Google account с legacy readable calendar/пустым receipt за цикл; atomically recheck eligibility + Begin до I/O. Pending/успешно проверенный/empty/all-denied account повторно не захватывается параллельным worker. Для v1 — одна автоматическая попытка на legacy connected account; после failed/cancelled verification статус error/closed, автоматического discovery retry scheduler нет. Восстановление — существующий OAuth reconnect flow; это может продлить недоступность UI/native cache до явного повторного подключения, даже после transient ошибки. Упавший worker с pending verification не перезапускает её циклически: тот же reconnect сбрасывает epoch и зависшие попытки. Использовать existing status/error, не новый dispatcher/queue или дополнительную lease table. Account с нулём календарей не требует proof для выдачи несуществующего scope. Cache tool не ждёт bootstrap, а сразу отвечает unavailable. Проверить параллельные worker/cancel/crash и общую UI/native projection после purge; это ограничение первой версии входит в предлагаемое approval, не скрыто за неопределённым backoff.

Все известные denials: Google current-context auth/invalid_grant закрывает весь account; read-permission loss — конкретный calendar; transient/rate-limit не отзывают право автоматически. Подключить к одному Store invalidation primitive sync fail, live reads/mutations, capability/discovery errors и rule-sync provider errors, сохранив текущие bounded API errors. Delete/reconnect/повторное Begin и поздние results проходят тот же fence; delete может отказать из-за существующих sync rules — не обходить это. Не выдумывать отсутствующий account-disable endpoint; любой фактический status transition и будущий disable обязаны использовать тот же primitive. Apple auth recheck остаётся eligible, Graph/Apple общие capabilities не обнуляются.

Если обычная summary не помещается в остаток уже непустой страницы, завершить страницу и вернуть это событие целиком на следующей. Cursor стоит после последнего реально выданного события, не после lookahead/прочитанных строк. Marker с reference и доступными временем/status допустим только если summary не помещается даже на пустой странице либо сама SQL summary projection превышает 32 KiB; marker означает partial и отдельную причину, не обычную запись. Metadata overflow — явный error, без молчаливого усечения scope. 16 KiB — design cap, не обещание числа tokens.

3. Курсор без накопления страниц

Keyset pagination по существующему SQL order: (start_at IS NULL, start_at, start_date, event_id, calendar_id); последний calendar ID делает исходный неопределённый tie детерминированным. SQLite использует точное scalar SQL значение ключа, PostgreSQL — свой типизированный timestamp/date key; не превращать SQLite TIMESTAMP в новый формат для сравнения на следующем шаге. Seek имеет раздельные timed/all-day ветви с явной обработкой NULL: обычный row-tuple > с nullable start_at/start_date недопустим. На совпадающих starts/IDs и переходе к all-day проверяется полный static union. Этот scope не вводит новую UTC/nanosecond сортировку и не меняет порядок старых readers. Offset не выбираем.

Предпочтительный cursor: authenticated opaque token с последним tuple, expiry 300 s, hash effective args/scope/config и server-verified credential binding; использовать существующий encryption primitive с отдельным purpose/AAD. Курсор не содержит events/pages и не требует cursor/session/replay таблицы или глобального page cache. Max token 4 KiB, identifiers до 1 KiB каждый; обычный размер cursor измеряется отдельно и входит в 16 KiB ответа. Это явное отступление от экспериментального 128-byte locator: практический API не наследует его silently. На E0 фиксируется компактный length-prefixed кодек и проверяется верхняя граница на допустимых IDs, включая Unicode/control characters; JSON escaping не должен неожиданно раздуть cursor. Если кодек не укладывается в cap, пересмотреть представление до исполнения, без скрытого добавления state-store.

Семантика cached_weak: повтор cursor снова читает тот же SQL участок; данные при обновлении кеша могут отличаться. Exact byte replay, общий snapshot, фиксация всех старых страниц и ограничение на суммарные 256 страниц исключены из нового контракта. Токен аутентифицируется и связывается с актуальным credential, args и scope; подмена/expiry/config или scope change даёт CURSOR_UNAVAILABLE, а не restart. Никаких детальных claims об end-user isolation за одним Gateway credential.

4. Нужные ограничения без отдельной платформы

Ключи и небольшая summary формируются bounded SQL projection. Go не получает неограниченный payload для удаления descriptions постфактум. E1 поправка к E0: SQLite/PostgreSQL формируют JSON только из title/start/end/status и проверяют byte length этой summary projection в SQL. В Go передаётся проекция ≤32 KiB; больше — marker с ID/start/end из существующих колонок. Длинный description сам по себе не повод скрывать title. Этот перенос guard с raw payload на summary явно согласован запросом устранить блокер заголовков; прежние правила/результаты E0 сохранены ниже и в его SPEC. SQL/backend стоимость отдельно проверяется: ограничение Go payload не называется total RSS bound. Признак master сейчас находится внутри JSON; byte guard не освобождает SQLite/PostgreSQL от его разбора для WHERE. На E0 сравнивается стоимость oversized master до LIMIT и обычных строк, backend time/bytes (или прямо unknown). Один persisted discriminator допустим лишь при доказанной необходимости; молча перенести фильтрацию masters после LIMIT нельзя.

Сохраняем имеющиеся range indexes. Новый узкий index допускается только если paired EXPLAIN/замер показывает необходимость; четыре paging-колонки, нормализация всех timestamps и обязательная schema 8 из редакции 3 не переносятся. Большая история с редкими overlap проверяется с коротким query deadline: LIMIT/seek не доказывают bounded CPU. Целевой timeout выбирается по локальному измерению обычных запросов до фиксации runtime-контракта.

События и freshness одной страницы читаются в короткой read-only transaction (PostgreSQL явно Repeatable Read, SQLite snapshot); транзакция закрывается до отдельной свежей проверки прав перед release. Для начала используем существующий body cap и при необходимости локальную nonblocking квоту тяжёлого cached SQL read с deadline. Общий limiter для modern POST не входит в минимальный scope: cached/slow client не должен занять слоты live/mutation tools. Граница SDK parsing/serialization остаётся известной общей стоимостью; transport-wide RSS hard bound не заявляется. Общий HTTP limiter допустим только как отдельное доказанное требование с bounded write/slow-reader и availability tests; новая очередь/планировщик не нужны.

5. Права — существующий обязательный prerequisite

До появления нового инструмента нужно закрыть finding Astra в текущем discovery: успешный полный список атомарно отзывает исчезнувшие календари, а freeBusy/downgrade не подтверждает право выдавать старые title/details. Errors/partial discovery не публикуют неполный membership. Используем текущие connection/calendar records и точечный reconciliation, без новой системы ACL. В E1 на существующих таблицах проверен консервативный протокол: начало verification атомарно закрывает чтение, удаляет старые cached projections, сбрасывает cursor/object/lease state и повышает существующую sync generation. Полный staged результат открывает только подтверждённые grants; regrant требует новой provider-filtered проекции. Старая discovery/cache write отклоняется по generation и ciphertext, а Capture/Validate обрамляют выдачу страницы. Это решение пилота, не изменение всех реальных runtime writers. До переноса этих условий и подтверждения реальных provider signals runtime-план не implementation-ready.

E0 явно называет проверяемый authority signal для каждого провайдера: Google сохраняет AccessRole без схлопывания freeBusy/reader; Graph CanEdit не является доказательством чтения приватных деталей; Apple path/name не подтверждают CalDAV detail-read privilege. Для Graph/Apple нужен подтверждённый доступный сигнал, а не предположение. Старые/неподтверждённые grants закрыты для нового cached summary. После изменения доступа pre-change payload не показывается до успешной повторной проекции под подтверждёнными правами. Tests: successful A+B→A, full-detail→freeBusy/restricted, failed discovery, concurrent credential update/discovery, возврат прав со старым кешем; первый вызов и continuation должны отказать в прежних данных. Upstream права между discovery неизвестны — контракт говорит last-confirmed local authority. Source target sync window и фактическое покрытие различаются; pending/degraded/parked не означают fresh/full. Даже title/time требуют разрешения.

3. Новый контракт и consistency

Предлагаемый контракт: calendar-cached-pages/1.0.0, отдельные JSON schemas и типы. Экспериментальный managed-pages/0.1.0 и существующий calendar.Page не меняются. Вход: обязательные RFC3339 start/end, необязательные calendar_ids (до 16), page_size (default 50, 1–100), cursor. Неизвестные поля отклоняются; view фиксирован expanded, deleted=false, projection=full. Диапазон положительный, не более 366 дней; выход за фактическое sync window отражается в metadata, не вызывает live fetch.

Выход: version, consistency=cached_weak, observed_at, фиксированное имя sort contract, items (полный EventV2 либо oversized marker), continuation, coverage и source metadata: canonical calendar ID, provider, status, stale, last_success_at, next_sync_at, covered window, конечный error code. has_more=false означает исчерпание доступного обхода; coverage.complete остаётся false в cached_weak. Ready/fresh/covered отражаются отдельно по каждому источнику; missing/pending/failed/parked/degraded/expired window не превращаются в пустой полный ответ.

Начальный режим — короткая read transaction на страницу. Внутри неё согласованы events и freshness; между страницами синхронизация может менять данные. Событие, переместившееся за границу ключа, может быть пропущено/повторено; source set фиксирован с первого запроса. Общий upstream или traversal snapshot не обещается. Удерживаемая WAL/MVCC transaction на 300 секунд не выбирается: она занимает connection и удерживает историю. Её добавление либо revision-fenced snapshot — отдельное решение с проверкой всех mutation paths.

Порядок нового инструмента: timed events сначала по нормализованному UTC start с фиксированной точностью до наносекунд; затем all-day по ISO date; tie-breakers — canonical CalendarID, EventID с бинарной/C collation. Это отдельный order contract; all-day не получают вымышленный timezone. Порядок существующих live/native/UI ответов не меняется.

Пустой calendar_ids разрешает только connected/readable календари из SQL; max 17 metadata rows позволяет отказать при scope >16 без event fetch. Exclusions/imported policy применяется к aggregate по canonical и provider reference, эквивалентно текущему fan-out; explicit IDs обходят exclusions. Legacy reference разрешается через SQL только при однозначном совпадении, затем фиксируются canonical IDs. Нет dedup по iCalUID. Запрет/unknown explicit calendar даёт общий bounded access error, не частичный список.

4. Ограниченный SQL reader и миграция

Предлагается additive schema 8: paging metadata page_kind, page_start, page_end, instance_kind и частичный индекс для non-deleted/non-master записей по (calendar_id, page_kind, page_start, event_id). UTC key для timed хранится в одном фиксированном текстовом формате; all-day использует отдельную группу и ISO date. Common upsert поддерживает метаданные; tombstones/repair/full-sync sweep проверяются на согласованность. Миграция backfill читает SQL-extracted start/end date/date_time и instance kind ограниченными batches, с byte guard на scalar fields (до 128 B для времени, 32 B для kind), не декодирует полные EventV2 в Go; index строится в той же миграции. Ключи выводятся из исходных JSON timestamp strings, чтобы PostgreSQL microsecond storage не потерял наносекунды. Новый reader применяет timed overlap к page_start/page_end; all-day сохраняет ISO-date overlap с UTC day-boundary правилами текущего cached reader. Некорректные данные приводят к явному отказу миграции, без тихого пропуска. Отсутствие paging metadata у eligible row после миграции даёт явный UNAVAILABLE, не пустой успешный ответ. Schema 8 применяется общей migration-процедурой при запуске с БД независимо от endpoint opt-in; feature flag управляет каталогом, не версией БД.

Reader выбирает ограниченные keys по каждому из ≤16 календарей: максимум page_size+1 на источник, затем общий merge только метаданных. Seek сравнивает полный tuple (kind, start, CalendarID, EventID), включая постоянный CalendarID конкретного источника; одноимённые event IDs разных календарей не смешиваются. Payload читается по выбранным primary keys — максимум page_size+1, в той же короткой транзакции. SQL проверяет UTF-8 byte length до передачи payload драйверу: SQLite length(CAST(payload_json AS BLOB)), PostgreSQL octet_length(payload_json::text). Выше 32 KiB возвращаются metadata и oversized marker без большого payload в Go; фактическая SDK-сериализация остаётся окончательной проверкой. Identifier metadata также ограничены: input IDs ≤2048 UTF-8 B, oversized stored IDs вызывают bounded error до выдачи ключей, а не молчаливое усечение.

Проверки EXPLAIN должны показывать scoped index seek на следующей странице без полного ORDER BY payloads. Наличие LIMIT само по себе не считается доказательством bounded scan/CPU. No OFFSET для этого reader. Все алгоритмы и границы проверяются на SQLite и PostgreSQL; копирования пилотного SQLite expression index недостаточно.

5. Курсор, replay, права и память

Случайный непрозрачный handle 256 bit, ≤128 ASCII, absolute TTL 300 s. In-memory state хранит frozen request/scope/sort/budgets, keyset position и уже выданные serialized pages для exact replay, включая terminal page; root request replay не обещается. Это ограниченный transient cursor/replay state поверх существующего event store. Данные будущих страниц читаются из SQL; полного второго corpus или disk spool нет. Повтор страницы сохраняет её observed_at/freshness as-of; новые страницы читают текущее состояние. Процессный restart/expiry/eviction возвращает CURSOR_UNAVAILABLE; нет скрытого restart/fallback.

Auth middleware создаёт server-verified credential identity и передаёт её через SDK context; raw key, token и клиентские identity headers не сохраняются/не логируются. Primary и legacy credentials изолированы, rotation/restart инвалидируют state. Bind включает credential identity, catalog/path/tool/schema, эффективные args, resolved scope/exclusions/config и order. Calendar не может различать конечных пользователей, использующих один upstream credential Gateway: изоляция здесь по проверенному Calendar credential, отдельные Gateway подключения/ACL — вне текущей реализации.

На новой странице и replay повторно проверяются текущие connected/readable/selected calendars и конфигурация; изменение scope/доступа инвалидирует обход целиком. Auth выполняется до SQL/replay disclosure и повторно перед release ответа. В cached mode анонимный доступ запрещён; NATIVE_APP_TOKEN/READ_ONLY_TOKEN не дают MCP access. Одновременные вызовы одного cursor делят один результат либо получают отказ до DB work; разные cursors не сериализуются глобальным engine mutex.

Предлагаемые лимиты: 4 одновременно строящихся страницы на процесс; пятый вызов — RESOURCE_EXHAUSTED до SQL. До 128 active traversals, 256 pages/traversal, 16 MiB/traversal и 48 MiB/process на сохранённые serialized replay bytes и учтённые metadata; резерв page/state до query. Итоговый SDK CallToolResult (text+structured, compact JSON) ≤48 KiB; JSON-RPC overhead измеряется отдельно. TTL cleanup и Close освобождают state; отменённая транзакция закрывается сразу. Эти квоты не называются RSS hard cap. При нехватке budget нет silent truncation или выдачи некорректного continuation.

Форма токена и replay

Основной synthetic путь — непредсказуемый 256-bit opaque handle с in-memory state. Альтернативный spike — authenticated encrypted state token, только если всё состояние помещается в 128 ASCII символов; иначе bounded отказ, без поднятия cap. Обычный signed plaintext/base64 JSON не подходит из-за раскрытия query/provider tokens. Внешние ключи и production key lifecycle не нужны: ключи только случайные одноразовые в fake процессе.

Encrypted token не устраняет серверное состояние автоматически: при weak provider повторный fetch может изменить страницу. Для точного replay требуется сохранённый результат или доказанная воспроизводимость на общем R, без нового provider-вызова. Last-page-only cache несовместим с повтором любого ранее выданного cursor до expiry; это не допустимая незаметная оптимизация. Учитывать всю принятую replay window либо отдельно предлагать изменение контракта.

TTL абсолютный, не продлевается чтением; restart/eviction/подмена/foreign identity возвращают bounded отказ без объяснения binding. Конкурентные одинаковые cursors разделяют один materialized outcome либо второй запрос отклоняется до dispatch. В fake scheduler проверить revocation между admission, provider completion и response release: после отзыва данные не выпускаются. Это испытание алгоритма на fake authorities, не production security acceptance.

5. Оценка памяти и нагрузки

Вместо одной цифры HeapAlloc собирать кривые: первый результат, середина traversal, steady replay, максимальное число idle traversals, expiry/cancel/cleanup. Reference aggregate и каждый кандидат запускаются в разных свежих subprocesses на одном seed; полный expected corpus не хранится внутри измеряемого worker.

Предварительная модель, не измеренный результат

M_peak ≈ M_runtime + M_provider_fetch + M_collect/sort + M_page_encoding
         + M_retained_cursor/replay + M_inflight_concurrency

A: retained_data ≈ C × S × P × decoded_record_size + replay + indexes
B: retained_data ≈ C × N × decoded_record_size + replay + indexes
C: retained_data ≈ C × (S_paged × P + N_eager) × decoded_record_size + replay

replay_bytes ≈ Σ фактически сохранённых materialized результатов и индексов
decoded_record_size / JSON_bytes и число одновременно живых копий измеряются.

Пример только для масштаба: 10 000 записей с body 1 KiB — 9,77 MiB одного сырого body без Go objects, IDs, recurrence/attendees, сортировки, JSON и replay. При S=16 и P=64 тот же body для head/page buffers — 1 MiB до накладных расходов. 256 сохранённых MCP-страниц по 48 KiB — ещё 12 MiB на traversal; четыре таких replay окна — 48 MiB. Эти оценки нельзя выдавать за RSS или суммировать с уже учтёнными shared buffers дважды.

Предлагаемые предохранители эксперимента

Начальные лимиты для проверки поведения, не найденные production settings: retained state до 16 MiB на traversal и 48 MiB глобально, до 256 materialized pages на traversal; diagnostic target peak RSS ≤192 MiB на worker, остановка supervisor при наблюдаемом RSS >256 MiB или wall-time >30 s. Политика admission резервирует byte accounting для replay/буферов до нового dispatch, а не только проверяет len готовой страницы. При достижении квоты — RESOURCE_EXHAUSTED, caller сохраняет уже принятые данные как partial, без автоматического root replay. Ранее гарантированный cached replay не выкидывается ради нового запроса.

RSS polling не является строгим cgroup cap: краткий overshoot возможен. Если платформенный high-water/guard недоступен, так и отметить и не заявлять process memory gate пройденным. GOMEMLIMIT может быть отдельным GC-spike, но это мягкий runtime target, не hard enforcement. Docker/cgroup и Linux/amd64 production gate сюда не входят.

Большие matrix cases намеренно могут не поместиться в лимиты. Считается проверенным корректный отказ до неконтролируемой работы, а не успешное перечисление любой ценой. Reference aggregate запускается с тем же supervisor; если он остановлен, expected corpus для корректности создаётся отдельным независимым способом вне memory worker, и это ограничение сравнения показывается явно.

8. Риски, условия остановки и rollback

  • Слишком сильный контракт: fixed replay + weak providers + ограниченная память могут оказаться несовместимы для требуемого диапазона. Не скрывать проблему за eviction. Отчёт предлагает bounded отказ или отдельно согласуемую contract delta.
  • Unsorted/eager fetch: корректный порядок может требовать полного набора до первой страницы. Пилот должен показать этот пик, а не перенести allocation в fixture setup вне измерения.
  • Read model вместо direct path: существующий UI cache не использовать как готовый snapshot; для него другое назначение/согласованность, и он вне scope.
  • Dirty baseline: до выполнения повторно сверить relevant sources и hashes. Изменение checkout сторонней работой не откатывать; воспроизводимость помечается по фактически использованным inputs.
  • Неполные измерения: unavailable RSS, пропущенный peak, killed worker и отсутствующий high-water обозначаются явно. Нельзя на их основании говорить «память безопасна».
  • Новый consequential выбор: если для пилота нужна правка runtime, настоящая source интеграция, изменение общего envelope или права на сеть — остановить только зависимую работу, представить дельту; не расширять scope автоматически.

Rollback: отменить только созданные этим пилотом процессы, удалить только принадлежащие ему временные binary/cache/profile и новый каталог после сохранения отчёта по желанию пользователя; убрать/исправить execution record в этом плане. Не делать checkout/reset/stash чужих dirty-файлов. Поскольку runtime, registry, БД и production не меняются, сервисный rollback и data migration не нужны.
