Implementation Plan: Apple Read-Model Recovery

Implemented locally; production canary still requires approval

Task summary

Make Apple read-model synchronization resilient to malformed individual iCalendar resources without deleting the last valid snapshot or falsely reporting the source as ready. Warnings accumulate across the complete attempt, including multi-page syncs.

Base revision: 58dcadc50fad4ec3983c8cb234b0d11dbef25107

Current behavior

  • appleSyncMembers errors currently fail the whole Apple page with protocol.
  • The coordinator parks protocol failures and applies no valid sibling objects.
  • Production direct reads returned valid events while the cache remained empty for the affected source.

Desired behavior

  1. Apply valid objects from the attempt.
  2. Mark the attempt recoverable with the existing public failed/protocol source status.
  3. Do not advance the provider cursor or sweep old generations, even if a later page is clean.
  4. Keep unresolved-object membership intact and retry from the unchanged cursor.
  5. Only a later complete attempt can transition the source to ready; the retry state must be claimable when due.

Implementation steps

  1. Extend EventSyncPage with per-page recoverable warnings and accumulate them across RunOne.
  2. Add an atomic storage path that applies valid rows but preserves cursor/generation and records internal retryable degraded/protocol status, exposed publicly as failed/protocol.
  3. Change Apple replacement/incremental parsing to isolate only typed object parser failures; keep HTTP/auth/transport failures fatal.
  4. Add tests for multi-page warnings, retryable state claiming, no-master recurrence data, cursor preservation, and no-sweep behavior.
  5. Add an opt-in Postgres parity fixture and run a canary only after explicit deployment approval.

Risks and mitigations

  • Stale unresolved-object data: retain it but expose the existing failed/protocol status and retry.
  • Accidental sweep/cursor advancement: enforce with transaction tests.
  • Retry storms: current Apple retry is one-minute based rather than exponential; monitor fetch volume during canary.
  • Direct/read-model drift: require production-shaped parity before canary.

Rollback

  1. Disable EVENT_READ_MODEL_ENABLED for both calendar-serve and calendar-worker.
  2. Stop the worker if retry volume is abnormal.
  3. Keep additive schema and rows for diagnosis; do not drop tables or reset provider cursors.
  4. Return to direct-provider reads and redeploy the previous immutable image only with explicit approval.

Open questions

  • Expose the existing generic failed/protocol status initially; do not expose Apple object paths.
  • Use the existing one-minute Apple retry base initially; tune after canary request-volume evidence.
  • No webhook or migration work is required for this fix.
