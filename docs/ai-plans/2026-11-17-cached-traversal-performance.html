Почему полный обход стал медленнее

17 ноября 2026 · Revision 1 · Диагностика завершена · Implemented: согласованные шаги A–C выполнены и проверены

Главная устранимая причина на SQLite — JSON-проекция до LIMIT. На PostgreSQL — повторный просмотр диапазона и цена отдельных проверок прав. Новых кешей, индексов, миграций и расширения пула этот план не предусматривает.

1. Объём и границы

Запрос: объяснить замедление полного обхода и найти ускорения без новых кешей и расширения пула. На этапе диагностики выполнены разбор сохранённых фаз R6, отдельные синтетические SQL-эксперименты и один SDK-обход SQLite без фоновой нагрузки; тогда все 159 файлов исходного R6 manifest совпали по SHA-256. После согласования внедрены шаги A–C; результат приведён в разделе9.

Checkout: calendar-mcp, ветка codex/google-orphan-occurrence, HEAD 24c8e163b7e301040922f29b5f39ace150e3083d. Существующий грязный checkout и прежние результаты сохранены. Временный PostgreSQL после диагностики остановлен. Реальные провайдеры, credentials, прикладная БД и production не использовались.

Цель предлагаемого внедрения: сократить повторную работу каждой страницы, сохранив порядок, курсоры, отзыв прав, лимиты 16 KiB/32 KiB и ограниченный Go working set. Полный обход остаётся последовательностью страниц; равенство скорости с одной неограниченной выдачей не обещается.

Это медианы трёх полных обходов R6 с синтетическими UI-чтениями и sync-записями на том же пуле. Baseline — тестовая SDK-обёртка полной Store-выдачи, а не прежний production MCP-контракт. Первая страница имеет отдельные 20 парных замеров; их нельзя смешивать с полными обходами.

Каждая страница заново проверяет аргументы и права, выполняет SQL, пакует ответ и проходит SDK/HTTP. На SQLite это три получения соединения/транзакции: начальная authority, чтение, финальная authority. Число страниц ограничивает полный SDK-ответ 16 KiB с text и structured представлениями. Поэтому page_size=50 оставляет те же 16 страниц для 400 обычных событий и 34 страницы при 16 источниках: повторяемая source metadata занимает значительную часть бюджета.

На 4000 событиях R6 переносит около 2,55 MB SDK-результатов за обход. Рост page_size без изменения контракта не решает проблему и может увеличивать число прочитанных, но не выданных строк: wide/25 декодирует около 852 строк для 400 результатов, wide/50 — около 1618 строк.

Источник: исходный R6 отчёт; пересчёт фаз: phase-analysis.json.

Проценты — суммы длительностей по трём полным обходам, делённые на сумму клиентских WalkMS. SQL событий входит в ReadNS; суммировать его с ReadNS нельзя. Authority включает ожидание пула, транзакцию и metadata. Остаток включает SDK/HTTP, клиентские marshal/unmarshal, проверку и хеширование, планировщик; это не измерение чистого сетевого времени.

В новом одиночном SQLite SDK-прогоне без фоновой нагрузки 4000 событий заняли 5,881 с: SQL событий 5,619 с, начальная authority всех страниц 30,18 мс, финальная 17,57 мс. Значит, дорогое начальное authority в R6 связано главным образом с конкуренцией. Но даже без неё SQL остаётся медленным.

Фон R6 — один цикл каждые 5 мс, который последовательно читает полные cached events за час и пробует sync-запись. Это стрессовая синтетика, не измеренная частота production-запросов. Для authority отдельного таймера ожидания нет; точную долю ожидания внутри неё имеющиеся фазы не дают.

4. Подтверждённый дефект SQLite

В event_pages.go CTE selected AS MATERIALIZED содержит JSON-проекцию и scalar guards вместе с ORDER BY/LIMIT. SQLite 3.53.3 вычисляет проекцию до отбора top-N. Покрывающие индексы range-веток используются, однако внешний запрос повторно просматривает диапазон и сортирует его на каждой странице.

Кроме проекции, master JSON-проверка в текущем плане идёт раньше cursor predicate: даже в конце обхода она обрабатывает 4000 строк. Порядок предикатов в изолированном SQLite-эксперименте уменьшил число этих проверок в середине до 2000, в конце до 25. Это поведение текущего движка, а не универсальная гарантия SQL.

Count probes отделены от таймингов. Корпус — timed events с 512 байтами description; смешанные/all-day, malformed и jumbo-варианты этим экспериментом не проверены.

Доказательства: тайминги и EQP, счётчики вычислений, SQL harness.

5. PostgreSQL: другая оптимизация

В реальном EXPLAIN ANALYZE текущего SQL узел Result с JSON-проекцией получает уже 26 строк после top-N Sort. Перенос SQLite-исправления на PostgreSQL без оснований не нужен. Запрос при этом всё ещё читает диапазон 4000 строк для top-N; разделение timed/date keyset-веток — отдельная возможная работа.

ValidateAuthorityTickets делает по запросу на каждый из максимум 16 источников в одной свежей read-only repeatable-read транзакции. SQL-микрозамер на 16 корректных синтетических grants, включая begin/commit: медиана 0,876 мс для 16 запросов против 0,185 мс для одного запроса. Это 4,74× для данной проверки, а не для всего обхода. В R6 wide эта фаза занимает 25,7%; устранение большей части её стоимости даёт ориентир около 20% общего времени при неизменных остальных фазах, но это ещё не end-to-end замер.

Пакетный вариант соединяет явный набор expected tuples с connections/calendars/sync-state, проверяя те же revision, receipt, статус, can_read и auth/permission fence. Эксперимент проверил только корректные grants; негативные случаи обязательны при внедрении. Сырые PostgreSQL-замеры.

7. Проверки, риски и откат

Уже выполнено: сравнение 159 source hashes; пересчёт фаз из 24 R6 speed cases; SQLite SQL parity трёх измеренных обходов на вариант после прогрева; подсчёт JSON-вычислений в начале/середине/конце; один текущий SDK-обход без фона; PostgreSQL EXPLAIN и authority microbenchmark. Старые raw evidence не изменялись.

После реализации запланировано: целевые storage/cachedpages/mcpserver race-тесты, PostgreSQL integration, затем полный Go race/vet/build при приёмке двух взаимодействующих runtime-изменений. Синтетические boundary cases: одинаковые timestamps/IDs между источниками, timed/date смесь и переход, master и jumbo-master до LIMIT, malformed scalars/JSON, oversized markers, 1/16 источников, page_size 25/50, все источники отзыва/ошибок, дубликаты tickets.

Сохранить after-Pack revoke barrier, expiry, no-skip cursor parity, 16 KiB SDK и 32 KiB transfer bounds, covering range UNION, single-slot release, cancellation и slow-writer checks. Изменённые SQL-варианты не считаются корректными по одному dense-корпусу.

Приёмка производительности: ускорение SQL dense SQLite и полного SDK-обхода относительно свежего до-прогона; сокращение round trips финальной authority до одного и улучшение wide PostgreSQL. Зафиксировать медиану и разброс отдельных парных полных обходов, не объявлять p95 по трём samples. Сохранить прежние first-page SLO ordinary/wide C1 ≤50 мс и C4 ≤100 мс. Проверить natural-GC RSS и большие payloads: MATERIALIZED CTE может держать raw payload в SQL executor; Go transfer bounds не доказывают жёсткую границу памяти SQL.

Если целевой выигрыш не воспроизводится или нарушается контракт — остановить соответствующий шаг, не расширять scope автоматически. Откат: убрать только принятый diff этого этапа поверх сегодняшней dirty baseline, сохранив R6 и чужой WIP. Нет миграций или production-отката.

8. Следующие возможности и gate

Следом по профилю: разделить timed/date keyset SQL и ограничить сканирование курсором через существующие индексы; уменьшить повторное декодирование невыданных строк при byte-limited page; сократить повторные сериализации Pack/handler. На dense SQLite Pack занимает лишь 0,4% — начинать с него невыгодно; на wide PostgreSQL 13,2% делает его более интересным.

Объединение initial authority и data-read в одну read-сессию может убрать дублированную metadata и один вход в пул, но требует отдельного контракта владения соединением. Сессия должна закончиться до Pack, а финальная проверка — остаться свежей после Pack. Удержание единственного SQLite-соединения через Pack способно блокировать конкурентный отзыв прав; оно исключено из первого этапа. Смена частоты фоновых UI-чтений также исключена.

Gate / approval: 17 ноября пользователь явно согласовал внедрение SQLite-оптимизации и пакетной проверки прав по этому плану, включая сравнение полного обхода до/после. Разрешены шаги A–C, локальные синтетические проверки и обновление этого документа. По AGENTS.md изменения auth/SQL runtime требуют HTML approval plan до реализации. Commit, push, PR, merge, deploy и real-data действия требуют отдельного явного разрешения.
