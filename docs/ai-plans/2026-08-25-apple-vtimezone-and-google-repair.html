Apple VTIMEZONE compatibility and explicit Google event repair

Approval required before implementation

Task summary

Accept Apple Calendar resources whose non-IANA TZID is defined by an embedded VTIMEZONE, and make the existing operator-only Repair action able to repair one narrowly-defined malformed Google all-day event.

Observed current behavior

  • Apple sync decodes the uploaded iCalendar object, then calls Prop.DateTime(nil). The library calls time.LoadLocation(TZID); it cannot resolve Apple’s GMT+0100 despite the resource defining that timezone in VTIMEZONE. The whole resource is quarantined as protocol.
  • Google sync isolates malformed events and stores a reason such as invalid_time_range. Repair currently only refetches the event, so an all-day event with identical start.date and end.date remains quarantined.
  • The diagnostics repair endpoint is already authenticated, CSRF-protected, and schedules an object-level repair. It does not currently disclose or authorize a provider-data mutation separately.

Desired behavior and safety boundary

  • Apple: parse a matching custom fixed-offset VTIMEZONE such as GMT+0100, then materialize the event with the correct offset. Do not rewrite Apple data.
  • Google: only when an operator invokes Repair, and only for an all-day event whose sole fault is start.date == end.date, set end.date to the following calendar day. Re-fetch and project it only if the corrected object validates.
  • No automatic mutation during normal sync. Timed events, missing dates, reversed ranges, recurrence semantics, and every other provider reason remain quarantined and require manual repair.
  • The repair result must show whether the provider object was corrected, was unchanged, conflicted, or remains quarantined. Cached events remain visible throughout.

Likely files

  • internal/apple/event_sync.go and a focused Apple helper — resolve custom VTIMEZONE before event date-time parsing and preserve an actionable reason.
  • internal/apple/event_sync_test.go — exact supplied Apple-style resource, plus unsupported/missing timezone definitions.
  • internal/google/event_sync.go — explicit, ETag-aware all-day correction in RepairEventSyncObject, followed by re-fetch/validation.
  • internal/google/event_sync_test.go — safe correction, no mutation for other invalid ranges, Google conflict/error behavior, and successful projection.
  • internal/calendar/event_sync.go, storage, and internal/web/ only if a new repair outcome/reason is needed to present mutation status accurately.
  • frontend/src/... — only if the existing Repair feedback cannot distinguish corrected versus merely queued/still quarantined.

Implementation steps

  1. Add a calendar-level timezone resolver for a resource’s VTIMEZONE. Initially support only definitions with one unambiguous fixed UTC offset; retain a typed unsupported_custom_timezone reason for complex transition rules rather than guessing.
  2. Use that resolver for Apple event and recurrence time parsing in the sync path; validate start/end as before and continue isolating a bad object from its calendar siblings.
  3. Classify Google repair eligibility strictly: date-only start/end, identical dates, non-cancelled event, and no unsupported event form. Use the current ETag/conditional update so a concurrently edited event is never overwritten.
  4. Perform the one-day end-date correction only in the already explicit operator repair flow. Re-fetch after the write, re-run the normal window validator, and return a truthful object-repair outcome.
  5. Expose a concise repair status in diagnostics, without exposing raw provider payloads outside the existing allowlisted detail endpoint.
  6. Update this plan with actual files, test evidence, limitations, and deployment result after implementation.

API, permissions, and deployment impact

The browser API remains the same Repair endpoint, but its Google branch can now perform a narrowly scoped external write. It remains protected by Authentik, the diagnostics operator allowlist, and CSRF. No database migration is expected. The deployed worker needs the existing Google OAuth scope to update events; a permission failure is reported without retrying or modifying cached data.

Risks, limitations, and rollback

  • A VTIMEZONE with daylight transitions cannot be represented safely as one fixed offset. It will remain quarantined with an explicit reason until a full transition-aware resolver is added.
  • Automatic Google correction is intentionally confined to an explicit repair click and an exact malformed all-day shape. ETag conflict, auth failure, or an unexpected post-write representation leaves the object quarantined.
  • Rollback is an immutable-image pin rollback. Google changes already accepted by Google are user data and cannot be undone by deployment rollback; the repair audit/result must identify that a correction occurred.

Open questions

  • Is fixed-offset custom timezone support sufficient for the current Apple failures, or should transition-aware VTIMEZONE support be part of this change? Proposed safe scope: fixed-offset now, typed quarantine otherwise.
  • Should diagnostics show a separate confirmation dialog before a Google provider write? Proposed scope: no extra dialog because Repair is already an explicit authenticated action, but label its outcome as “corrected at provider”.

Implementation record

  • Implemented Apple fixed whole-hour VTIMEZONE normalization in internal/apple/timezone.go, and applied it before sync validation and ordinary recurrence materialization. GMT+0100 becomes the valid IANA zone Etc/GMT-1; the event instant remains +01:00.
  • Unsupported fractional offsets, duplicate/missing definitions, and transition-aware zones remain quarantined with unsupported_custom_timezone.
  • Implemented Google repair in internal/google/event_sync.go: only an explicit repair of a default, non-recurring, date-only event with equal dates sends a conditional PATCH for end.date = start.date + 1 day, with notifications suppressed; it then refetches and validates before projection.
  • Added focused Apple and Google regression coverage. Local Go package tests, web tests, go vet ./..., frontend tests/typecheck/build, and git diff --check passed before the final Apple read-path normalization change; Apple package tests and diff check passed again after that change. Full final verification remains required before commit/release.
