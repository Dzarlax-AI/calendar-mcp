План: исправление ошибок фоновой синхронизации календарей

Нужно явное approval до реализации

1. Краткое резюме

Сначала напрямую выкатить небольшой диагностический hotfix без PR, чтобы worker перестал скрывать реальные причины ошибок. Затем на основании production-данных подготовить один большой PR с исправлениями Google sync, Apple protocol/degraded-поведения, retry/backoff и наблюдаемости.

Граница первой фазы: только безопасное улучшение диагностики и ограничение шумных логов; не менять credentials, календарные данные или sync state вручную.

2. Что подтверждено сейчас

  • calendar-serve и calendar-worker работают и healthy на digest sha256:c919ac44….
  • За 30 минут worker записал около 343 сообщений calendar event read-model sync failed, примерно раз в 5 секунд.
  • Лог печатает только category=%T, поэтому наружу виден бесполезный *errors.joinError.
  • Все три Google calendar sync state сейчас failed/transient; один Apple state — degraded/protocol.
  • Apple adapter получает CalDAV HTTP 500 для одного календаря и применяет существующую защиту «force 207»; остальные Apple calendars sync проходят.
  • Google connection остаётся connected; значит проблема фонового event-sync отделена от OAuth GUI-потока.

3. Желаемое поведение

  • Каждая ошибка sync логируется с безопасными категорией, provider, canonical calendar ID в редактированном виде, error code, retry decision и correlation/run ID; credentials, tokens и payloads не логируются.
  • Ошибки Google API различаются как auth, permission, rate limit, transient и protocol; для каждой категории применяется предсказуемый backoff.
  • Один проблемный календарь не создаёт глобальный busy-loop и не скрывает успешную синхронизацию остальных.
  • Apple protocol/degraded calendar либо получает корректный bounded retry/parked state, либо явно отображается в UI как stale/degraded с понятной причиной.
  • Worker остаётся healthy при ошибке отдельного provider, но alert/операционный сигнал становится actionable.

4. Фаза A — диагностический hotfix без PR

  1. В internal/runtime/worker.go заменить логирование только типа на безопасное структурированное сообщение с %v и классифицированными полями; не включать raw OAuth/API payload.
  2. В internal/eventsync/service.go сохранить исходную причину при оборачивании ошибок (через %w или typed error), чтобы worker видел provider/API code, а не только общий ErrProviderFailure.
  3. Добавить focused tests на сохранение причины и отсутствие секретов в диагностическом сообщении.
  4. Запустить локальные тесты, собрать CI image, выкатить immutable digest напрямую в production без PR.
  5. После rollout собрать 10–15 минут логов и таблицу calendar_sync_state; только эти данные использовать для Фазы B.

Ожидаемый результат: вместо *errors.joinError появится конкретный Google HTTP/API reason или точная ошибка Apple parser/CalDAV.

5. Фаза B — большой PR с исправлениями

  1. Google adapter: проверить параметры Events.List для replacement/incremental, корректность sync token, обработку 401/403/429/5xx и поведение после token refresh; добавить integration-like fixtures для реальных API error shapes.
  2. Apple adapter: локализовать календарь, возвращающий CalDAV 500; сохранить успешные multistatus items, но не превращать повторяемую protocol проблему в бесконечный retry.
  3. Coordinator: сделать retry policy категориальной и bounded; permanent auth/permission/protocol ошибки переводить в park/paused state с ручным refresh, transient — в exponential backoff с jitter.
  4. Storage/API: сохранить безопасный last_error_code, attempt count и next retry metadata; не хранить raw provider payload в БД.
  5. Observability: добавить счётчики/structured logs для provider, outcome, retry category и latency; payloads, tokens и идентификаторы учетных записей исключить.
  6. UI: показать stale/degraded/parked источник и действие восстановления, не маскируя частичный успех календаря.

8. Проверки

  • gofmt -w ..., go test -race -count=1 ./..., go vet ./..., git diff --check.
  • Provider tests: Google 401/403/429/5xx, stale sync token, pagination; Apple 500/207, malformed resource, parked state.
  • Worker tests: один failing calendar не блокирует остальные; retry interval увеличивается и bounded; errors.Join не скрывает underlying cause.
  • Production smoke: оба контейнера healthy, нет fatal/panic, aggregate error rate снижается, sync state Google/Apple переходят в ожидаемые состояния.
  • Manual UI: healthy, stale/degraded и parked source отображаются отдельно; повторный refresh не создаёт busy-loop.

9. Риски и rollback

  • Диагностический лог может случайно раскрыть чувствительный provider payload — поэтому разрешён только allowlist полей и redaction test.
  • Изменение retry policy может увеличить freshness lag; сохраняем текущую cached projection и rollback на предыдущий immutable digest.
  • Принудительный reauth Google не является частью hotfix; credentials и DB вручную не меняем.
  • Apple provider может возвращать частично валидный multistatus при HTTP 500; нельзя удалять уже подтверждённые cached events из-за одной плохой resource.

Rollback Фазы A: вернуть предыдущий digest. Rollback Фазы B: откатить PR и digest; миграции допустимы только backward-compatible и с отдельным rollback-планом.
