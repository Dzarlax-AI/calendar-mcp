Local Calendar Mock Workbench

Approval required before implementation

Task summary

Add one explicit local development command that opens the Calendar UI with realistic, mutable synthetic data. It will make UI polishing possible without Authentik, a local Go server, connected providers, or personal calendar data.

Current behavior

  • npm --prefix frontend run dev starts Vite, but the React app requests same-origin /api/ui/bootstrap and renders “Calendar is unavailable” when no server supplies it.
  • The new visual suite already has realistic raw API fixtures and Playwright-only route interception in frontend/e2e/fixtures/calendar.ts. Those fixtures cannot serve an interactive browser session.
  • Production remains protected by ForwardAuth and browser CSRF/origin controls. This work must not weaken that boundary or call provider APIs.

Desired workflow

npm --prefix frontend run dev:mocks opens http://localhost:5173/spa/app with a populated Calendar. Create, edit, delete, refresh, filters, rich descriptions, links, recurring scope dialogs, and read-only states behave locally against in-memory mock responses. Restarting Vite resets all mock changes.

Proposed design

  1. Move the raw, provider-safe calendar fixture data into a browser-neutral module under frontend/src/dev/; Playwright imports the same source so test and workbench data cannot drift.
  2. Add a Vite development-only middleware plugin behind an explicit VITE_CALENDAR_MOCKS=true flag. It serves only /api/ui/bootstrap, event reads, refreshes, and Calendar event mutations from an in-memory store.
  3. Add dev:mocks; keep the existing dev command untouched. The mock plugin is absent from production build/preview and ordinary dev unless the flag is set.
  4. Support Calendar-only routes. Control-plane/diagnostics APIs are deliberately out of scope and retain their normal unavailable behavior until a separate request.
  5. Show a compact, development-only “Mock data” indicator in the Calendar toolbar so screenshots or demos cannot be mistaken for live data.
  6. Use a deterministic local clock/date only in mock mode, so the supplied events are visible immediately and UI sessions are repeatable.

Likely files

  • frontend/src/dev/calendarMockData.ts — shared raw bootstrap/events and in-memory mutation helpers.
  • frontend/src/dev/calendarMockServer.ts — Vite middleware handler and request/response behavior.
  • frontend/e2e/fixtures/calendar.ts — reduce to the Playwright adapter over the shared fixture.
  • frontend/vite.config.ts and frontend/package.json — opt-in dev command and Vite plugin wiring.
  • frontend/src/features/calendar/CalendarPage.tsx or a small app-level helper — mock-only visible indicator, if it can remain isolated from live behavior.
  • README.md — local command, scope, reset behavior, and “never production data” boundary.

Safety and behavior boundaries

  • No API keys, cookies, credentials, Authentik headers, provider SDKs, network calls, or real calendar data enter the mock mode.
  • Mock mode is Vite-development-only and opt-in; production builds and the Go-embedded SPA do not expose mock endpoints or bypass authorization.
  • Mutations modify memory only and reset on Vite restart. They do not create invitations or notifications.
  • Fixture HTML remains sanitized by the existing production component; the workbench must not add unsafe HTML rendering.

Verification and manual QA

  • npm --prefix frontend run typecheck, npm --prefix frontend run test, npm --prefix frontend run test:e2e, and npm --prefix frontend run build.
  • Add focused tests for mock read/mutation behavior and an E2E smoke that loads the app through the Vite mock middleware rather than Playwright interception.
  • Manual: run dev:mocks; verify populated Calendar, rich event, create/edit/delete, filter selection, and restart reset. Then run plain dev and confirm it does not supply mock data.
  • Inspect the production build for no mock endpoint/source import in the output path.

Risks and trade-offs

  • A large mock could become a second backend. Scope it to Calendar CRUD and reuse raw wire fixtures; do not imitate every control-plane endpoint.
  • Shared fixtures need small, explicit adapters because Playwright's Page.route API must remain out of browser/Vite runtime code.
  • A mock banner is intentionally visible; hiding it would make accidental demo screenshots misleading.

Model allocation

One GPT-5.6-Sol lead will implement and integrate the mock transport because the boundary between dev middleware, shared fixture contracts, and production exclusion is security-sensitive. No subagent lane is planned: the implementation is compact and parallel edits would increase fixture-drift risk. No model receives credentials or production data.

Implementation record

  • Added frontend/src/dev/calendarMockData.ts with the shared raw fixture and an in-memory Calendar CRUD store; the Playwright adapter now uses that same store.
  • Added a Vite serve-only middleware behind VITE_CALENDAR_MOCKS=true, plus npm --prefix frontend run dev:mocks. Plain dev, production build, and preview do not enable it.
  • Added a mock-only toolbar label and deterministic initial date (2026-08-25) so the workbench opens with visible events.
  • Added shared-store unit coverage and a separate Vite middleware Playwright smoke command; CI runs the smoke separately from the production-preview visual suite.
  • Documented the local command, scope, and reset semantics in README.md.

Verification record

  • Passed: npm --prefix frontend run typecheck, npm --prefix frontend test (36 tests), npm --prefix frontend run build, and npm --prefix frontend run test:e2e:mocks (1 browser smoke).
  • Confirmed the normal visual command lists its original 25 production-preview tests and excludes the mock-only smoke.
  • Local macOS visual screenshot comparison remains intentionally unavailable because the repository stores Linux baselines; CI is the authoritative baseline runner. No baseline images were changed.

Rollback

Revert the dedicated mock module, Vite wiring, command, tests, and documentation in one commit. Live UI, Go server, data, auth, and deployment remain unchanged.

Approval gate

Implementation must not begin until this plan is explicitly approved. Approval covers only local frontend mock mode and its tests/docs; it does not authorize deployment, provider calls, real-data automation, or auth changes.
