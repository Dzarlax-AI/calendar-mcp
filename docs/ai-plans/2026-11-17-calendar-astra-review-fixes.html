Границы и исходная версия

Рабочая ветка codex/google-orphan-occurrence, HEAD 24c8e163 и локальные изменения сессии, включая фильтр мастеров до LIMIT. Для контрольных замеров сохраняем именно текущее дерево с локальными изменениями. HEAD сам по себе не воспроизводит эту версию.

  • Сохраняем покрывающие ветви SQLite, фильтрацию мастеров и приоритет timed-ветви до применения общего LIMIT. Пагинация не возвращается к повторному сканированию диапазона или запросу за строками, отброшенными фильтром.
  • Сохраняем существующий буфер UI/native до 8 МиБ и 8 192 строк на один запрос. Пока результат помещается в буфер, чтение освобождает SQLite-соединение до декодирования. Для превышения лимита сохраняем потоковый путь.
  • SQLite остаётся с одним открытым соединением. Используем текущую конфигурацию пула и существующие хранилища состояния. Новые кеши, миграции, фоновые процессы и расширение пула за пределами этой ревизии.
  • Сохраняем лимиты 16 КиБ для полного SDK-ответа и 32 КиБ для сводки события, передаваемой из SQLite или PostgreSQL, TTL курсора 300 секунд и привязку к вызывающему, источникам и полномочиям. Проверки прав остаются пакетными. Успех запроса с правами записи не заменяет подтверждение прав чтения.

P1 · Доступ и доступность чтения

P1.1 · Учитывать подтверждённую роль Google из CalendarList

Из ревью. CalendarList.Get и CalendarList.List получают роль. Сейчас первое чтение использует её для метаданных, а при списочном преобразовании роль теряется. Локальное подтверждение прежней роли может оставаться действующим после наблюдения более узкой роли.

Изменение. Перед Google I/O захватить действующее локальное подтверждение для одного календаря или ограниченный набор подтверждений аккаунта для списка. Для каждой страницы сверять её результат с этим набором и с привязкой токена, которым был отправлен именно её HTTP-запрос. Перед успешным завершением обработать подтверждённое несовпадение через существующий механизм ObserveGoogleRole с проверкой актуальности. Отсутствие элемента на странице ничего не говорит о роли. Повышение роли и открытие закрытого подтверждения остаются за полным проверенным discovery. Хранить набор только в рамках вызова. Для списка использовать пакетное чтение и не делать отдельный SQL-запрос на каждую совпавшую роль.

Приёмка. Для одиночного чтения и для последующей страницы списка подтверждённое понижение исключает выдачу по старым правам сразу после обработки. Совпадение не пишет в БД. Запоздалый результат с прежним токеном, ревизией или подтверждением не закрывает новый доступ. Пропуск элемента и результаты с правом только на запись не выдают разрешение на чтение. Число вызовов Google остаётся прежним.

P1.2 · Доводить подтверждённое закрытие Google до БД при отмене запроса

Из ревью. Транзакция закрытия использует контекст исходного запроса. Если он отменён после получения подтверждённого отказа, транзакция может откатиться и оставить старое подтверждение.

Изменение. После получения и классификации подтверждения выполнить только локальную операцию закрытия с собственным коротким дедлайном. Верхняя граница для реализации — существующий ориентир 5 секунд для операций закрытия. Внешний вызов сохраняет исходную отмену. Применить тот же принцип к подтверждённому понижению роли через P1.1 и Events.List. Сохранить исходный ticket, ревизию, привязку токена, классификацию квоты и порядок блокировок. Ошибку записи пробросить как сбой операции закрытия и отразить в существующей диагностике.

Приёмка. Тесты с управляемой отменой до получения ответа и сразу после подтверждённого результата. Во втором случае запись закрывается при доступной БД. Устаревший результат оставляет новую ревизию в силе. Ошибка БД и истечение локального дедлайна видны вызывающему пути. Повторных внешних вызовов нет.

P1.3 · Подхватывать ротацию Microsoft OAuth между worker и API

Воспроизведено. Worker успешно сохраняет обновлённый токен. Два следующих независимых запроса через API с уже созданным провайдером получают конфликт снимка. Маршрут Microsoft сейчас не обновляется через RefreshProvider.

Изменение. Применить к Microsoft существующий путь сопоставления снимка токена с актуальной записью. При следующем входящем запросе заменить устаревший экземпляр соответствующего маршрута до обращения к провайдеру. Сохранить CAS при записи токена и замену маршрута с проверкой текущего экземпляра. Если ротация произошла после отправки операции, сохранить её результат и обработать новую привязку на следующем входе.

Приёмка. Два Store одного тестового хранилища, управляемые OAuth и Graph. Worker ротирует токен, следующий самостоятельный вызов API использует новую привязку. Один входящий вызов выполняет не более одной провайдерской операции, в том числе при конфликте во время записи. Параллельные обновления сохраняют новый токен и соседние маршруты. Проверить одиночное и списочное чтение, а также отправку операции записи на тестовом транспорте.

P1.4 · Обновлять окно MCP при смене дня UTC

Воспроизведено. Worker сдвигает границы окна после полуночи UTC. MCP-ридер продолжает сравнивать запрос с окном запуска и может отклонить новый диапазон, который уже покрывают источники.

Изменение. Использовать общую функцию окна worker и MCP. MCP вычисляет окно один раз на запрос по внедряемым часам. Сохраняем текущую привязку курсора к фактическим границам окна и явную проверку окна каждого источника. По этому варианту смена UTC-дня завершает действие выданного курсора с cursor_unavailable. Новый обход начинает с первой страницы.

Приёмка. Один процесс с тестовыми часами до и после полуночи принимает новый диапазон после ребейза всех запрошенных источников. Если хотя бы один источник ещё не покрыл диапазон, весь запрос закрывается. Проверить ушедшую границу, продолжение курсора в тот же UTC-день, пересечение полуночи и сохранение абсолютного TTL.

P2 · Совместимость диапазона и восстановление маршрута

P2.1 · Вернуть совпадение результатов SQLite для равных UTC-инстантов

Воспроизведено. Одинаковый диапазон, переданный как UTC или с +02:00, дал разное число событий. Writer сохраняет UTC-скаляры, а SQLite-фильтр UI/native получает исходный offset. Существующие строки, особенно Apple и Microsoft, могут иметь формат прежнего writer.

Изменение. Сначала поднять изолированный SQLite fixture с обоими форматами и зафиксировать представление скаляров на используемом драйвере. Для новых UTC-строк приводить параметры timed-фильтра к UTC. Для сохранившихся offset-строк проверить совместимость на том же запросе в пределах выбранных источников и консервативных временных границ. Окончательное решение о пересечении для таких кандидатов принимать по точным инстантам. Если совместимость требует широкого скана или отдельной миграции, вынести выбор способа обработки старых строк по результатам проверки и замеров. PostgreSQL продолжает использовать сравнение типизированных timestamp.

Приёмка. Одинаковые набор и порядок на эквивалентных диапазонах Z, +02:00 и -05:30, включая переход даты, доли секунды, точное касание границы и all-day. Проверить старые и новые строки каждого провайдера, UI и native входы. Исходные offset и timezone в payload сохраняются. План запроса MCP и поведение буфера подтверждаются отдельно.

P2.2 · Восстановить live-маршрут Google после успешного bootstrap

Из ревью. API при старте пропускает pending-подключение. Worker завершает bootstrap в отдельном процессе. Поиск отсутствующего маршрута прерывается до вызова функции обновления.

Изменение. Если канонический маршрут Google отсутствует, проверить в БД только нужное подключение. При подтверждённой готовности создать маршрут существующей фабрикой и зарегистрировать его с проверкой актуальности. Для списочной выдачи, где вызывающий ещё не знает ID, добавить одну пакетную проверку появившихся готовых подключений. Оставить прежние ограничения на fan-out и порядок результатов. Для pending, failed или неизвестного подключения сохранить отказ.

Приёмка. API стартует до завершения bootstrap. После успешного завершения явное чтение и список видят маршрут без перезапуска. Неудачный bootstrap не открывает его. Конкурентные запросы сохраняют один актуальный маршрут, соседние провайдеры остаются доступны. Регистрация сама по себе не вызывает Google и не отдаёт кэшированную страницу.

Отзыв доступа в UI/native

До изменения события и статусы источников читались разными запросами. При отзыве между чтением payload и сборкой ответа источник мог исчезнуть из статусов, а его события оставались в ответе. У современного MCP своя финальная проверка полномочий.

ВариантПоведение и цена
Доступ на момент чтенияСобытия из начального снимка могут попасть в один уже начатый ответ после отзыва. Сохраняет текущую семантику и задержки.
Проверка перед возвратом результатаПредпочтительный вариант для дальнейшей проработки. Сопоставить полномочия снимка события с действующими при уже существующем пакетном чтении статусов после декодирования. При отзыве или смене поколения убрать события этого источника из результата. Остальные источники проходят при сохранённых полномочиях. При невозможности выполнить финальную проверку действует существующий путь ошибки запроса.

Граница проверки

  • У Google есть authorization_revision для подключения и detail_receipt для календаря. Обычная ротация OAuth-токена сохраняет оба значения. Прежний ответ можно отбросить при несовпадении хотя бы одного значения или при недоступности источника.
  • При явном переподключении Apple или Microsoft существующее подключение получает новую authorization_revision. В той же транзакции старая проекция удаляется, lease сбрасывается, а результат discovery принимается только для исходной ревизии.
  • Изменение прав одного календаря Apple или Microsoft меняет его собственное подтверждение доступа и сбрасывает только его проекцию. Продление OAuth и захват lease штатной синхронизацией сохраняют полномочия. Паркование задания само по себе остаётся статусом синхронизации.

При чтении фиксируем полномочия выбранных источников, включая пустые, в одном снимке с событиями. После декодирования пакетный запрос статусов сравнивает их с текущими полномочиями. Календарь определяется по ID строки SQL. При несовпадении события этого источника исключаются, для источника выставляются unavailable и stale=true, а ответ получает complete=false. Ошибка финальной проверки завершает запрос ошибкой. Гарантия действует на момент финального снимка БД.

Операции над серией продолжают использовать отдельный путь с проверками записи. Буфер сохраняет лимиты 8 МиБ и 8 192 строки. Пока выборка помещается в буфер, SQLite-соединение освобождается до декодирования. Для переполнения остаётся потоковое чтение.

Локальная приёмка

В синтетических проверках быстрый reconnect сохраняет соседний источник, исключает события старой ревизии и открывает новую проекцию для следующего запроса. Тесты охватывают потоковое чтение, пустой источник, позднюю верификацию, сохранение авторизации при ротации OAuth, отзыв одного календаря и ошибку финального чтения.

Тяжёлое чтение Store для UI. Шесть пар свежих процессов, по четыре параллельных запроса, 16 источников и 3 599 событий с описаниями по 2 КиБ. Медиана составила 192,5 → 196,6 мс (+2,1%), выдача совпала. Пул SQLite сохранил одно открытое соединение.

Полный race-прогон прошёл с 760 успешными тестами и одним пропуском PostgreSQL. Отдельный интеграционный прогон Storage с PostgreSQL прошёл все 124 теста, включая reconnect Google, Apple и Microsoft. Проверки go vet и сборки сервера прошли.

Порядок выполнения и откат

Контрольная точка 0 · Сохранить исходную версию
Координатор фиксирует состав локальных изменений, исходный бинарник и синтетические замеры. Этот комплект позволяет принять каждую фазу независимо и сохранить работу сессии при откате.
Контрольная точка 1 · Закрыть P1
Предлагаемые исполнители — Terra с высоким усилием для ограниченных участков. Один исполнитель ведёт Google transport и Store для P1.1–P1.2. Изменения Microsoft в Factory и Registry идут после согласования связки с Google, чтобы у Factory был один активный редактор. Изменение окна в runtime и cachedpages независимо по коду и может идти параллельно. Для каждого участка вернуть diff, целевые тесты, результаты и ограничения. Astra 6.2 проверяет фактический diff на гонки, пропуск закрытия, ошибки привязки и границы курсора. Координатор принимает совместный результат по проверкам и замерам.
Контрольная точка 2 · Закрыть P2
После приёмки P1 исполнитель Storage проверяет совместимость старых строк и правит диапазон. Исполнитель Registry берёт bootstrap после стабилизации P1.3. Оба возвращают diff и локальные проверки. Astra 6.2 проверяет изменения на совместимость и повторные запросы. Координатор проверяет совместный результат, включая набор мастеров и тяжёлый UI.
Отдельная проработка UI/native
Проверить источники идентификатора поколения, семантику частичного ответа и задержки. Вернуться с предлагаемым контрактом и объёмом работ до изменения поведения.

Откат. При непрохождении проверок обратимо снять только изменения проблемной фазы по сохранённому diff. Перепроверить корректность состояний и повторить замер на сохранённой исходной версии. Для будущего запуска со схемой 008 использовать только совместимую версию с проверкой полномочий у всех писателей. Изменения production в этот план не входят.

Локальная реализация P1, P2 и проверки отзыва UI/native согласована и выполнена. Операции с реальными аккаунтами, commit, push и деплой требуют отдельного решения.

Правила реализации и согласования

Результаты локальной реализации

  • P1. Google применяет все подтверждённые изменения ролей на полученной странице и сверяет каждый ответ с токеном этого запроса. Подтверждённое закрытие использует отдельный локальный дедлайн. Ошибка закрытия различима в CalendarList, Events.List и worker. Microsoft заменяет только устаревший маршрут и проверяет новый снимок перед установкой. MCP пересчитывает окно UTC на запрос. Курсор, пересёкший границу окна, возвращает cursor_unavailable.
  • P2. SQLite отбирает timed и all-day в индексных диапазонах одного запроса и сортирует ключи до чтения payload по rowid. Для сохранённых старых offset-строк точное сравнение выполняется до помещения события в буфер. Готовый Google-маршрут появляется после bootstrap по запросу или при списочной выдаче. Ошибка верификации и неизвестный аккаунт не подставляют соседний маршрут.

Отдельный race-прогон Storage с одноразовой PostgreSQL — 111 тестов, включая пропущенный ранее. go vet и сборка сервера прошли. Все девять проверок p95 первой страницы уложились в пороги. На SQLite с 16 источниками p95 составил 5,2–5,5 мс при одном клиенте и 14,2–15,7 мс при четырёх.

Ограничения P1 и P2. При отмене на остальных операциях Google SDK может вернуть отмену вызывающему коду. Сбой локального закрытия фиксируется в серверной диагностике. Прежнее краевое поведение SQLite при переходе UTC-скаляра в пятизначный год остаётся вне проверенного диапазона. Порядок выборки подтверждён на закреплённой версии драйвера.
