Google OAuth reconnect fix

Approval: approved by the user on 2026-08-22.

Scope and current behavior

Fix Google reconnect when the OAuth exchange returns a new access token without a new refresh token. Production currently saves that response over the previous credentials, then ignores the saved token during provider construction and fails verification.

Desired behavior and assumptions

Preserve the previous refresh token when the provider omits a replacement, and use any successfully loaded saved OAuth token. Existing encrypted credential storage and provider routing remain unchanged.

Likely files and steps

  1. Add regression coverage in internal/connections/service_test.go and internal/google/auth_test.go.
  2. Merge the prior refresh token during reconnect and stop rejecting access-only saved tokens.
  3. Run focused tests, race tests, vet, and build.

QA, risks, and rollback

QA covers both credential merge and provider HTTP authorization. Main risk is retaining a stale refresh token when Google intentionally omits it; OAuth semantics make preservation the expected behavior. Rollback is reverting the two source changes. No production mutation is part of this approved implementation step.

Open questions and approval gate

No open implementation questions. Commit and deployment require separate explicit approval after local verification.

Implementation record

Implemented on 2026-08-22. Reconnect now retains an existing refresh token when Google omits a replacement; provider construction accepts a saved access token without requiring a refresh token; Google authorization requests explicit consent so an already-damaged production connection can obtain a new refresh token.

Verification: the three focused regression tests passed; go test -race -count=1 ./..., go vet ./..., and the server build all exited successfully. Production remains unchanged and still requires a deployment followed by one interactive Google reconnect.
