SQLite: меньше повторной работы, короче очередь

17 ноября 2026 · Revision 1 · Диагностика завершена · Implemented: A+B выполнены; сравнение полного обхода завершено

Предложение: два обычных индексных пути timed/date и раннее освобождение соединения UI-читателем. Без новых кешей, индексов, миграций, очередей или расширения пула. Сложный top-K по источникам не включён.

1. Точка отсчёта

Текущий локальный R7 уже откладывает summary JSON до LIMIT и пакетно проверяет актуальность подключений после Pack. На этапе диагностики runtime не менялся и все 200 файлов final source manifest R7 совпадали по SHA-256. После явного согласования внедрены A+B; результаты приведены ниже. Production не менялся. Ветка codex/google-orphan-occurrence, HEAD 24c8e163b7e301040922f29b5f39ace150e3083d; чужой WIP сохранён.

Запрос — ускорить повторное чтение SQLite и обход 16 источников с фоном, сохранив простоту сервиса. Предыдущий план A–C выполнен; его согласование не распространяется автоматически на этот новый runtime diff.

2. Откуда берутся секунды

4000 событий / 16 источников требуют 334 SDK-страницы: ответ ограничен 16 KiB с повторяемыми source metadata и text/structured представлениями. Это полный обход, а не длительность одной страницы. Стрессовый фон пытается читать полный UI-список и выполнять sync-запись каждые 5 мс; это не измеренная production-нагрузка.

Это три полных обхода текущего frozen R7. Строки таблицы не покрывают все фазы. В начальном снимке нет отдельного wait-таймера; доминирование очереди следует из контрольного прогона без фона. Перенос его работы в другой метод сам по себе перенесёт ожидание вместе с ней. Слияние двух metadata-чтений может убрать небольшие накладные расходы, но не объясняет основной выигрыш.

SQLite заново собирает rowid всего окна через range UNION, затем применяет внешний cursor и сортирует остаток. На каждой странице повторяется работа с уже пройденным диапазоном. Отдельные native range-пути позволяют передать нижнюю границу курсора в индекс сразу.

3. Что проверять в single-tenant

Межпользовательская ACL этому случаю не нужна. Существующая проверка относится к жизненному циклу подключения: аккаунт активен, receipt/revision соответствуют текущей авторизации, старый cursor не продолжает предыдущее подключение. Google не опрашивается при чтении страницы; удалённые изменения доступа учитываются только после того, как сервис их наблюдал.

Финальная проверка после Pack отклоняет уже загруженную страницу, если до этой проверки источник успели локально отключить или переавторизовать. Это текущий согласованный контракт. Его можно отдельно ослабить до разрешения старых ответов уже начатых запросов, но удаление этой проверки не устраняет занятое UI-читателем соединение. Для данного этапа не добавляем новые проверки, роли или ACL; существующие snapshot/cursor fences сохраняем.

Медианы трёх последовательных SQL-only обходов после reference-прогрева, без HTTP/Pack/фона. Большой корпус имеет 160 SQL-страниц, поскольку выдаёт 25 строк за шаг; SDK с source metadata выдаёт меньше и требует 334 страницы. Все варианты сохранили порядок ID/calendar и projected JSON. Малые fixtures также содержат одинаковые IDs между источниками, timed/all-day границу, stray dates, masters и oversized summary.

Выбор — две global ветки. Их выигрыш 1,46× в большом SQL-only случае меньше, чем у top-K, зато поведение проще и нет почти тройного проигрыша на tied данных. У текущих индексов event_id не входит в сортирующий префикс после start: большие группы одинакового времени всё равно требуют сортировки. Top-K не даёт гарантии короткого сканирования таких групп.

Прототип global split использует covering range scan существующего индекса, затем отдельный rowid lookup для master-фильтра и ключей. Типы и порядок проходят старые условия до LIMIT; summary JSON строится только для окончательных page_size+1 строк. Прямое native-сравнение без защиты типов пропустило повреждённый numeric start_at. Проверенный вариант сначала проверяет такой случай по полям timed-index и при его наличии использует неизменённый текущий SQL. В runtime оба запроса должны быть внутри одного read snapshot; prototype проверял статические данные.

UI-читатель: JSON сейчас декодируется, пока открыты SQL rows. В отдельном эксперименте перенос decode после Close сократил удержание соединения 25,49 → 11,28 мс, сохранив общее время 25,49 мс и полное содержимое EventV2. Для этого потребовался временный буфер 2,97 MB сырых данных внутри одного вызова, без повторного использования между запросами.

С лимитом raw buffer 8 MiB корпус с description 2 KiB переключился обратно в streaming во всех 20 итерациях: удержание 54,72 → 53,49 мс. Для него существенного выигрыша нет. Это проверка удержания слота, а не измеренное ускорение всего SDK. Процессный RSS кандидата с фоном ещё не измерен.

6. Приёмка, ограничения и gate

Критерии приёмки (результаты ниже): сравнить frozen текущий R7 с A, затем A+B, отдельно с прежним фоном и без него. Повторить парные полные обходы 400/4000, 1/16 источников, page_size25/50, C1/C4, sparse/ties/mixed/master/jumbo. Сохранить counts/digests и source freshness. Отдельно измерить UI connection hold, total time, raw-buffer fallback и natural-GC RSS. Требуется фактическое улучшение полного 16-source обхода с фоном; SQL-only выигрыш не заменяет этот результат.

Тесты: covering plans и cursor bounds; одинаковые времена/IDs и разные end_at; числовые/blob/слишком длинные scalars; UTC offsets, дробные секунды и end не в полночь; границы 8 MiB и 8192 строк; tiny/large/malformed JSON; cancellation до/после Close; concurrent disconnect/reconnect; late series writes. Сохранить after-Pack revoke, expiry, single-slot release, 16 KiB SDK /32 KiB transfer. Прежние first-page SLO C1≤50 мс/C4≤100 мс. Финальные Go race/vet/build и PostgreSQL integration подтверждают отсутствие побочного изменения общей storage логики.

Первоначальные SQL-only эксперименты не покрывали произвольные RFC3339 окна и candidate SDK implementation; после реализации проверены целевые границы, SDK parity и cancellation. Диагностический UI-прототип ограничивал только raw bytes; runtime дополнительно ограничивает число строк и проверяет переключение путей. Три итоговых раунда не дают p95 полного обхода. Для больших payloads streaming fallback ожидаемо сохраняет прежнюю очередь. Ограничение raw buffer не является жёсткой границей RSS; измерить одновременные UI-вызовы обязательно.
