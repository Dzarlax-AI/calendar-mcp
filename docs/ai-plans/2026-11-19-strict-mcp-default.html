Единый каталог Calendar MCP

19 ноября 2026 · Редакция 2 · Заменяет предложение об условном дефолте. Локальная реализация согласована и проверена. Выкладка вне объёма.

Целевой контракт

Один основной маршрут /mcp с теми же 12 инструментами, которые уже доступны на рабочем строгом маршруте. Шесть чтений используют локальные права и публикации. Шесть записей сохраняют типизированные схемы, живой вызов провайдера и действующий учёт квитанций. В документации он называется Calendar MCP. Прямой клиент подключается с ключом Calendar. Gateway использует тот же маршрут.

Платформенный worker автоматически выполняет проверку прав, публикацию и сверку записей при включённой модели событий. При отсутствии актуального снимка API возвращает действующую ошибку готовности или неполное покрытие. Чтение не инициирует вызовы провайдера.

Что уйдёт из конфигурации

Для опубликованного /mcp требуются модель событий, платформенная БД, шифрование и основной ключ. Действующие native/UI/REST профили сохраняют собственные требования.

При отсутствии условий запуска MCP возвращает 404. Существующий запуск без DATABASE_URL сохранит REST при настроенном слушателе. Standalone MCP с чтением напрямую у провайдера будет снят. Пользователям такого MCP понадобится платформенная установка с worker.

Переход клиентов

  • Рабочий Gateway уже использует основной /mcp в строгом режиме. Последняя проверка обнаружила в активном реестре одну календарную запись. Это покрывает Gateway, а прямых потребителей ещё предстоит инвентаризировать.
  • Снять отдельные /mcp/modern и /mcp/compat после миграции их потребителей. Схемы get_events на этих путях отличаются от нынешнего строгого /mcp, поэтому переходу нужны проверка аргументов, результата и пагинации. После снятия старые адреса возвращают 404.
  • Отдельно проверить потребителей Google-инструмента get_cached_events, который сегодня доступен на явном /mcp/modern. Дать клиентам эквивалентный сценарий через строгий get_events или уже существующий нативный маршрут, подтвердив разницу в правах и покрытии. При обнаружении клиента, которого нельзя перевести, согласовать переходный срок до удаления его контракта.
  • Сохранить рабочие имена и схемы строгих инструментов в tools/list, канонические идентификаторы, входные лимиты и правила доступа. Gateway должен принять существующие контракты чтений и записей без изменения ACL.

Объём реализации и проверка

  1. Сверить свежий origin/main и перечень зарегистрированных клиентов. Исходное дерево сейчас соответствует de20bc1. Проверить готовность к снятию старых маршрутов и get_cached_events до удаления.
  2. Упростить регистрацию каталога в internal/mcpserver, конфигурацию в internal/config и запуск API/worker в internal/runtime. Обновить .env.example, README, инструкции проекта, затронутые тесты и синтетические сценарии. Миграция БД для одного каталога не предусмотрена.
  3. Проверить полный Go race suite и go vet. Через локальный Gateway и прямой MCP сверить 12 схем, шесть чтений, 7/7 на страницах, отсутствие provider I/O для чтений, действующие квитанции и защиту после записи. Локальные сценарии записи использовать только с изолированными провайдерами.
  4. Проверить старые пути, конфигурации со снятыми переменными, совместимость REST V2, native/UI и запуск worker. Проверить, что ни один старый путь не создаёт дополнительный каталог и что конфигурация без локального источника не переключается на живые чтения.

Для отката использовать текущий совместимый двоичный артефакт с прежней конфигурацией и уже активированным строгим режимом. Рабочие параметры, публикация PR и выкладка требуют отдельного разрешения.

Согласованный объём

Согласовано оставить один строгий /mcp, убрать три флага выбора и перевести worker на обновление платформенных публикаций автоматически. Это включает снятие standalone MCP и старых адресов после проверки потребителей. Флаг REST V2 остаётся в пределах текущего контракта REST. Рабочий сервер остаётся на прежней версии.

Локальные результаты

  • До правок рабочий реестр Gateway подтвердил одну включённую календарную запись на основном маршруте и шесть классифицированных чтений. Конфигурация personal-assistant указывает на внешний адрес, который переписывается в основной /mcp. В просмотренных конфигурациях personal-ai-stack, Display, Book, Calendar App, calendar-sync и Codex ссылок на снятые каталоги или get_cached_events не найдено. Внешние конфигурации, которыми мы не управляем, остаются за границей этой инвентаризации.
  • Обычная сборка регистрирует только строгий /mcp и его завершающий слеш. Старые пути возвращают 404. Запуск без платформенной БД сохраняется для явно настроенного REST. ENABLE_V2 управляет только REST. Исторические MCP-фикстуры собраны за отдельным тестовым тегом.
  • Три старые переменные исключены из выбора поведения. Совместимые прежние значения принимаются с предупреждением для миграции. Явные несовместимые значения и старый режим подготовки API отклоняются. Обычная настройка .env.example включает платформенную модель событий.
  • Все 12 определений tools/list совпали с прежней строгой сборкой. Сценарии локального Gateway проверили шесть чтений без provider I/O, отзыв, курсоры, ACL и защиту записей. В семиисточниковом сценарии два прогрева дали 7/7. Изолированные отказы дали 6/7, последующее подтверждение и публикация восстановили 7/7.
  • Пройдены Go race suite, целевые проверки конфигурации и runtime, исторические тесты MCP, go vet и сборка. README описывает единственный маршрут, кэш, миграцию клиентов, REST-only и сделанные замеры. Рабочих изменений и календарных записей не выполнялось.
